- Сайт отвечает 200: web :3000, публичный ai-aggregator.ru, TMA :3100/health.

## Что сломано
`web` — 30 172 перезапуска, `worker` — 27 265. Оба в статусе `waiting restart`.
Причина: они падают с `EADDRINUSE`. Порты 3000/3100/3101 держат ПРОЦЕССЫ-ОРОФАНЫ,
которые запущены вне текущего PM2 (родитель — PM2 God Daemon из /srv/aiag/.pm2,
но PM2 их не видит как свои живые). Эти процессы живут с 29 сентября, аптайм 36+ часов.

**Следствие, которое важно не перепутать:** сайт отвечает 200, но обслуживается
устаревшим кодом. Фиксы безопасности в `apps/web` (KYC-гейт, setRole) в проде НЕ работают.

## Почему не чинил сразу
Перезапуск без подготовки уронит работающий сайт. Нужен аккуратный разбор: кто именно
держит порты, как они соотносятся с записями PM2, и только потом замена. Пока это не сделано,
`web` нельзя обновлять — любой деплой снова упрётся в занятый порт.

## Вывод для следующего деплоя
`pm2 restart` из скилла aiag-deploy НЕ РАБОТАЕТ как написано: команда по умолчанию смотрит
в /root/.pm2, а приложения живут под /srv/aiag/.pm2. Нужен `PM2_HOME=/srv/aiag/.pm2`.
Плюс проверять аптайм, а не код ответа: /health отвечает «ok» и при старом процессе.

## Обновлено 03.10: web починен в коде, но задеплоить не удалось

`apps/web` **собирается** — TDZ-ошибка («Cannot access 'C' before initialization») была
реальной: `topModels` вычислялся на этапе импорта через `flatMap`, а `MODEL_TYPE_CHIP`
объявлялась ниже. Починка — перенос декларации выше. Проверено `next build` до конца.

Деплой web на VPS НЕ удался, три причины подряд:

1. **`bun install` на сервере падает**: bun 1.3.13 не понимает `lockfileVersion: 3`
   (репозиторий требует bun 1.4.2). Релиз загружался, но установка зависимостей
   прерывала деплой ДО переключения симлинка — прод при этом не страдал.
2. Обход: `node_modules` скопирован из работающего релиза (как уже делали для gateway) —
   новых зависимостей web не добавлял.
3. **`next start` порождает дочерний `next-server`, который переживает `pm2 restart`
   и продолжает держать :3000.** Новый процесс не мог занять порт — `EADDRINUSE`.
   После явного убийства держателя порт освободился, но новый релиз всё равно не поднялся;
   в логах PM2 причина не читается (пусто).

Сайт всё это время отвечает 200 на старом релизе `20260823T203722Z-eac8ae0`.
Новый релиз лежит на диске: `20261001T000310Z-f8fd40e`.

Вывод для будущих деплоев: одного `pm2 restart` мало для Next-приложений — нужно
останавливать pm2-запись И убивать процесс, реально слушающий порт. Плюс проверять
аптайм нового pid, а не только HTTP 200: в откате HTTP был 200 при старом процессе.
