## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client UI → TMA API | All server-side guards (ownership, price, atomicity) live in plan 02/03 routes; the UI is a thin client. The panel must never be the trust point. |
| user → TON Connect | The mint tx is signed in the user's own wallet; the UI cannot move funds on its own. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-16-16 | Spoofing | client-side isOwner | mitigate | `isOwner` is a UI hint only; every write the panel triggers is re-guarded server-side (make-transferable guards id+tg_user_id; transfer guards transferable + self-deal). A tampered client cannot bypass the server guards. |
| T-16-17 | Information Disclosure | white-label / currency | mitigate | Panel shows credits + TON only, never ₽, never "Startonus" (verified by grep) — upholds the white-label + crypto-only TMA rules. |
| T-16-18 | Repudiation | honest pending state | mitigate | The UI shows submitted ≠ done ("право перейдёт после подтверждения ~1-3 мин") — never claims the transfer completed before the webhook confirms (PRODUCT.md UI=reality). |
| T-16-19 | Tampering | clone/rent confusion | accept | Disambiguation is copy-level; a confused user is a UX risk, not a security one. Mitigated by explicit MOVE-vs-COPY wording. |
