# Phase 16 (R1.4) — Передаваемый агент (iNFT-на-TON) — DISCUSS / CONTEXT

## Founder decisions captured this session (2026-06-10)

1. **Цель фичи = «и то, и другое в одной механике»** — одна механика «передача права собственности на агента с переносом обезличенной памяти» обслуживает И дарение/передачу, И продажу выращенного агента.
2. **Что переходит = агент БЕЗ личной истории** — настройки + «обученная» память/знания едут; личные диалоги прошлого владельца стираются. → ре-шифруется только обезличенная часть, приватность прошлого владельца защищена стиранием.
3. **Минт = ленивый, в момент передачи/продажи, ЗА СЧЁТ приобретателя через Startonus** (founder 2026-06-10). «Сделать передаваемым» = бесплатный DB-флаг + цена (без газа). Реальный mint происходит при фактической передаче: NFT минтится прямо на TON-кошелёк ПРИОБРЕТАТЕЛЯ, который сам платит за минт в TON через TON Connect (для продажи — плюс цена агента в кредитах). **Переиспользуем существующий Startonus-плюминг Phase 15** (`packages/shared/src/startonus.ts` `generateInvoice` → TON Connect tx → `nft/webhook` confirm). Founder'ское «retire Startonus» (CLAUDE.md decision #4) **отменяется** в пользу репурпоса под НЕ-спекулятивный agent-iNFT (это механизм минта, не спекулятивная коллекция «Знаки»).

## The mechanic — три РАЗНЫХ действия (product clarity)

| Действие | Что делает | Оригинал | Память | Кол-во |
|---|---|---|---|---|
| Клонировать (есть, Wave-1) | копия спека | остаётся у автора | без памяти | 1→много |
| Аренда (есть, Wave-1) | платишь сумму автора → клон | остаётся у автора | без памяти | 1→много |
| **Передать/Продать (NEW R1.4)** | переносишь ОДИН экземпляр | **пропадает у старого** | обученная едет, личные чаты стёрты | **1→1** |

Ключ: clone/rent = **копия** (оригинал жив); transfer = **перемещение** (оригинал теряется). 1-of-1 «вещь».

## Что переходит / что нет

- ✅ **Едет:** персона (SOUL), конфиг моделей, скиллы/инструменты/MCP-дефиниции (БЕЗ ключей), обученная память/знания (ре-зашифрованная).
- ❌ **Не едет:** ключи/секреты (новый владелец подключает свои — правило «spec-not-data»), личная история диалогов (стирается), баланс/бюджет (у нового владельца свой).
- **После передачи:** агент работает на аккаунте/балансе/ключах нового владельца.

## Архитектура (TON-нативно, Startonus-минт-при-передаче, off-chain re-key)

1. **«Сделать передаваемым»** = бесплатный DB-флаг + (для продажи) цена. Без газа, без чейна — просто помечаем агента передаваемым/продаваемым.
2. **Передача/продажа (асинхронный flow — точный аналог `nft/purchase` + `nft/webhook` Phase 15):**
   - (a) приобретатель инициирует → создаём pending-transfer запись → `generateInvoice` (Startonus) на mint NFT прямо на **TON-кошелёк приобретателя**, `userData` = transfer_id, callbackUrl = `…/tg/api/tma/agents/transfer/webhook`;
   - (b) приобретатель платит **за минт в TON через TON Connect** (для продажи — плюс цена агента в кредитах, атомарно на этом же шаге);
   - (c) Startonus минтит → callback на webhook → подтверждение;
   - (d) **по webhook, атомарно (один `sql.begin`):** `UPDATE agents SET tg_user_id = new WHERE tg_user_id = old` (guard на старого владельца), `DELETE FROM agent_runs` (стереть личную историю), зачистить секреты/ключи, ре-шифровать обученную память на ключ нового владельца (когда появится — D-5), при продаже — кредиты продавцу (**AIAG 0%, как author-rent**, две equal-and-opposite `tg_ledger_entries`, идемпотентность по `(ref_kind, ref_id, kind)`); cash-out наружу gated **FD-2**.
3. **Без вторичного рынка / bonding-curve / котировок.** Цену ставит владелец. Рамка «вещь», не «доля» (анти-Virtuals).

**Минт-модель:** NFT минтится на приобретателя в момент акции (mint-on-acquire через Startonus), а не «transfer существующего токена». Сжигать/игнорировать старый сертификат при ре-продаже vs on-chain transfer — деталь для plan-phase. **Кто платит минт при ДАРЕНИИ** (получатель vs даритель) — открытый вопрос plan-phase.

## Переиспользует уже готовое (Wave-1 LIVE на проде)

Владение агентом, author-rent расчёт (0% cut, payout в кредиты), коллекционные карточки, atomic-транзакция (Wave-1 paid-rent `apps/tg-miniapp/app/api/tma/templates/[id]/rent/route.ts` — guarded debit + seller credit + 2 ledger-entries + идемпотентность). **+ Startonus mint-плюминг Phase 15**: `packages/shared/src/startonus.ts` (`generateInvoice`), `app/api/tma/nft/purchase/route.ts` (pending→invoice→TON Connect tx), `app/api/tma/nft/webhook/route.ts` (async mint confirm), `BuyButton.tsx`. По сути **+1 тип транзакции + репурпос Startonus** — почти ничего с нуля.

## Скоуп-каты (YAGNI)

НЕ делаем: 0G (несовместим с Telegram TON-only + не нужен), on-chain память, TEE/oracle-сеть, proxy-re-encryption (простого backend decrypt→re-key достаточно — личные чаты стёрты), вторичный рынок, мульти-чейн, СВОЙ mint/facilitator (используем Startonus). Минт ленивый — только при фактической передаче, за счёт приобретателя.

## ⚠️ Honest-флаг по зависимости (sequencing)

«Обученная память/знания» сейчас почти пустая: память агента = «10 последних пар» (`loadHistory(...,10)`); полноценная pgvector-память — это **R1.2 D-5 (ещё НЕ построена)**. Поэтому:
- **MVP R1.4** = передача владения + спека (персона/конфиг/скиллы) + стирание истории + Startonus mint-on-acquire (за счёт приобретателя) + продажа за кредиты.
- «Перенос знаний с ре-шифрованием» наполняется смыслом **только после D-5**. Можно шипнуть владение+передачу сейчас, memory-re-key включить позже.

## Startonus — как работает на самом деле (research 2026-06-10, docs bot.startonus.com/docs)

**Создание коллекции = НЕ через API, только вручную через бота** `@startonus_bot`:
- `/createCollection` (бот деплоит контракт коллекции на TON) ИЛИ `/importCollection` (импорт существующей из Getgems).
- Затем в профиле приложения настраиваются **mint-set шаблоны** (название/описание/картинки/цены) → `/createMinterSecret` (секрет) → template `id` берётся из `/mintStats` или админки.
- Стоимость деплоя / владелец контракта в доках НЕ указаны → **проверить прямо в боте** (вероятно небольшой TON-fee за деплой).

**Вывод по модели:** коллекция создаётся ОДИН раз ВРУЧНУЮ (нами/founder), не per-user и не per-agent (API создания нет → тысячи коллекций невозможны). Правильная модель = **ОДНА общая коллекция «Агенты»**, каждый агент = **item** в ней, кастомизируется через `nftData` (имя/портрет/атрибуты агента → тянется в коллекционную карточку, связка с D-14).

**Минт = один эндпоинт** `POST /api/minter/generate-invoice/custom` (`secret` в теле):
- `id` (template id), `address` (адрес коллекции), `secret`, `owner: {tgId, userName?, wallet}` (получатель — ОБЪЕКТ), `nftPrice?`, `nftAmount?`, `nftData?: {name, description, image, content?(видео mp4), attributes?[], buttons?[]}`, `callbackUrl?`, `userData?`.
- Ответ: `{id, to, value, payload, validUntil}` → TON Connect tx. Success-callback: `{success, item, owner, referrers[], mint, userData?}`.

⚠️ **КРИТИЧНО: наш Phase-15 `packages/shared/src/startonus.ts` УСТАРЕЛ vs текущий API.** Наш код шлёт `{collectionId, price, recipient(строка), …}`, а docs требуют `{id(template), address, owner(объект {tgId,wallet}), nftPrice, nftData}`. → План «reuse startonus.ts as-is» НЕВЕРЕН: клиент надо **переписать** под актуальный шейп (+ добавить `nftData` для карточки агента) и проверить на боевом боте. Это новая задача в plan (правка 16-03 + shared-клиент).

**Operator-setup (расширен):** создать коллекцию «Агенты» через @startonus_bot → настроить mint-template → `/createMinterSecret` → взять template `id` (`/mintStats`) → env: `STARTONUS_SECRET`, `STARTONUS_AGENT_COLLECTION_ADDRESS`, `STARTONUS_AGENT_MINT_TEMPLATE_ID` (+ `PUBLIC_BASE_URL`).

## Founder-gates / риски

- **FD-2** (выводимость кредитов наружу) — нужна только для cash-out продавца наружу; продажа за кредиты ВНУТРИ работает без неё.
- **FD-3** (two-entity) — крипто-передача/NFT на зарубежном юрлице.
- **Telegram TON-only** (blockchain guidelines) — ок, мы и так на TON; ETH/SOL = де-листинг (не вводить).
- **Юр-якорь:** utility-право доступа, вне ЦФА 259-ФЗ; не торгуемая «инвестиция».
- **Risk:** backend как доверенная точка ре-шифрования (модель доверия выбрать в plan); риск смешения со спекуляцией (рамкуем как «вещь»).
- **Startonus-зависимость:** внешний минтер (`bot.startonus.com`); нужны `STARTONUS_SECRET` + Startonus-коллекция для агентов (через @startonus_bot). Async-mint = transfer финализируется ТОЛЬКО по webhook → обязательны pending-state, идемпотентный webhook, обработка failed/timeout (как `nft_purchases.status`).

## Открытые техн. вопросы → решить в plan-phase

1. Модель доверия ре-шифрования: backend decrypt→re-key (рекомендую) vs proxy-re-encryption.
2. Минт через Startonus: создать Startonus-коллекцию «Агенты» (через @startonus_bot) + завести `STARTONUS_SECRET`; цена минта (mint-fee в TON); кто платит минт при ДАРЕНИИ (получатель vs даритель); сжигать старый сертификат при ре-продаже vs on-chain transfer.
3. Где живёт «обученная память» до D-5 — MVP без неё (только конфиг+персона) ИЛИ лёгкая зависимость от D-5.
4. UX-поверхность: где в TMA живут «сделать передаваемым», «подарить», «продать» (отдельный экран vs действия на карточке агента); как не путать с clone/rent.
5. Схема БД: новые колонки/таблицы (`agent_ownership`/`agent_transfers`/NFT-привязка); миграция (manual `sudo -u postgres psql`, RK-8).

## Success criteria (предварительно)

1. Владелец может «сделать агента передаваемым» → минтится TEP-62 NFT на TON, агент-карточка показывает статус «передаваемый».
2. Дарение 1:1: агент атомарно переходит другому юзеру; личная история стёрта; старый владелец теряет доступ; NFT у нового владельца.
3. Продажа: покупатель платит кредитами → продавец получает кредиты (AIAG 0%) → передача как в п.2; всё в одном `sql.begin`, без двойного списания.
4. Невозможно: продать чужого/уже-переданного агента; утечка ключей/секретов; появление вторичного рынка/котировок.
5. UI честно различает clone/rent (копия) и transfer (перемещение).
