# TON: отдельные полномочия worker и репетиция восстановления

Дата: 29.09.2026. Этот документ описывает проверяемый локальный кандидат, а не включённые production-платежи.

## Граница полномочий

Четыре независимых роли: Web LOGIN, API LOGIN, TON worker LOGIN и владелец финансовой функции NOLOGIN. Владелец не имеет административных атрибутов; worker не может принять его роль. Исполняемая точка — `aiag_ton_worker.settle_invoice_v1(uuid,jsonb)`. Она проверяет `SESSION_USER`, разрешает только native TON/testnet, выполняется с явно закреплённым `search_path` и вызывает неизменённое существующее финансовое ядро.

У Web/API и worker нет прямого выполнения старой функции и прямой записи в защищённые балансы, события, квитанции и решения. Владелец функции получает только необходимые чтения/вставки и выбранные колонки UPDATE. Для блокировки строки события требуется право UPDATE на одну колонку; сам immutable trigger по-прежнему запрещает изменение события. Worker получает только чтение и два неизменяющих validation-helper для отложенной проверки согласованности при COMMIT. Эти права не превращаются в разрешение самостоятельно править деньги.

Установщик `packages/database/scripts/ton-worker-boundary.ts` принимает только отдельный локальный адрес тестовой дочерней БД на `127.0.0.1:15432`, при `AIAG_TEST_DATABASE=1`. Он сам открывает новый ограниченный по времени клиент: передать чужую транзакцию вместо подключения нельзя. Роли должны быть заранее созданы; установщик не создаёт и не печатает пароли.

До выдачи прав проверяются роли, членство, опасные прямые и default-права, запись в schema, 18 исходных финансовых функций, точный набор денежных триггеров и типы обязательных таблиц. Неподходящая схема отклоняется. Новая схема, функция и выдача прав выполняются одной транзакцией. Повтор не переписывает существующую границу молча.

**Это не доказательство, что текущие Web/API уже работают с такими credentials.** Внешнее развёртывание, отдельные секреты каждого процесса и вся совместимость ролей приложения проходят отдельную приёмку. Режим worker в текущем запуске остаётся `disabled`/`observe`, без автоматического переключения на начисление.

## Внутренний клиент

`@aiag/database/ton-reconciliation-internal` предоставляет `createTonSettlementWorkerDatabase` и `settleTonInvoiceAsWorker`. Отдельный URL обязан содержать именно выбранного worker; параметры запроса, меняющие соединение, отклоняются. В каждой транзакции проверяются фактический логин, текущая роль, отсутствие административных полномочий, NOLOGIN-владелец и установленная функция. Ошибка не вызывает fallback на прежний привилегированный клиент.

Это серверный интерфейс доверенного verifier/reconciler. Его нельзя публиковать как Web endpoint, принимающий «verified» JSON от покупателя. Проверка native PostgreSQL использует синтетические chain evidence; настоящая финальность блокчейна в этой волне не проверялась.

## Настоящий dump/restore

`packages/database/scripts/ton-worker-restore.ts` создаёт custom-архив через `pg_dump`, затем восстанавливает его через `pg_restore --single-transaction --exit-on-error` в новую случайную локальную БД. Параметры, снимающие владельцев или ACL, не используются. Копия сравнивается с исходной по количеству записей во всех таблицах рассматриваемых схем, владельцам/правам/функциям и точному финансовому снимку TON.

Восстановленная копия должна вернуть ту же квитанцию по уже завершённой операции, а ожидающий платёж — завершить один раз. Платёж в исходной БД остаётся ожидающим, его баланс не меняется. Web/API сохраняют запрет на финансовую функцию и прямую запись после восстановления.

Очистка использует ограниченные ожидания: неуспешное graceful close уничтожает только принадлежащий клиенту socket и остаётся отмеченным как неопределённое завершение. Ошибка одного этапа не пропускает остальные. Для потерянного подтверждения CREATE выполняется проверка уникального имени, владельца и известного OID через отдельное соединение. Подтверждённый PostgreSQL `duplicate_database` не считается неизвестным успехом: чужая одноимённая БД не удаляется. Смена идентичности или недоступность очистки — `TON_RESTORE_CLEANUP_UNCONFIRMED`, не успешный отчёт.

Репетиция выполняется в одном контролируемом тестовом кластере. Глобальные роли заранее существуют в нём; dump одной БД не является резервной копией ролей другого сервера. Off-host storage, шифрование/ротация резервных копий, RPO/RTO и независимое восстановление всего production-кластера здесь не аттестованы.

## Повторить локальную проверку

Из корня актуального Aggregator worktree после установки закреплённых зависимостей и локальных PostgreSQL18-инструментов:

```bash
scripts/with-native-test-services.sh bash -c '
  bun run db:test:bootstrap &&
  RUN_NATIVE_DB_INTEGRATION=1 bun run test:unit --no-file-parallelism \
    packages/database/scripts/__tests__/ton-worker-boundary.native.integration.test.ts \
    packages/database/scripts/__tests__/ton-worker-boundary-safety.native.integration.test.ts \
    packages/database/scripts/__tests__/ton-worker-restore.native.integration.test.ts
'
```

Helper сам владеет `flock /tmp/ai-ecosystem-build.lock`, временными PG/Redis и их очисткой. Не оборачивать его тем же внешним flock. Тесты создают случайные роли, только собственную дочернюю БД и синтетические данные; не заменять URL на production.

## До реального включения

Нужно определить и проверить credentials процессов в настоящем окружении, доступ к базе и права всех совместимых Web/API операций; пройти wallet/link/checkout, подтверждённый внешний testnet-сценарий и отдельное решение о запуске. Наличие нового worker-клиента и успешного восстановления не включает их автоматически. Проверочный `ton-privilege-preflight` остаётся диагностическим и не выдаёт разрешение на production.

Первоисточники PostgreSQL18: CREATE FUNCTION / Writing SECURITY DEFINER Functions Safely; pg_dump; pg_restore. Исходники: https://www.postgresql.org/docs/18/sql-createfunction.html , https://www.postgresql.org/docs/18/app-pgdump.html , https://www.postgresql.org/docs/18/app-pgrestore.html .
