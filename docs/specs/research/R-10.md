# R-10 — Telegram delivery + TMA hardening

**Item:** Agent delivery through the end-user's OWN Telegram bot (grammY, Bot API + Telegram Business, OFFICIAL only) + native WebApp via the telegram-apps SDK + hardening `initData` verification (R1-3).
**Date:** 2026-06-03
**Repo paths cited are relative to** `C:\Users\боб\projects\aggregator`.

---

## Summary

Three distinct things are bundled in this item; they need separate verdicts.

1. **Delivery via the end-user's OWN bot.** Today the worker pings users from a *single AIAG product bot* using a hand-rolled `fetch` to `api.telegram.org/bot{TG_BOT_TOKEN}/sendMessage` (`apps/agent-worker/src/bot-api.ts`). There is **no grammY**, no per-user bot token, and no Telegram Business support anywhere in the live tree (only the AIAG alert bot in `packages/telegram-alerts`). Moving to "agent replies in the user's own Telegram, in their own chats" is a real architecture change. The clean, official, no-ban-risk way to do it is **Telegram Business mode** (Bot API 7.2+, the user connects *our* bot under Settings → Telegram Business → Chatbots and we act on their behalf with `business_connection_id`) — and grammY has first-class support for it. The alternative ("user pastes their own bot token, we run a bot instance per user") is also pure Bot API and ban-safe, but operationally heavier and is a *different product* (their bot, their @username) than Business mode (their personal account, secretary-style).

2. **telegram-apps SDK.** The TMA currently reads `window.Telegram.WebApp.*` raw (`useAuth.ts`, `providers.tsx`) with no theme/haptics/viewport integration. Adopting `@telegram-apps/sdk` v3 is a low-risk, high-polish upgrade (theme sync, haptics, viewport CSS vars), and its sibling server package `@telegram-apps/init-data-node` is the recommended fix vehicle for the hardening item below.

3. **initData hardening (R1-3).** The current `verifyInitData` (`apps/tg-miniapp/src/lib/verify-init-data.ts`) has **two concrete defects**: (a) the HMAC equality test uses a plain JS `!==` string compare (`computedHash !== hash`), which is **not constant-time** (timing-oracle on the hash), and (b) the freshness window is **86 400 s (24 h)** — far too wide for a replay window and only an upper bound, with no nonce/replay protection. The fix is small and self-contained: swap the equality to `crypto.timingSafeEqual` over equal-length buffers and tighten the freshness window, ideally by delegating to the maintained `@telegram-apps/init-data-node` `validate(initData, token, { expiresIn })` which does both correctly. This is the one part of R-10 that is a true bug fix and should ship first.

**Bottom line recommendation:** (A) Ship the **initData hardening now** (constant-time compare + short `expiresIn`, via `@telegram-apps/init-data-node`). (B) Adopt **`@telegram-apps/sdk` v3** for the WebApp shell as a polish pass. (C) Build the OWN-bot delivery on **grammY in Telegram Business mode**, run as a separate long-poll/webhook process (NOT inside the Next.js TMA edge/runtime), reusing the existing `agent-run` BullMQ pipeline — but treat it as the next phase, gated behind the money-path being solid.

## Key findings with sources

### A. Current code reality (grounded in the repo)

- **Delivery is single-bot Bot API, hand-rolled.** `apps/agent-worker/src/bot-api.ts` builds `BASE = https://api.telegram.org/bot${TG_BOT_TOKEN}` and POSTs `sendMessage`. The chat target is **the user's own `telegram_id`** passed as `chat_id` (`runAgent` calls `sendBotMessage(agent.tg_user_id, …)` in `apps/agent-worker/src/agent-runner.ts`, e.g. `notifyCompleted`/`notifyFailed`). So today "delivery" = the AIAG bot DMs the user a "run finished" card with a deep-link back into the Mini App. It is **not** "the agent operates inside the user's own bot / business account."
- **No grammY, no Business, no MTProto.** Grep for `grammy|telegraf|business_connection|bot.api` across the live tree returns only: `apps/agent-worker/src/bot-api.ts` (raw fetch), `packages/telegram-alerts/src/bot.ts` (raw fetch alert bot), and docs/planning files. There is no bot framework dependency at all. This is a greenfield decision — good, because it means we pick the right one once.
- **The completion card still says ₽.** `buildRunCompletedMessage` formats `Стоимость: <b>${costRub.toFixed(2)} ₽</b>`. Per `apps/tg-miniapp/CLAUDE.md`, TMA currency must be crypto credits, not rubles — so the delivery message copy is part of the pending ₽→credit migration and should be fixed in the same pass that touches delivery.
- **Auth flow.** `useAuth.ts` (client) reads `window.Telegram.WebApp.initData`, POSTs it to `/tg/api/tma/auth/verify`, gets an HS256 JWT, caches it in Telegram `CloudStorage`. `app/api/tma/auth/verify/route.ts` calls `verifyInitData` then mints a 24 h JWT (`iss=aiag-tma`, `aud=aiag-gateway`, `jti`). `middleware.ts` verifies that JWT (alg pinned HS256, CVE-2025-29927 header strip — already hardened in R0). **initData itself is the weak link** and is only checked at the `auth/verify` boundary.

### B. initData validation — the authoritative algorithm and the two defects (R1-3)

Telegram's official spec (https://core.telegram.org/bots/webapps, "Validating data received via the Mini App"):
- `secret_key = HMAC_SHA256(<bot_token>, "WebAppData")`, then compare `hex(HMAC_SHA256(data_check_string, secret_key))` to `hash`. `data_check_string` = all fields except `hash`/`signature`, sorted alphabetically, joined by `\n`. **The repo's `verify-init-data.ts` implements this correctly** (lines 26–34).
- Telegram also now documents an **Ed25519 public-key method** (third-party validation without the bot token): data-check-string is prefixed `"<bot_id>:WebAppData\n…"`, and you verify the base64url `signature` field against Telegram's published public keys. Not needed for us (we hold the bot token), but relevant if we ever let *third parties* validate.
- **Freshness:** the spec explicitly says "To prevent the use of outdated data, you can additionally check the `auth_date` field."

**Defect 1 — non-constant-time compare.** Line 34: `if (computedHash !== hash) return …`. JS `!==` on strings short-circuits at the first differing byte → a timing side-channel on a 64-hex-char digest. Fix: compare with `crypto.timingSafeEqual(Buffer.from(computedHash,'hex'), Buffer.from(hash,'hex'))` after a length check (timingSafeEqual throws on length mismatch). The repo already imports `node:crypto`, and `crypto.timingSafeEqual` is used elsewhere in the codebase (`apps/web/src/lib/admin/session.ts`), so this is consistent with house style.

**Defect 2 — 24 h replay window, no replay defense.** Line 39: `if (ageSec > 86400)`. A captured `initData` string is **replayable for a full day**. The community-standard maintained server package `@telegram-apps/init-data-node` defaults `expiresIn` to **86 400 s (1 day)** too, but the docs recommend tightening it ("We consider init data sign valid for 1 hour", `expiresIn: 3600`) and warn: *"It is recommended to always check the expiration of the initialization data, as it could be stolen but still remain valid"* (https://docs.telegram-mini-apps.com/packages/tma-js-init-data-node/validating). Because we mint a 24 h JWT immediately on first verify and the client caches it in CloudStorage, we **do not need** a 24 h initData window — initData is used once, at login. Tighten to **~300–900 s** (5–15 min) to bound replay, and optionally add a one-shot nonce (store the `hash`/`auth_date` pair in Redis with a short TTL and reject re-use) for true replay protection.

**Recommended fix vehicle.** Rather than maintaining our own HMAC code, delegate to `@telegram-apps/init-data-node` (`validate(initData, token, { expiresIn: 600 })`) which: does the HMAC correctly, uses Node's timing-safe primitives internally, throws on signature/expiry, and offers `isValid()` (boolean, no throw) and `validate3rd()` (the Ed25519 path) and `signData()` (server-side signing, useful for tests). Current major version is **v2.x** (npm `@telegram-apps/init-data-node`). Keeping our own file is also acceptable if we just apply the two fixes — the dependency is the lower-maintenance option.
Sources: https://docs.telegram-mini-apps.com/packages/tma-js-init-data-node/validating ; https://docs.telegram-mini-apps.com/platform/init-data ; https://www.npmjs.com/package/@telegram-apps/init-data-node .

### C. grammY + Telegram Business — the OWN-bot delivery path

- **Bot API 7.2 (2024-03-31)** introduced Telegram Business: `BusinessConnection`, `getBusinessConnection`, `business_message`/`edited_business_message` updates, and the **`business_connection_id` parameter on `sendMessage`/`sendPhoto`/… so the bot acts on behalf of the connected user**. Latest Bot API is **10.0 (2026-05-08)**. Source: https://core.telegram.org/bots/api-changelog .
- **grammY ships Business support built-in.** `bot.on("business_message", ctx => …)`; `ctx.businessMessage`/`ctx.msg`; `const conn = await ctx.getBusinessConnection()` then `conn.user` is the business-account owner; differentiate owner vs customer via `ctx.from.id === conn.user.id`; gate replies on `conn.rights?.can_reply`; `ctx.reply()` and variants automatically attach `ctx.businessConnectionId` so the message is sent **as the owner** (Telegram shows a small "via bot" indicator). Source: https://grammy.dev/advanced/business .
- **Hard prerequisite & UX:** the end-user must add our bot under **Settings → Telegram Business → Chatbots** (Telegram Premium feature) before any `business_connection` arrives. This is a one-time user action we cannot automate; it must be in onboarding copy. Source: https://grammy.dev/advanced/business .
- **OFFICIAL, no MTProto, no ban risk — confirmed.** grammY is a pure Bot API framework; updates come via the two official, mutually-exclusive mechanisms (`getUpdates` long-poll OR webhook; calling `getUpdates` while a webhook is set returns HTTP 409). No userbot/MTProto, so no ToS/ban exposure. Rate limit to respect: bulk sends are capped ~30 msg/s globally (429 above that). Sources: https://core.telegram.org/bots/api ; https://core.telegram.org/bots/faq .
- **GramIO/Telegram.Bot confirm the same Business surface** (cross-framework sanity check): `BusinessConnection`, `business_connection_id`, `can_reply`. Sources: https://gramio.dev/telegram/types/businessconnection ; https://telegrambots.github.io/book/4/business.html ; https://core.telegram.org/api/bots/connected-business-bots .

- Package `@telegram-apps/sdk`, latest **3.11.8** (npm). v3 is a component model: `init()` for initial config (fullscreen, swipe-to-close behavior), `themeParams` to sync background/text/accent to the user's Telegram theme, `viewport`/`initViewport` which exposes `--tg-viewport-height` / `--tg-viewport-width` / `--tg-viewport-stable-height` CSS vars, and `hapticFeedback` (light/medium impacts for buttons/toggles — "premium feel"). ## Concrete recommendation

### 1. initData hardening (R1-3) — ship FIRST, smallest, highest security value

Option chosen: **adopt `@telegram-apps/init-data-node`** in `app/api/tma/auth/verify/route.ts`, keeping the route's JWT minting unchanged.

```ts
import { validate } from '@telegram-apps/init-data-node';
// ...
try {
  validate(initData, botToken, { expiresIn: 600 }); // 10-min replay window
} catch (e) {
  return NextResponse.json({ error: 'invalid_init_data', reason: String(e?.code ?? 'invalid') }, { status: 401 });
}
// parse user from initData (parse() from the same pkg) → mint JWT as today
```

If we prefer **zero new dependency**, apply the two fixes in `verify-init-data.ts` directly:
- Replace line 34 with a length-checked `crypto.timingSafeEqual`:
  ```ts
  const a = Buffer.from(computedHash, 'hex');
  const b = Buffer.from(hash, 'hex');
  if (a.length !== b.length || !crypto.timingSafeEqual(a, b)) return { ok:false, reason:'hash_mismatch' };
  ```
- Change line 39 `86400` → a config (`TMA_INITDATA_MAX_AGE_SEC`, default `600`).
- (Optional, true replay defense) record `hash` in Redis `SET key 1 NX EX 600`; reject if the key already exists.

Both options are runtime-safe: `auth/verify` already declares `runtime = 'nodejs'`, so `node:crypto` / `Buffer` are available. Do **not** move this check into Edge middleware.

### 2. WebApp shell — adopt `@telegram-apps/sdk` v3 (polish phase)

Add `init()`, `themeParams` binding (drive CSS vars / Tailwind theme), `viewport` CSS vars for the bottom-nav safe area, and `hapticFeedback` on primary actions (run agent, top-up). Replace the raw `window.Telegram.WebApp.initData` read in `useAuth.ts` with the SDK's retrieveLaunchParams/initData accessor. Mind `basePath /tg` (per `apps/tg-miniapp/CLAUDE.md`) and keep `TonConnectUIProvider` inside the `'use client'` boundary (existing `providers.tsx` constraint).

### 3. OWN-bot delivery — grammY in Telegram Business mode (next phase)

Architecture:
- **New long-running process** `apps/tg-bot` (grammY), run under pm2 alongside `tma`/`agent-worker` — NOT inside Next.js. Use **webhook** mode behind the existing nginx (one path, secret-token header) or long-poll on the 2 GB VPS; webhook is lighter on a single small box.
- **Connection capture:** `bot.on('business_connection')` → persist `business_connection_id`, owner `user.id`, and `rights.can_reply` to a `tg_business_connections` table keyed by `telegram_id`. Onboarding UI must instruct the user to add the bot under Settings → Telegram Business → Chatbots.
- **Inbound:** `bot.on('business_message')` for customer messages the agent should answer → enqueue onto the **existing `agent-run` BullMQ queue** (same pipeline the Mini App uses in `app/api/tma/agents/[id]/run/route.ts`), tagging the job with `businessConnectionId` + source.
- **Outbound (delivery):** the worker's terminal step (`notifyCompleted` in `agent-runner.ts`) gains a delivery target. When the run originated from a business chat, send via grammY with `business_connection_id` so the answer appears **as the user's own account**; when it originated from the Mini App, keep the current "via AIAG bot DM + deep-link" card. Centralize this behind a small `deliver()` seam so the worker doesn't hard-code transport.
- **Money path stays authoritative:** the same `settleRun` atomic debit applies regardless of delivery channel; do not let a delivery failure roll back billing or vice-versa (deliver AFTER settle, fire-and-forget with retry, exactly as the current `sendBotMessage` is best-effort).
- **Copy fix:** while here, change `buildRunCompletedMessage` off ₽ to crypto credits (pending unit migration).

Sequencing rationale: (1) is a security bug → now. (2) is cheap polish → soon. (3) is a feature that multiplies the money path's blast radius → only after the gateway-registry `DEFAULT_MODEL` bug and balance flow are solid (see `apps/agent-worker/CLAUDE.md`).

## Risks

- **Telegram Business requires Premium + manual setup.** Only Premium users can connect chatbots, and they must do it by hand in Settings. This narrows the audience and adds an onboarding failure mode; if most users aren't Premium, the "user pastes their own bot token" model (separate bot per user) may reach more people — but that's a different product surface and more ops. Decide which OWN-bot story we actually want before building.
- **`business_connection_id` lifecycle.** Connections can be revoked or have `can_reply=false`; sending to a stale/insufficient connection errors. Must persist + refresh `rights` on every `business_connection` update and gate sends on `can_reply`.
- **Tightening `expiresIn` too far breaks slow logins.** A 5-min window can reject users on poor mobile networks who background the app. 10 min (600 s) is the safer default; make it env-configurable. (Note: the user-facing JWT is still 24 h — only the *initData login* window tightens.)
- **Adding a dependency vs. hand-rolled.** `@telegram-apps/init-data-node` reduces our crypto-maintenance burden but adds supply-chain surface; either path fixes R1-3, so this is a team preference, not a correctness question.
- **Process count on a 2 GB VPS.** A new grammY process is small, but webhook mode + nginx routing + Redis sharing must be sized; long-poll is simplest but holds an open connection. Verify on prod (no local runtime — per project memory).
- **Rate limits.** ~30 msg/s global cap; business broadcasts and bursty agent replies must be throttled to avoid 429s.

## Open questions

1. **Which OWN-bot model is the product?** Telegram Business "secretary on the user's personal account" (Premium-gated, our single bot) vs. "user brings their own @bot token, we host an instance" (broader reach, heavier ops). R-10's brief says Business — confirm that's the intended UX and that Premium-gating is acceptable.
2. **Replay window number.** Is 600 s acceptable product-wide, or do we want a one-shot nonce in Redis for hard replay protection (worth it given we already run Redis for BullMQ)?
3. **Dependency policy:** adopt `@telegram-apps/init-data-node` + `@telegram-apps/sdk`, or keep hand-rolled and just patch `verify-init-data.ts`? (Recommend adopt — same maintainers, less crypto to own.)
4. **Inbound business messages = billable runs?** If a customer messages the user's business chat and our agent answers, whose balance is debited and at what markup? This must be answered before wiring `business_message` → `agent-run`, because it changes who pays.
5. **Webhook vs long-poll** for the grammY process on the single VPS, given nginx already fronts `/tg` and strips spoofable headers.

## Adversarial review

**Verdict: PARTLY holds up.** The repo diagnosis is accurate, the Business/grammY architecture is sound, and most external facts check out. But the single most important security claim — the one that drives the headline "adopt the dependency" recommendation for the highest-value item (R1-3) — is **factually wrong**, and as written the chosen fix would leave Defect 1 unfixed.

### Critical issue — the recommended fix does NOT fix Defect 1 (verified against package source)

R-10 (line 43) asserts `@telegram-apps/init-data-node` "uses Node's timing-safe primitives internally," and §1 picks "**adopt `@telegram-apps/init-data-node`**" as the chosen option, with the manual `crypto.timingSafeEqual` patch demoted to a "if we prefer zero new dependency" fallback. I downloaded and read the actual published package (`@telegram-apps/init-data-node@2.0.10`, latest on npm, the version R-10 targets). Its hash comparison is:

```js
function processSign(actual, expected) {
  if (actual !== expected) {            // <-- plain JS !== — NOT constant-time
    throw new SignatureInvalidError();
  }
}
```

This is the **identical non-constant-time `!==` string compare** that R-10 correctly flags as Defect 1 in our own `verify-init-data.ts:34`. The package does real HMAC via `node:crypto.createHmac`, and it does fix Defect 2 (expiry — `expiresIn` defaults to `86400` seconds, configurable), but it does **not** use `timingSafeEqual` anywhere (0 occurrences in the shipped CJS/ESM). Therefore:

- Adopting the dependency as recommended fixes Defect 2 but **leaves Defect 1 (the timing oracle) exactly as it is today.** The recommendation's own rationale ("does the HMAC correctly, uses Node's timing-safe primitives internally") is false on the second clause.
- The demoted "fallback" — the manual `crypto.timingSafeEqual` patch in R-10 §1 — is in fact the **only** option presented that actually fixes Defect 1. The ranking is backwards for the security goal.
- And the timing oracle is not theoretical: published research distinguishes ~20µs remote timing deltas with ~1000 samples over the internet, and HMAC-compare timing leaks have been exploited in real APIs (Keyczar 2009, OAuth/OpenID impls). So Defect 1 is a genuine, not academic, gap.

**This does not mean "don't use the package"** — its `parse()`, `expiresIn`, error types, and the Ed25519 `validate3rd()` path are all real and useful. It means: **do not rely on the package for constant-time comparison.** Either keep the comparison ours (manual `timingSafeEqual` patch — simplest, fully fixes both defects, zero supply-chain add) or use the package for parse/expiry but still re-verify the hash ourselves with `timingSafeEqual`. As written, R-10 §1's primary path is a correctness regression against its own stated threat.

### Facts that DO hold up (independently verified)

Public node-entry signature is `validate(value, token, options): void` — so R-10's `validate(initData, token, { expiresIn: 600 })` example is valid usage. `expiresIn` is in **seconds**, default `86400`, `0` disables. Exports `isValid`, `validate3rd`/`isValid3rd`, `signData`, `parse` as claimed.
- `@telegram-apps/sdk` latest = **3.11.8** (exact match to R-10).
- Bot API **7.2 = 2024-03-31** introduced Telegram Business (`BusinessConnection`, `business_message`, `business_connection_id`); grammY has first-class Business support; OFFICIAL Bot-API-only path, no MTProto/ban risk; ~30 msg/s global send cap; `getUpdates` vs webhook mutually exclusive (409 on conflict). All correct.

### Secondary issues / missing risks

- **Severity inversion.** R-10 frames R1-3 as the highest-value security ship, but in our threat model the JWT is minted once at login and the initData window is single-use. The *replay window* (Defect 2) is the more impactful of the two for us (a stolen 24h-valid initData is directly replayable), while the timing oracle (Defect 1) requires thousands of high-resolution samples against a login endpoint. Both should be fixed, but the easy, complete fix is the **manual two-line patch**, not the dependency — which inverts R-10's recommended ordering. Net: ship the manual `timingSafeEqual` + short `expiresIn` patch; treat the package as optional convenience, not the security mechanism.
- **Replay protection still absent in both options.** Neither the manual patch nor the package provides nonce/one-shot replay defense; tightening `expiresIn` only *bounds* the replay window, it does not close it. R-10 mentions the Redis-nonce option but leaves it "optional." Given Redis is already running for BullMQ and initData is used exactly once, a one-shot `SET hash 1 NX EX <ttl>` is cheap and is the only thing that actually stops replay inside the window — recommend promoting it from optional to default for the login path.
- **Inbound-billing open question is a blocker, not a footnote.** Open question #4 (who pays when a customer messages the user's business chat and our agent answers) is correctly raised, but it is a hard gate: wiring `business_message` → `agent-run` without a settled answer risks debiting the wrong party or running unbilled agent work at our cost. This should be elevated from "open question" to an explicit precondition on phase 3.
- **Premium-gating reach is under-quantified.** R-10 flags that Business requires the end-user to have Telegram Premium and to manually add the bot, but does not estimate what fraction of the audience that excludes. This materially affects whether phase 3 is worth building at all vs. the "bring-your-own-bot-token" alternative; it deserves a number (even a rough one) before committing engineering.
- **`business_connection_id` must be passed explicitly on delivery sends.** R-10 says `ctx.reply()` auto-attaches the connection id — true for *replies in an update handler*, but the **outbound delivery** path (worker `notifyCompleted` firing later, outside any `ctx`) must call `bot.api.sendMessage(chatId, text, { business_connection_id })` explicitly. R-10's §3 outbound bullet is slightly optimistic about this being automatic; the worker has no `ctx`.

### Tightened recommendation

1. **R1-3, ship first — but flip the chosen option.** Apply the **manual patch** in `verify-init-data.ts` as the primary fix: length-checked `crypto.timingSafeEqual` (fixes Defect 1 — the package does NOT) + `expiresIn`/`TMA_INITDATA_MAX_AGE_SEC` default 600s (fixes Defect 2). Add the Redis one-shot nonce (`SET hash 1 NX EX 600`) as part of this ship, not "optional," since it is the only true replay defense and Redis is already present. Use `@telegram-apps/init-data-node` only if you want its `parse()`/error types — and if you do, still re-verify the hash with `timingSafeEqual` rather than trusting `validate()`'s `!==`.
2. **`@telegram-apps/sdk` v3 (3.11.8) — unchanged.** Low-risk polish; proceed as written, respecting basePath `/tg` and the `'use client'` boundary.
3. **grammY Business delivery — unchanged architecture, two gates added.** Build it (separate pm2 process, reuse BullMQ, deliver-after-settle). But (a) make the inbound-billing decision (open Q#4) a hard precondition, not an open question, and (b) quantify Premium-gated reach before committing. In the outbound worker path, pass `business_connection_id` explicitly — there is no `ctx` to auto-attach it.
