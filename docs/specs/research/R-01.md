# R-01 — Managed-Hermes runtime infra

**Question:** What infrastructure should run a per-user managed Hermes agent (~300-600 MB idle, up to ~1 GB active, browser off) at scale? Compare on-demand sandbox clouds (Daytona, Modal, E2B, Fly Machines) vs k3s pods + hibernation (kube-green). Decide cost/idle/active, cold-start, isolation (fs, network, secrets), density, and ops complexity. Recommend a concrete path and a phased rollout. Current VPS is 2 GB and full.

---

## Summary (TL;DR)

**Recommend Daytona on-demand sandboxes as the managed-Hermes runtime, because Hermes v0.15 ships a first-class `daytona` backend with stop/resume hibernation built in — zero glue code, idle cost ≈ disk-only (~$0.4-0.8/agent/mo), active cost ≈ $0.07-0.13/agent/hr, and per-sandbox filesystem/network/secrets isolation that structurally prevents one agent from reading `/srv/aiag/shared/.env` or another agent's data.** Keep **Modal as the documented fallback** (also a built-in Hermes backend, gVisor isolation, sub-second memory-snapshot restore). **Reject kube-green** for this use case: it is a *time-schedule* sleeper (sleep 20:00 / wake 08:00 by CRD), not a per-request on-demand waker — it cannot wake one user's agent on an inbound Telegram message, which is the core requirement. Self-hosted k3s on a bigger VPS is viable only for a closed beta (≤10-30 agents) where the RF legal entity must hold the compute; it carries the highest ops burden and the weakest secrets isolation.

The decisive fact: **the agents almost always idle.** A Hermes agent runs for seconds-to-minutes per task, then sleeps for hours. Paying for an always-on process per user is wrong by 1-2 orders of magnitude. The whole comparison reduces to "which option makes idle nearly free *and* wakes fast on demand *and* isolates secrets." Daytona wins on all three with the least engineering.

## Key findings

### F1. Hermes already integrates Daytona and Modal natively — this is the single biggest decision driver

Hermes v0.15 supports **seven terminal/execution backends: local, Docker, SSH, Singularity, Modal, Daytona, and (newest) Vercel Sandbox.** Daytona and Modal are documented as giving "serverless persistence — your agent's environment hibernates when idle and wakes on demand, costing nearly nothing between sessions." Config is a few YAML lines plus one env var (`DAYTONA_API_KEY`, or `MODAL_TOKEN_ID`/`MODAL_TOKEN_SECRET`).

```yaml
terminal:
  backend: daytona
  container_cpu: 1
  container_memory: 5120     # MB  (Hermes default ~5 GiB)
  container_disk: 10240      # MB  (max 10 GiB on Daytona)
  container_persistent: true # stop/resume instead of delete
```
Sandbox names follow `hermes-{task_id}`; with `container_persistent: true` Daytona **stops (not deletes)** on cleanup and **resumes** next session. Modal equivalent snapshots the filesystem across sessions (`~/.hermes/modal_snapshots.json`).

**Implication:** the "huge build" the explainer feared — "learn to spin up/down a Hermes instance per agent (in a sandbox, on demand)" — is **largely already solved by Hermes itself.** We do not write a provisioner; we set a backend in config and supply an API key. This collapses the highest-risk unknown.

- Source: NousResearch/hermes-agent README + `website/docs/user-guide/configuration.md` (https://github.com/NousResearch/hermes-agent , https://hermes-agent.nousresearch.com/docs/user-guide/configuration)

> ⚠️ **Caveat to verify on the pinned build.** Hermes' Modal/Daytona setting is documented as the *terminal* (shell-command execution) backend. The README also states "the entire agent runs in the cloud sandbox … the environment persists between invocations." These two framings should be reconciled on the actually-installed v0.15.2: confirm whether (a) the whole `hermes gateway` loop hibernates in the sandbox, or (b) only tool/shell execution runs remotely while a thin gateway stays resident locally. Our architecture differs materially between (a) and (b) — see Open Questions Q1. Either way the sandbox-cloud path is the right substrate; the only question is what stays resident on our side.

### F2. kube-green is the wrong tool — it is a clock, not a doorbell

kube-green is a Kubernetes operator with a `SleepInfo` CRD: you declare *what time and days* to set Deployment replicas to 0 ("sleep") and restore them ("wake"). Canonical example: sleep a namespace at 20:00, wake at 08:00 weekdays. It also suspends CronJobs. It is built for **dev/test environment cost-saving on a schedule and holiday/nightly shutdowns** — not for "wake user #4172's agent because a Telegram message just arrived."

For a marketplace of personified agents, demand is per-user and unpredictable; you need **scale-to-zero with request-driven wake** (a doorbell), which kube-green does not provide. To get request-driven wake on k8s you would bolt on KEDA HTTP-add-on / Knative serving + a router — i.e. you rebuild what the sandbox clouds give for free, on a cluster you also have to run.

- Sources: kube-green.dev/docs/configuration; Qovery "environment sleeping"; rossfairbanks.com kube-green writeup (see Sources).
- **Verdict:** kube-green is disqualified for on-demand per-agent wake. (k3s itself, separately, is discussed in F7 as a self-host option — but using *plain pods you stop/start via the API*, not kube-green.)

### F3. Cost model (browser OFF; per agent; 2026 list prices)

Two profiles modeled: **Trim** (1 vCPU, 1 GiB billed RAM, ~300-600 MB real idle) and **Hermes-default** (1 vCPU, 5 GiB RAM as the config ships). Active = while a task runs; agents idle the vast majority of the time.

**Per-agent monthly all-in (Daytona, Trim, realistic light usage):** assume 30 active minutes/day = 15 active-hr/mo × $0.0666 = **$1.00 compute** + ~$0.4-0.8 disk = **≈ $1.4-1.8/agent/mo.** Heavier (2 active-hr/day = 60 hr/mo) ≈ $4/agent/mo. The explainer's "~$0.30/mo light agent" assumed very low active time (a few minutes/day, ~5 active-hr/mo → ~$0.33 + disk); that holds for truly bursty agents but **budget $1-2/agent/mo as the planning figure.** Inference tokens are billed separately upstream (OpenRouter/our gateway) and are not part of this.

> Modal's sandbox 3× CPU multiplier and US non-preemptible premium make it **~2-2.5× Daytona/E2B on raw compute**; E2B's flat **$150/mo Pro base fee** makes it uneconomic until you have hundreds of agents to amortize it. Daytona is the cost leader for our scale.

### F4. Cold-start is a non-issue for all four clouds; it disqualifies nothing

Telegram interactions tolerate 1-3 s latency easily. Daytona stopped-resume and Fly start-on-request are fast; Modal memory-snapshots restore sub-second-to-~1 s; E2B creates at 78 ms p50. The only cold-start cliff is Daytona **archived** state (after 7 days idle, restore is size-dependent and slower) — acceptable for a dormant agent's first message after a week; keep frequently-used agents in *stopped* (not archived) state, or pre-warm on a cheap signal (user opens the TMA).

### F5. Secrets isolation — the hard requirement — is satisfied structurally by every sandbox cloud and is the strongest argument against self-host

The brief's non-negotiable: *one agent must not read another agent or `/srv/aiag/shared/.env`.* Hermes' own docs warn its agent profiles are **not fs-isolated** within one host — so co-locating user agents with our secrets on one box is unacceptable.

- **Daytona / E2B / Fly**: each agent = its own sandbox/microVM with its own filesystem and network namespace. Our `/srv/aiag/shared/.env` lives on a **different machine** (our VPS); a user's sandbox has no path to it and no shared kernel mount. E2B and Fly use **Firecracker microVMs** (hardware-level, separate kernel — hardest escape boundary). Daytona uses isolated managed containers.
- **Modal**: **gVisor** — a user-space kernel intercepting syscalls; strong isolation, softer than a microVM but explicitly marketed for "untrusted/agent-generated code."
- **Per-agent secrets**: inject only that agent's own provider key into its sandbox env at start; never mount the shared `.env`. This is the natural model on all four.

By contrast, **self-host (F7) is where secrets isolation gets dangerous**: if user agents run on the same box as our gateway/worker and `/srv/aiag/shared/.env`, a Hermes profile (not fs-isolated) or an agent-written skill can read host secrets. Self-host therefore *mandates* per-agent Docker/gVisor/Kata sandboxing that you build and maintain yourself — re-implementing what the clouds give for free.

### F6. Density (self-host ceilings, browser OFF) — from the explainer's own triangulation

Per-agent RAM ≈ 300 MB idle, up to ~1 GB active (browser off; browser on = 1-2 GB, ÷3-4 the counts). On a self-hosted box: **2 GB ≈ 0-2 agents (current VPS, already full), 8 GB ≈ 10-12, 16 GB ≈ 25-30.** These are hard physical ceilings and ignore the fact that idle agents still pin RAM unless stopped. On-demand clouds have **no per-node ceiling we manage** — density is the provider's problem; we pay per active second and per idle GiB of disk.

### F7. Self-hosted k3s + stop/start (NOT kube-green): viable only as a closed-beta stopgap

If the RF legal entity must hold the compute (the explainer flags a two-entity boundary; foreign $-billed clouds map to the foreign entity), the fallback is a bigger VPS (8-16 GB) running k3s or plain Docker, each agent a pod/container with `--cap-drop ALL`, `--pids-limit`, resource limits (Hermes' own Docker backend already does this hardening). To get "idle ≈ free" you stop/start containers via your own controller keyed on activity — **you build the doorbell yourself** (kube-green can't, F2). Ceiling ~10-30 agents (F6), highest ops complexity (cluster, autoscaling, your own sleep/wake controller, your own microVM/gVisor layer for true isolation), and the weakest secrets story (F5). Good enough to prove the end-to-end money path with a handful of agents; **not** the scale answer.

### F8. Operational complexity ranking (low → high)

1. **Daytona** (lowest) — Hermes-native backend, one API key, provider runs the substrate, isolation built in. We manage: API key, per-agent config, a stop/archive policy, billing reconciliation.
2. **Modal** — also Hermes-native; slightly more config (token id+secret, snapshot file); higher cost; gVisor.
3. **Fly Machines** — not a Hermes backend → we write the provisioner (create/stop/start machine, wire the proxy wake). More glue, but a mature platform.
4. **E2B** — Hermes-native-ish via Daytona-equal API but $150/mo floor; best isolation; over-engineered for our stage.
5. **Self-host k3s + custom stop/start** (highest) — we run and secure everything, including the isolation and the wake controller.

## Concrete recommendation

**Adopt Daytona as the managed-Hermes runtime. Configure Hermes' `daytona` backend with `container_persistent: true`, one `DAYTONA_API_KEY`, per-agent isolated sandboxes, auto-stop at 15 min, archive after a few days of inactivity. Keep Modal wired as the documented fallback. Never co-locate user agents with `/srv/aiag/shared/.env`.**

Why Daytona over the others, in one line each:
- **vs kube-green:** kube-green can't wake one agent on demand (it's a scheduler), Daytona does it natively (F2).
- **vs self-host k3s:** self-host caps at ~10-30 agents, carries the heaviest ops + the weakest secrets isolation, and re-implements the wake controller (F5-F7).
- **vs Modal:** ~2-2.5× cheaper at our scale and Daytona-native in Hermes; Modal stays as fallback (F3).
- **vs E2B:** E2B's $150/mo floor is uneconomic until hundreds of agents; revisit if we need Firecracker-grade isolation for genuinely hostile tenants (F3, F5).
- **vs Fly Machines:** Fly needs us to write the provisioner; Daytona needs zero glue (F8).

**Billing alignment (founder-flagged two-entity boundary):** Daytona/Modal are $-billed → they sit under the **foreign legal entity**, consistent with the explainer's split (RF entity = RUB rails; foreign entity = $/crypto compute). Plan the contracting accordingly before turning managed-Hermes on for real users.

### Phased rollout

- **Phase 0 — Prove the loop (1 agent, manual).** On a dev box (or our VPS, but with the sandbox backend so the agent body runs *in Daytona*, not on the VPS), stand up ONE real Hermes v0.15.2 with `backend: daytona`, pointed at our `:4000` gateway (so markup/white-label/billing fire), and run the end-to-end path: *create → Hermes wakes in Daytona → calls model via `:4000` → `settleRun` debits balance.* This is the explainer's #3 highest-risk unknown; verify it before anything else. Measure real idle RAM, active RAM, resume time, and a week's Daytona bill for one agent.
- **Phase 1 — Provisioner + lifecycle (closed beta, ≤20 agents).** Build the thin control plane: on agent-create, mint a Daytona sandbox config + inject only that agent's provider key; map TMA agent ⇄ sandbox id; expose status (sleep/working) per the explainer's redesigned agent card; enforce auto-stop/archive; reconcile Daytona spend into per-agent cost telemetry. Resolve Q1 (what stays resident on our side) here.
- **Phase 2 — Scale + cost controls (open beta).** Per-agent monthly compute budget caps (reuse the existing daily/monthly budget gate in `agent-runner.ts`), pre-warm on TMA-open, archive policy tuning, alerting on runaway sandboxes, and a Modal-fallback switch. Add the published-template install flow (separate item) so installing a template provisions a new isolated sandbox.
- **Phase 3 (optional) — Hostile-tenant hardening.** If/when untrusted public templates run arbitrary tools, evaluate moving to **E2B (Firecracker)** or Modal-gVisor for the hardest escape boundary, and add an egress guard inside the sandbox (mirrors the R1-7 SSRF `safeFetch` work already planned for the worker).
- **RF-only escape hatch (only if legal forces it):** an 8-16 GB RF VPS running Hermes' hardened **Docker** backend (not kube-green) with a homegrown stop/start controller, capped at ~20 agents for closed beta. Accept the ceiling and the ops cost; migrate to Daytona for scale.

## Risks

- **R1 — Terminal-backend vs whole-agent ambiguity (HIGH, gates the design).** If Daytona/Modal only sandboxes *shell execution* and the `hermes gateway` loop must stay resident, then per-user always-on gateway processes reappear on our side and the "idle ≈ free" economics partly collapse. Must be confirmed on v0.15.2 in Phase 0 (Q1). The README's "entire agent runs in the cloud" framing suggests we're fine, but the config doc calls it the *terminal* backend — reconcile empirically.
- **R2 — List-price drift.** All 2026 prices are list/marketing figures (Daytona $0.0504 vCPU-hr / $0.0162 GiB-hr; Modal sandbox 3× multiplier; E2B $150/mo floor; Fly $0.15/GB-mo rootfs). Re-quote before committing a budget; multipliers (Modal US non-preemptible 3.75×) bite hard.
- **R3 — Archived cold-start cliff.** Agents idle >7 days auto-archive on Daytona → slower first wake. Mitigate with stopped-not-archived for active users and pre-warm on TMA-open.
- **R4 — Vendor lock-in / availability.** Daytona is a young company; a hard dependency is a single point of failure. Mitigation is cheap because Hermes also speaks Modal and Fly/Vercel natively — keep one fallback wired and tested.
- **R5 — Legal/entity timing.** $-billed compute must sit under the foreign entity per the founder's two-entity split; turning managed-Hermes on for real users before that structure exists creates a compliance gap.
- **R6 — Per-agent cost runaway.** A looping or browser-heavy agent can rack up active-hours. Reuse the existing monthly/daily budget gates and add a hard sandbox-uptime cap + alert.
- **R7 — gVisor softness (Modal fallback).** If we ever fall back to Modal for untrusted public templates, note gVisor is a softer boundary than Firecracker; prefer E2B/Fly microVMs for hostile tenants (Phase 3).

## Open questions

- **Q1 (must answer in Phase 0):** On the pinned Hermes v0.15.2, when `backend: daytona`/`modal` is set, does the *entire* agent loop hibernate in the sandbox, or does a `hermes gateway` process stay resident locally with only tool execution remote? Determines whether we run any per-agent resident process and re-shapes the cost model and the VPS load.
- **Q2:** Exact Daytona resume latency for a *stopped* (non-archived) ~5 GiB sandbox, measured, not marketed — needed for the TMA "waking…" UX.
- **Q3:** Does routing each sandboxed Hermes at our `:4000` gateway over the public internet (sandbox → our VPS) need auth/mTLS and an allowlist? (Today the worker calls `127.0.0.1:4000`; a remote sandbox cannot.) This intersects the R1-7 egress/SSRF guard and gateway exposure.
- **Q4:** Real measured idle vs active RAM for a configured Hermes agent (browser off) — to right-size `container_memory` (5 GiB default may be wasteful; trimming to 1-2 GiB cuts the GiB-hr line materially).
- **Q5:** Does Daytona's RF-network reachability / data-residency posture create any RKN/latency issue from RU users, or is all traffic TMA→our VPS→Daytona (so the user never touches Daytona directly)?

## Adversarial review

**Holds up: PARTLY.** Platform selection (Daytona-first, Modal fallback, reject kube-green, self-host only as RF stopgap) is sound and survives scrutiny. The *economic case as written does not* — its headline "idle ≈ free" premise is falsified by Hermes' own architecture, and its isolation framing is overstated for the platform it actually picks.

### What I verified (independently sourced, 2026-06-03)

- **F1 — native Daytona/Modal backend: CONFIRMED.** Hermes ships `terminal.backend: daytona|modal` with `container_persistent`, file sync-back, and "serverless persistence." (Hermes config doc + DeepWiki Execution Environments.) The "we don't write a provisioner for *tool execution*" claim is real.
- **F2 — kube-green is a clock, not a doorbell: CONFIRMED, fully correct.** SleepInfo CRD is purely `sleepAt`/`wakeUpAt`/`weekdays`/cron, sets replicas to 0 on a schedule. No request-driven wake. Disqualification is correct.
- **F3 raw rates: CONFIRMED.** Daytona $0.0504 vCPU-hr / $0.0162 GiB-hr / $0.000108 GiB-disk-hr; Modal sandbox $0.00003942/core-s with 3× sandbox + up to 1.25–2.5× regional (≈3.75× US non-preempt) and $0.0242 GiB-hr; E2B $150/mo Pro floor, rates ≈ Daytona. All check out.

### Key issues (in severity order)

1. **R1 is not an open question — it is answerable now, and the answer breaks the headline economics. (CRITICAL.)** Both the Hermes config doc and the DeepWiki architecture page state plainly: the Daytona/Modal backend runs **only shell/tool command execution remotely; the main agent loop (`hermes gateway`) stays resident on the local host and "never hibernates or migrates remotely."** Sandboxes preserve *filesystem state, not live processes/PID space/background jobs.* The README's "your agent's *environment* hibernates" refers to the tool-execution environment, not the agent loop. Consequence: the per-user `hermes gateway` process (300–600 MB idle) **stays on our side and pins RAM** — exactly the "always-on process per user" the doc claimed Daytona eliminates. So "idle ≈ disk-only ≈ $0.4–0.8/agent/mo" and the "$0.30–$2/agent/mo" planning figure are **invalid as stated**: they price the dormant sandbox but omit the resident orchestrator. The doc had the evidence to resolve this before recommending and instead assumed the favorable branch ("README framing suggests we're fine"). It is not fine. Real cost = (resident-gateway hosting, which still hits the F6 RAM ceiling we were trying to escape) + (sandbox active compute) + disk.

2. **F5 isolation is overstated for the platform actually chosen. (HIGH.)** The TL;DR says Daytona "structurally prevents one agent reading another agent's data" and groups it with E2B/Fly. But Daytona **defaults to shared-kernel Docker containers**; hardware-isolated microVM/Kata is opt-in. The genuinely strong boundaries (Firecracker) belong to E2B and Fly — the two options the doc *rejected*. F5/R7 soften this to "isolated managed containers," but the decisive language oversells it. For multi-tenant user agents (and certainly Phase-3 hostile public templates), shared-kernel container escape is a real residual risk; "structurally prevents" is too strong. (Cross-machine isolation from `/srv/aiag/shared/.env` does hold — that part is correct, because the `.env` is on a different host.)

3. **Hermes default config exceeds Daytona defaults. (MEDIUM, feasibility.)** The shipped `container_memory: 5120` (5 GiB) and `container_disk: 10240` (10 GiB) sit at/above Daytona's default per-sandbox max (1 vCPU / **1 GB RAM** default; default ceilings ~4 vCPU / 8 GB / 10 GB, higher only via support). 5 GiB RAM needs a quota bump and inflates the GiB-hr line ~5×. Q4 (right-size to 1–2 GiB) is not a nice-to-have; it gates whether the modeled rates apply at all. Also note Modal's `container_disk` default is **50 GiB (51200)**, not 10 — a 5× storage-cost surprise if Modal is switched on without trimming.

4. **Q3 (cross-network gateway) is partly pre-answerable and partly under-weighted. (MEDIUM.)** Today the worker hits `127.0.0.1:4000`; a remote sandbox cannot. The doc lists this as open but doesn't flag that it forces **exposing the billing/markup gateway to the public internet with real auth (token/mTLS) + allowlist** before managed-Hermes can bill correctly — a non-trivial security workstream that intersects R1-2 (the zero-auth webhook already noted in our R1 plan) and R1-7 (SSRF). Mitigant found: Daytona supports per-sandbox outbound CIDR allowlists + block-all and authenticated preview tokens, which *helps* the egress-guard story — worth citing as a strength, not just an open question.

5. **Tokens omitted but dominate. (CONTEXT.)** Correctly scoped out, but for a founder reading "$1–2/agent/mo," the real bill is upstream LLM tokens via our gateway — orders of magnitude larger than compute. The "$0.30/mo agent" headline risks anchoring the wrong number.

### Tightened recommendation

Keep the platform call: **Daytona-first, Modal documented fallback, kube-green rejected, self-host (hardened Docker + homegrown stop/start) only as the RF-legal stopgap.** That ranking is correct and the F2/F3/F8 reasoning is sound. But fix the framing and the gating order:

- **Re-price honestly.** Per-agent cost = resident-gateway hosting (subject to the same F6 RAM ceiling) + active sandbox compute + disk. Drop "idle ≈ free / $0.30–$2/mo" as the planning figure until Phase 0 measures resident-gateway RAM and whether many gateways can share one host. The sandbox saves *tool-execution* cost, not *orchestrator* cost.
- **Re-frame Phase 0 around the real unknown:** not "does the agent hibernate in Daytona" (answered: no), but **"how cheaply can N resident `hermes gateway` processes co-exist on our infra, and can one gateway multiplex many users or is it one-process-per-agent?"** That, not the sandbox, is what determines whether this scales. If it's one resident process per agent, we are back at the F6 density ceiling and Daytona only offloads the shell.
- **Stop calling Daytona's isolation "structural."** State it as shared-kernel Docker by default; require Kata/microVM (or move to E2B/Fly) *before* any untrusted/public-template tenant — pull Phase-3 hardening forward to a gate, not an "optional later."
- **Trim resources in the config from day one** (`container_memory` 1–2 GiB, set Modal `container_disk` explicitly) and confirm the Daytona quota bump for anything above defaults.
- **Treat gateway exposure as a Phase-1 security task, not an open question:** public `:4000` with token/mTLS + allowlist, reusing the R1-7 egress work and closing the R1-2 auth gap; lean on Daytona's outbound CIDR allowlist for defense-in-depth.

Net: the *direction* is right and well-argued; the *numbers and the isolation adjective* are wrong, and the single highest risk was resolvable from public docs before the recommendation was written.
