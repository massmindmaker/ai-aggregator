# R-20 — Agent-to-Agent (A2A) standards landscape & what it means for AIAG

> **Date:** 2026-06-04 · **Scope:** the agent-to-agent commerce stack — **ERC-8004** (trustless agent identity/reputation/validation), **Google A2A** (Agent2Agent comms), **AP2** (Agent Payments Protocol), and **x402** as the settlement rail — and how AIAG could participate.
> **Method:** live web (built-in WebSearch + WebFetch; Exa MCP returned HTTP 400 at run time, Firecrawl deferred). Every claim carries a URL + date; self-reported metrics flagged.
> **Reads first:** `docs/specs/2026-06-04-tool-market-x402-plan.md` (our TON→credits→x402 money architecture, v1/v2/v3 plan) and `docs/specs/research/2026-06-04-R17-market-monitor.md` (§2 x402, §10 standards convergence).
> **One-line frame:** these four standards are **complementary, not competing** — they stack as **discover (A2A) → authorize (AP2) → identify/trust (ERC-8004) → settle (x402)**. AIAG already owns the middle (USD-credit ledger + budget caps + settleRun); A2A would bolt onto the edges.

---

## 1) What each standard does + maturity

### A2A (Agent2Agent) — the **discovery + communication** layer
- **What:** an open protocol for agents to **discover, authenticate, and delegate tasks** to other agents across frameworks/vendors. Each agent publishes an **Agent Card** (a JSON capability/endpoint descriptor) that other agents fetch to learn what it can do and how to call it. It is the "agents talking to agents" wire format — the analog of MCP, but MCP is agent→tool while A2A is agent→agent.
- **Governance/maturity:** released by Google **Apr 9, 2025**; **donated to the Linux Foundation Jun 23, 2025** (vendor-neutral Agent2Agent Protocol Project). **150+ supporting orgs** (Accenture, Atlassian, Box, Cohere, LangChain, MongoDB, PayPal, Salesforce, SAP, ServiceNow, UiPath…); deep integration across Google/Microsoft/AWS; **active enterprise production deployments** at the one-year mark. **A2A v1.0 (early 2026)** is the first "production-grade" cut — headline feature is **Signed Agent Cards** (a cryptographic signature so a receiver can verify the card was issued by the domain owner). **Maturity: HIGH (standardized, neutral governance, in production).**
- Sources: [Linux Foundation — A2A surpasses 150 orgs, enterprise production](https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year) · [LF — A2A project launch](https://www.linuxfoundation.org/press/linux-foundation-launches-the-agent2agent-protocol-project-to-enable-secure-intelligent-communication-between-ai-agents) · [Google Developers — donation](https://developers.googleblog.com/en/google-cloud-donates-a2a-to-linux-foundation/) · [Rapid Claw — 2026 A2A guide (Signed Agent Cards)](https://rapidclaw.dev/blog/a2a-protocol-complete-guide-2026)

### AP2 (Agent Payments Protocol) — the **authorization** layer
- **What:** an open protocol (Google + 60+ partners) for **authorizing agent payments via cryptographically signed mandates**, so a payment carries proof of *what the human authorized* even when the agent transacts autonomously. Built on **Verifiable Digital Credentials (VDCs)** — tamper-evident signed objects chained into an auditable record. Mandate framework: an **Intent/Checkout mandate** (user constraints / finalized cart) + a **Payment mandate** (open = constraints for autonomous execution, closed = a specific authorized amount). AP2 is structured as an **extension of A2A** and is **payment-rail-agnostic** (cards, bank, *and* crypto).
- **x402 tie-in:** Google + Coinbase + Ethereum Foundation + MetaMask shipped the **A2A x402 extension** — AP2 mandates carry through into x402 on-chain settlement, giving crypto payments the same audit trail card payments get under AP2.
- **Governance/maturity:** **v0.2.0, Apr 2026** (Python-first, with TS/Kotlin/Go reference impls); governance **transitioning to FIDO Alliance** working groups. Named live deployments: PayPal × Google Conversational Commerce, Mastercard Agent Pay pilot in PayPal, and the A2A-x402 crypto extension. **Maturity: MEDIUM (real spec + named pilots, still v0.x, governance in transition).**
- Sources: [ap2-protocol.org](https://ap2-protocol.org/) · [Google Cloud — announcing AP2](https://cloud.google.com/blog/products/ai-machine-learning/announcing-agents-to-payments-ap2-protocol) · [Coinbase — Google AP2 + x402, "agents can now pay each other"](https://www.coinbase.com/developer-platform/discover/launches/google_x402) · [Crossmint — protocols compared (MPP/ACP/AP2/x402)](https://www.crossmint.com/learn/agentic-payments-protocols-compared)

### x402 — the **settlement rail** (the one AIAG already plans to use)
- **What:** revives HTTP **402 Payment Required** as a machine-native paywall. Server replies `402` + price; client signs a stablecoin (USDC) payment payload and retries; a **facilitator** (`/verify` + `/settle`) does the on-chain part (gas, settlement). Same flow whether the payer is paying a *tool* (agent→tool) or another *agent* (agent→agent) — A2A x402 just wraps the same signed payload.
- **Governance/maturity:** Coinbase-originated (May 2025); **x402 Foundation** with Cloudflare (Sep 2025); **moved to Linux Foundation Apr 2026** (Circle, Google, Microsoft, Stripe, Visa). Adoption snapshot (R17, Apr 2026): **~69k active agents, 165M+ tx, $50M volume, 100M+ cumulative tx on Base.** Stripe settles Base x402 USDC→USD via PaymentIntents (Feb 2026). **Maturity: HIGH as infra**, but **demand is supply-led / thin** (CoinDesk caveat, R17 §2). **This is the rail our `2026-06-04-tool-market-x402-plan.md` already commits to (Coinbase CDP facilitator).**
- Sources: [BlockEden — x402 Foundation](https://blockeden.xyz/blog/2026/03/05/x402-foundation-ai-payment-internet/) · [eco.com — x402 explained](https://eco.com/support/en/articles/12328618-x402-protocol-explained-how-ai-agents-pay-onchain) · [AWS — x402 agentic commerce](https://aws.amazon.com/blogs/industries/x402-and-agentic-commerce-redefining-autonomous-payments-in-financial-services/) · plus R17 sources.

### ERC-8004 (Trustless Agents) — the **portable identity + reputation** layer
- **What:** an Ethereum standard giving an agent a **portable on-chain identity + reputation** so a counterparty can vet it before transacting. Three functional registries:
  1. **Identity Registry** — **ERC-721** token per agent; the NFT links to off-chain metadata (name, description, supported endpoints, **wallet addresses**, model provenance, capability claims) via a content-addressed (IPFS) hash. Portable/browsable/transferable.
  2. **Reputation Registry** — a standard interface for clients/other-agents to publish + read **feedback signals** (a persistent, queryable history of ratings after interactions).
  3. **Validation Registry** — hooks for **validator contracts** to publish proof an agent *actually did what it claims*.
- **Relationship to A2A/MCP:** ERC-8004 **explicitly extends Google's A2A** — the registration/metadata advertises the agent's **A2A + MCP endpoints**, adding an on-chain trust/accountability layer on top of those off-chain comms protocols. (Co-authored across MetaMask/EF/Google/Coinbase.)
- **Governance/maturity:** first proposed **Aug 2025**; **live on Ethereum mainnet ~Jan 29, 2026** (R17). R17 cited **200k+ registrations across 20+ chains in 11 weeks**; one source notes **401 feedback submissions in the first two weeks** (early reputation activity). Note: some write-ups still call it "Draft EIP" with "early mainnet deployments" — i.e. **live but young; treat adoption numbers as early-stage/self-reported.** **Maturity: EARLY (live, real registrations, but nascent; reputation data thin).**
- Sources: [eco.com — ERC-8004 trustless agent identity](https://eco.com/support/en/articles/14730445-erc-8004-trustless-agent-identity) · [Allium — what ERC-8004 unlocks (3 registries, 401 early feedbacks)](https://www.allium.so/blog/onchain-ai-identity-what-erc-8004-unlocks-for-agent-infrastructure/) · [QuickNode — dev guide](https://blog.quicknode.com/erc-8004-a-developers-guide-to-trustless-ai-agent-identity/) · [erc-8004 contracts (GitHub)](https://github.com/erc-8004/erc-8004-contracts) · [EIP-8004](https://eips.ethereum.org/EIPS/eip-8004) · plus R17 §10.

**The stack, in one line:** **A2A** = how agents find/talk to each other · **ERC-8004** = whether you can trust the one you found (identity + reputation) · **AP2** = the signed permission to spend on the user's behalf · **x402** = the actual stablecoin settlement. They compose; none replaces our credit ledger.

## 2) How OUR agents could participate (discover → hire → pay, money through the credit ledger)

The decisive fact: **AIAG never needs to put a hot crypto wallet behind every agent, and never needs TON→Base bridging for A2A.** Our agents spend the **AIAG USD-credit unit**; the platform is the **single on-chain actor** that settles externally. A2A bolts onto the same `tool-market-x402-plan.md` architecture — an "external agent" is just a special, priced **tool** from the agent's point of view.

**Money flow (AIAG agent hires an EXTERNAL A2A agent):**
```
AIAG agent decides it needs a capability (e.g. "deep web research")
   ↓  DISCOVER  — fetch external Agent Card (A2A) / look up ERC-8004 identity+reputation
   ↓  VET       — read reputation registry / signed Agent Card before committing
   ↓  the agent-worker treats the remote agent like a paid tool call (our broker)
   ↓  AUTHORIZE — our budget caps + daily-spend guard = the de-facto "mandate" (AP2-shaped)
   ↓  SETTLE    — broker pays the remote agent's x402 invoice via Coinbase CDP (USDC/Base)
   ↓  DEBIT     — agent's AIAG credits debited (cost × markup, integer ¢) via settleRun
```
This is **identical to the v2 tool-broker** in `tool-market-x402-plan.md` — A2A is "the tool happens to be another agent." `ToolExecResult.cost_credits → toolFeesCredits → settleRun` already carries it. **No new ledger.**

**Money flow (an external agent hires an AIAG agent — we are the SELLER):**
```
External agent fetches OUR agent's A2A Agent Card (we publish one)
   ↓ it calls our agent endpoint; we reply 402 + price (x402 server side)
   ↓ it pays our x402 invoice (USDC/Base via the facilitator)
   ↓ WE credit the author (author-rent payout) + take model-markup/tool/deploy margin
```
This is the **inbound** mirror and is the more strategically interesting (turns AIAG templates into sellable services in the open agent economy) — but also the heavier lift (we'd run an x402 *server* + receiving wallet + payout accounting), so it is later.

**AIAG-agent hires another AIAG-agent (internal A2A):** the cleanest near-term slice — **no chain at all.** It's a pure **internal ledger transfer**: debit caller's credits, credit callee's author. The "A2A protocol" here is just our own job/queue contract; we get the *product* of agent-hiring-agent without x402/ERC-8004 risk. (This is the honest MVP of "agents hiring agents.")

**Where each standard plugs into our stack:**
| Standard | Our plug point | Build weight |
|---|---|---|
| **A2A Agent Card** | publish a Card per public template; consume external Cards in the broker | light–medium (JSON + signature verify) |
| **AP2 mandate** | our **budget caps + daily guard + allowlist already ARE the mandate** — adopt AP2's *shape* (signed intent), don't need its full VDC chain yet | conceptual now, real later |
| **x402** | already the committed rail (CDP facilitator, Server Wallet, testnet-first) | already planned (v2) |
| **ERC-8004** | optional: register OUR agents for **portable reputation**; read others' reputation before hiring | R&D, far slice |

## 3) Realistic near-term slice vs far-future R&D

**Near-term (this still fits the existing v1→v2 plan; small additions):**
- **Internal A2A = ledger-only.** Let one AIAG agent invoke another as a priced capability; settle as an internal credit transfer (debit caller, pay author). **Zero crypto, zero new infra.** This is the genuinely shippable "agents hire agents" and it strengthens author-rent (an author's agent can earn from *other agents*, not just humans).
- **Consume external x402 tools (already v2).** The same broker that pays an x402 *tool* can pay an external *A2A agent* — they're the same 402 flow. So "hire an external agent" piggybacks on the v2 tool-broker spike, no separate project.
- **Publish a (static) A2A Agent Card** for public templates — cheap, makes AIAG agents *discoverable* by the wider A2A ecosystem with no on-chain commitment. Optional, low-risk.

**Far-future / R&D (do NOT build now):**
- **ERC-8004 registration + on-chain reputation** for AIAG agents — portable cross-marketplace reputation is a real future differentiator vs walled gardens (Poe/Character.ai, R17 §5/§7), but it's early, thin on data, and adds Ethereum-mainnet ops we don't want on a 2GB box. Park as R&D; **revisit when an author actually asks to take reputation off-platform.**
- **Full AP2 VDC mandate chain** — we get 90% of the value from our existing budget caps; the signed-VDC audit trail matters only once we settle *real external* agent payments at volume. Adopt the *shape* now, the *spec* later.
- **Being an x402 SELLER (inbound).** Running an x402 server + receiving wallet + payout reconciliation for external buyers is a meaningful custody/accounting lift. Later.

**Honest demand caveat (carry from R17):** CoinDesk (Mar 2026) — micropayment demand "is just not there yet"; the space is **supply-heavy, demand-light**. So **build the rail thin, don't over-invest in A2A breadth** until a real buyer/seller shows up. Internal-ledger A2A has product value regardless of the crypto cycle; external A2A should stay a **thin adapter behind a flag**.

## 4) Does adopting any of this change our credit-hub / adapter plan?

**No — it validates and extends it; it does not redirect it.** The `tool-market-x402-plan.md` thesis (**TON front → AIAG USD-credits middle → x402/USDC back**, credit ledger as the bridge) is **exactly the right shape** for A2A:
- The credit ledger is **the universal unit** whether the agent pays a tool, an internal agent, or an external A2A agent. One unit, user never sees chains. **Unchanged.**
- A2A external-agent payments are **a new *kind of payee* on the existing x402 broker**, not a new settlement system. The adapter pattern (resolveUpstream / broker) absorbs it.
- **Our budget-card already pre-implements AP2's intent** — daily caps + per-call cap + allowlist = the user's "mandate." We can later *describe* it in AP2 terms without re-architecting.

**One refinement to fold into the plan:** generalize the v2 broker's notion of "tool" to **"priced external capability,"** of which `{x402 tool, A2A external agent, internal AIAG agent}` are three subtypes sharing one debit path. That keeps `v3 — A2A` (already in the plan as future) from becoming a separate stack. **No conflict with the credit-hub direction; it's a one-noun generalization.**

## 5) The honest custody / compliance angle

- **Custody (mirror the eval-sandbox + tool-market cautions):** A2A does **not** change our custody posture *if we keep agents spending credits, not coins*. The only on-chain wallet is the **platform's** CDP-managed Server Wallet (testnet-first, then a small funded Base wallet) — **never a hot mainnet wallet per agent on the 2GB prod box.** Inbound x402 (us as seller) would add a *receiving* wallet — defer precisely because it raises custody surface.
- **ERC-8004 = a public, immutable on-chain footprint.** Registering an AIAG agent writes its identity/endpoints/wallet to a public chain forever. That's fine for a *published* template, but conflicts with the **private/keys-out** template rule — never register anything that leaks keys, memory, or the personal Telegram. Treat 8004 registration as **publish-only metadata**, opt-in per author.
- **Compliance (the foreign-entity structure, per `/CLAUDE.md`):** agent-to-agent USDC settlement sits cleanly on the **non-RF foreign entity** that already "buys models from the RF aggregator" — same posture as x402 tools and the crypto-credit ledger. **Don't introduce A2A money flows on the RF (ИП) leg.** Founder decision (2026-06-03): "legal not factored now" — so A2A external settlement stays **R&D behind the foreign entity**, consistent with FD-2/FD-3.
- **White-label / honesty:** A2A external calls must not leak upstream provider brands, and the UI must label external-agent hiring honestly (`скоро`/`R&D`) until the broker is real — never dead-end a paid "hire this agent" flow into an unbuilt settlement (PRODUCT.md rule 1).
- **Trust without reputation data:** ERC-8004 reputation is **young and thin** (early feedback counts only). Hiring an external agent on the strength of an on-chain rating today is risky — keep a **curation gate** (we whitelist external agents) before trusting registry reputation, mirroring AIAG's curated-not-firehose edge (R17 §3).

## TL;DR (4-sentence summary)

The agent-to-agent stack has standardized into four **complementary** layers — **A2A** (discover/communicate, Linux Foundation, v1.0, 150+ orgs, production), **ERC-8004** (portable on-chain identity+reputation, live on Ethereum mainnet Jan 2026 but young/thin), **AP2** (signed-mandate payment authorization, v0.2, FIDO-bound, named pilots), and **x402** (the USDC settlement rail AIAG already commits to) — which compose as discover→trust→authorize→settle and **do not replace AIAG's USD-credit ledger; they bolt onto its edges.** Our agents could participate with **no new ledger and no per-agent hot wallet**: an external agent is just a priced capability on the *same* v2 tool-broker (pay its x402 invoice via Coinbase CDP, debit credits ×markup through `settleRun`), our budget caps already serve as the AP2-style "mandate," and the foreign-entity structure already absorbs the on-chain settlement leg. The **only genuinely near-term-actionable slice is internal A2A as a pure ledger transfer** — let one AIAG agent hire another and pay the author entirely in credits with **zero crypto/ERC-8004/AP2 risk**, which strengthens author-rent and ships within the existing plan; external x402-settled A2A piggybacks on the already-planned v2 tool-broker, while ERC-8004 registration and full AP2 VDC mandates stay R&D. **Net: adopt nothing new structurally — generalize the v2 broker's "tool" into "priced external capability" (tool | internal agent | external A2A agent) sharing one debit path, and ship internal agent-hiring first.**

**Near-term-actionable for us? YES, one slice:** internal agent-to-agent hiring billed as an internal credit transfer (no chain) — shippable inside the existing credit ledger and additive to author-rent. Everything crypto-settled (external A2A, x402-as-seller, ERC-8004 identity, full AP2 mandates) stays correctly parked as R&D behind the foreign entity, riding the v2 x402 broker when it lands.
