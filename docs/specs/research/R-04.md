# R-04 — Crypto credit + wallet architecture

> Research item for the AIAG TMA. Designs the credit/wallet: single canonical
> ledger, fiat-anchored credit unit + FX source, deposit-watcher reliability fix
> (cron reconciler + on-chain indexer), HOT Wallet integration, and jetton
> USDT-on-TON handling.
> Author: staff-eng research pass. Date: 2026-06-03.
> Code paths cited are absolute or repo-relative to `C:\Users\боб\projects\aggregator`.

---

## Summary

The TMA today runs a **second, parallel money system** bolted onto the side of
the real gateway ledger. It is a single-balance projection (`tg_user_balances.balance_rub`,
₽-denominated) credited by a **client-driven TON top-up poller** and debited by
`settleRun` in the agent-worker. The gateway — which already has a proper
fiat-anchored ledger (`organizations.subscription_credits`/`payg_credits`,
double-entry `gateway_transactions`, the atomic `aiag_settle_charge` stored
function, and a real CBR USD→RUB FX source with retries/cache/spread/sanity
bounds) — is **bypassed** for TMA billing. The result is two ledgers, two FX
sources (gateway = CBR; worker + topup = hardcoded `USD_TO_RUB = 90` and CoinGecko
TON→RUB), and a deposit watcher with four documented loss modes.

**Recommendation (headline):**

1. **Keep two physically separate balance tables** but make **one of them the
   single billing authority for the TMA**: `tg_user_balances` becomes the canonical
   TMA wallet ledger, upgraded from a single `balance_rub` column to a real
   **append-only double-entry ledger** (`tg_ledger_entries`) with the balance as a
   derived/materialized projection. Do **not** try to fold TMA users into the
   gateway's org-scoped `organizations` ledger — they have different identity
   (tg_user_id BIGINT vs org UUID), different currency anchor, and different legal
   entity (foreign crypto entity vs RF ИП). Unifying the *schema pattern* (the
   `aiag_settle_charge` double-entry+idempotency design) is right; unifying the
   *tables* is wrong.
2. **Peg the credit unit to USD, not ₽.** Define `1 credit = 1 USD` (store
   micro-USD integers). USD is the natural anchor: upstream model prices are quoted
   in USD, USDT is a USD stablecoin, and the foreign entity is USD-exposed. Kill
   `USD_TO_RUB = 90`. The gateway already proves the FX pattern (CBR); the TMA FX
   need is the *inverse* and simpler (cost is already USD upstream; only the *display*
   needs an FX rate, and credits-in equal USDT-in 1:1).
3. **Fix the deposit watcher** with a **server-side reconciler cron** (sweeps all
   `pending` topups against an on-chain indexer, independent of the client) **plus a
   push path** (TonAPI webhook → our endpoint) for low latency. The client poll
   stays only as a UX nicety, never as the source of truth.
4. **Adopt USDT-jetton-on-TON as the primary deposit asset** (stable, no FX risk on
   the credit), keep native TON as a secondary option (FX-converted at confirm time).
   Jetton handling requires the `transfer_notification` (op `0x7362d09c`) path and a
   **jetton-master allowlist** to defeat fake-token attacks.
5. **HOT Wallet** integrates as an additional TON Connect wallet via
   `walletsListConfiguration` (zero new flow) and/or its `@hot-wallet/sdk` for
   multichain — but for an MVP that bills in USDT-on-TON, the existing
   `@tonconnect/ui-react` flow already covers HOT Wallet because HOT exposes a TON
   Connect bridge. HOT's value is *reach* (30M+ Telegram wallets, multichain), not a
   new integration requirement.

## Part 1 — The ledger: single canonical authority

### 1.1 What exists today (code-grounded)

There are **two unrelated ledgers** in one Postgres `aiag` DB:

**A) Gateway / WEB ledger (mature, double-entry, org-scoped):**

- `organizations.subscription_credits` + `payg_credits` + `subscription_credits_expires_at`
  — the live balances (₽). Source: `packages/database/src/functions/settle-charge.sql`,
  `packages/api-gateway/src/routes/v1/balance.ts`.
- `gateway_transactions` — append-only ledger rows (`type`, `source`, `delta`,
  `request_id`, `metadata`), with a **partial UNIQUE index on `(request_id, source)
  WHERE type='api_usage'`** for idempotency. Source:
  `packages/database/src/schema/gateway.ts:239`.
- `aiag_settle_charge(_org_id, _request_id, _total_rub)` — a plpgsql function that:
  `SELECT … FOR UPDATE` on the org row (serializes per-org), checks idempotency
  *inside* the lock (kills TOCTOU), splits the charge into subscription+payg buckets,
  does a guarded `UPDATE … WHERE credits >= portion RETURNING`, writes the two ledger
  rows, and accrues author earnings. Raises typed `P0001..P0004` error codes. This is
  the **gold-standard money primitive in the repo.** Source: `settle-charge.sql:22`.
- FX: real CBR (Russian Central Bank) USD→RUB with 3-retry backoff, 24h Redis cache,
  7-day `last_known` fallback, configurable spread, and a 30..500 sanity bound.
  Source: `packages/api-gateway/src/lib/cbr.ts`.

**B) TMA ledger (immature, single-column, tg_user-scoped):**

- `tg_user_balances (tg_user_id BIGINT PK, balance_rub NUMERIC(14,4), updated_at)`
  — a **single mutable balance column, no transaction journal.** Source:
  `packages/database/migrations/0019_ton_wallets.sql:19`.
- Credited by the topup-check route: `INSERT … ON CONFLICT DO UPDATE SET balance_rub =
  balance_rub + EXCLUDED.balance_rub`. Source:
  `apps/tg-miniapp/app/api/tma/topup/check/[id]/route.ts:149`.
- Debited by `settleRun` in the worker: guarded `UPDATE tg_user_balances SET balance_rub
  = balance_rub - costRub WHERE balance_rub >= costRub RETURNING` inside one `sql.begin`
  with the run completion + daily-spend guard. Source:
  `apps/agent-worker/src/db.ts:328` (`settleRun`).
- FX: **hardcoded `USD_TO_RUB = 90`** in the worker (`apps/agent-worker/src/agent-runner.ts:30`)
  for cost estimation, and **CoinGecko TON→RUB** in `apps/tg-miniapp/src/lib/ton-rate.ts`
  for the top-up quote. Neither uses the gateway's CBR source.

The agent-worker's "aiag" path *does* route through the gateway (`AGENT_GATEWAY_URL =
http://127.0.0.1:4000/v1/chat/completions`), so the gateway *also* settles a charge
against **some org** for the same run — meaning a billable TMA run can hit **both**
ledgers (gateway org credits AND `tg_user_balances`), or, in the documented fallback,
go direct to OpenRouter and only hit `tg_user_balances`. This is the core incoherence.

### 1.2 The decision: projection vs unify

**Option A — Fold TMA users into the gateway `organizations` ledger (unify tables).**
Rejected. Reasons:
- Identity mismatch: gateway is `org_id UUID`; TMA is `tg_user_id BIGINT`. Every TMA
  user would need a shadow org row, and the gateway's whole auth/key model
  (`gateway_api_keys` org-scoped) does not map to a Telegram user.
- Currency/legal mismatch: the gateway ledger is ₽ for the **RF ИП** entity (CLAUDE.md:
  "Billing: RUBLES (₽) ONLY … No crypto"). The TMA is crypto for a **foreign entity**
  ("ALL crypto exposure off the RF entity"). Co-mingling crypto credits into the RF
  entity's org ledger is a compliance problem, not just a schema one.
- Blast radius: the gateway ledger is **live on the WEB product**; reshaping it for TMA
  risks the revenue path of a shipping product.

**Option B — `tg_user_balances` is the single TMA authority; gateway is a pure
upstream (no TMA settlement).** **Recommended.**
- The gateway becomes a **white-label model provider only** for the TMA. It should
  meter usage (so we know the upstream cost) but the **authoritative debit happens once,
  in the TMA ledger**, inside `settleRun`. The gateway's `aiag_settle_charge` runs
  against a **single internal "TMA house org"** purely for upstream-cost accounting /
  reconciliation, not as the user-facing balance. (Or: the TMA worker calls the gateway
  with a key whose org is a house account, and we treat the gateway charge as our COGS
  ledger, while the user-facing credit ledger is `tg_user_balances`.)
- This gives **exactly one balance a TMA user can see and one place it is debited**,
  eliminating the double-debit / which-ledger-is-truth ambiguity.

**Option C — Upgrade `tg_user_balances` to a real double-entry ledger (do this *inside*
Option B).** **Recommended and required.** A single mutable `balance_rub` column has no
audit trail: you cannot prove why a balance is what it is, cannot reconcile against
on-chain deposits, and cannot safely reverse a mis-credit. Port the gateway's proven
pattern:

```
tg_ledger_entries (
  id              UUID PK default gen_random_uuid(),
  tg_user_id      BIGINT NOT NULL,
  kind            TEXT NOT NULL,        -- 'topup' | 'run_charge' | 'refund' | 'adjustment' | 'tool_fee'
  delta_micro_usd BIGINT NOT NULL,      -- +credit / -debit, integer micro-USD (see Part 2)
  ref_type        TEXT,                 -- 'topup' | 'agent_run' | 'manual'
  ref_id          TEXT,                 -- topup.id / run.id (idempotency key)
  rate_meta       JSONB NOT NULL default '{}',  -- {usd_rub, ton_usd, source, ts} snapshot
  created_at      TIMESTAMPTZ NOT NULL default now()
)
-- idempotency: a charge/credit for a given (kind, ref_id) lands at most once
CREATE UNIQUE INDEX uq_tg_ledger_ref ON tg_ledger_entries (kind, ref_type, ref_id)
  WHERE ref_id IS NOT NULL;
```

Keep `tg_user_balances` as the **materialized projection** (the fast-read current
balance), updated in the *same transaction* that inserts the ledger entry, using the
same guarded `UPDATE … WHERE balance >= debit RETURNING` pattern `settleRun` already
uses. The ledger entries are the source of truth; the projection is for the hot read
path (run-start gate, wallet screen). A periodic invariant check (`SUM(delta) ==
projection`) catches drift.

**Net:** `settleRun` stays atomic and READ COMMITTED + guarded-UPDATE (per SECURITY.md);
it just additionally writes a `tg_ledger_entries` row in the same `sql.begin`. The
topup-credit path does the same. This is a low-risk extension of the existing pattern,
not a rewrite.

## Part 2 — Credit unit + FX anchor

### 2.1 The problem with the status quo

- The unit is `balance_rub` (₽), but the founder decision (CLAUDE.md, 2026-06-02) is
  **"TMA currency = crypto credits (USDT/TON); ₽ removed from TMA."** The ₽ column is
  now a misnomer pending migration.
- Two ad-hoc FX sources, neither the canonical CBR: `USD_TO_RUB = 90` (a stale constant,
  off by ~15-30% vs reality and silently undercharges or overcharges) and CoinGecko
  TON→RUB (a third-party rate with no spread, no fallback chain).

### 2.2 Recommended anchor: **USD, stored as integer micro-USD**

Define **1 credit = 1 USD**, stored as `BIGINT` micro-USD (`1_000_000 = $1`). Rationale:

- **Upstream cost is already USD.** `agent-runner.ts` `PRICING` is USD-per-1M-tokens; the
  gateway's `model_upstreams` prices are USD; OpenRouter/Kie bill USD. Anchoring credits
  to USD means **the COGS side needs no FX at all** — `cost_micro_usd =
  tokens × price_usd`. FX only enters for *display* and for *native-TON* deposits.
- **USDT is a USD stablecoin.** A USDT-jetton deposit credits **1:1** to USD credits
  (minus a small spread/fee). No FX rate, no rate risk, no "rate was stale" loss. This is
  the single biggest reliability win available and it falls out of the anchor choice.
- **Integer micro-USD kills float drift.** `NUMERIC` works but integers are unambiguous
  for a ledger and trivially summable.
- The foreign entity is USD-exposed; ₽ is irrelevant to it.

**Display in ₽ (and TON)** is a presentation concern only: show `credits × usd_rub` using
the **gateway's CBR source** (`fetchUsdRubRate()` in `packages/api-gateway/src/lib/cbr.ts`)
exposed via a tiny internal endpoint, so the TMA and gateway agree on one rate with one
fallback chain. Never hardcode 90 again.

### 2.3 FX source policy (concrete)

| Need | Source | Spread / fallback |
|---|---|---|
| Upstream cost (COGS) | none — already USD | n/a |
| USDT-jetton deposit → credits | 1:1 (USDT≈USD) | flat platform fee (e.g. 1-2%) instead of FX spread |
| Native-TON deposit → credits | TON→USD at confirm time | use a real source w/ retries+cache+spread+sanity bounds (mirror `cbr.ts`); snapshot the rate into `tg_ledger_entries.rate_meta` |
| ₽ display | CBR USD→RUB via gateway `fetchUsdRubRate()` | already has 3-retry, 24h cache, 7d last_known, 30..500 sanity |

For the native-TON rate, **reuse the cbr.ts shape** (it is the repo's vetted pattern):
fetch from a primary + fallback source, cache in Redis, keep a `last_known`, apply a
configurable spread, sanity-bound the value, and **snapshot the exact rate used into the
ledger row** so a deposit's credited amount is forever explainable. Prefer pulling
TON/USD from the same indexer you already trust for deposits (TonAPI exposes rates) to
avoid a third vendor.

**Migration note:** `tg_user_balances.balance_rub` (₽) must be converted to micro-USD
once, at a snapshot CBR rate, with a one-time `tg_ledger_entries` `kind='migration'` row
per user recording the old ₽, the rate, and the new micro-USD — so the cutover is itself
auditable. Per `packages/database/CLAUDE.md`, the ALTER runs via `sudo -u postgres psql
aiag` (app role cannot ALTER) and prod migrations are manual/untracked — plan the column
add + backfill + (eventual) drop accordingly.

## Part 3 — Deposit-watcher reliability (the funds-loss bug)

### 3.1 The four loss modes (confirmed in code)

The current watcher is `POST /api/tma/topup/check/[id]` driven **only** by the client
poll loop in `apps/tg-miniapp/app/profile/topup/page.tsx` (`POLL_INTERVAL_MS = 5000`,
`POLL_MAX_ATTEMPTS = 120` ⇒ **10-minute window**). It queries TonCenter v3 for the
**last 20 transactions** on the receiver and matches by `comment_tag`. Loss modes:

1. **App closed / user leaves before confirm** → no poll runs → topup stays `pending`
   forever → funds received on-chain, never credited.
2. **Outside the last-20-tx window** → on a busy receiver wallet, the matching tx scrolls
   past `limit=20` before the poll sees it → never matched. Source:
   `topup/check/[id]/route.ts:77` (`limit=20`).
3. **Past the 10-minute window** → slow block / congestion / user pays late → poll loop
   exhausts `POLL_MAX_ATTEMPTS` and gives up with "проверьте позже", but **nothing ever
   checks later** (no server cron). Funds stranded.
4. **TonCenter transient error** → route returns `status:'pending'` and the only retrier
   is the same doomed client loop. Source: `topup/check/[id]/route.ts:88-105`.

Additional latent issues:
- **No jetton support** — the matcher reads `in_msg.value` (native TON nanotons) only; a
  USDT-jetton deposit has `value≈0` + a `transfer_notification` body, so it would never
  match (Part 4).
- **Comment-tag-only matching** is weak: it does not verify the *sender* equals the
  user's linked wallet, and TON text comments are not authenticated. Two users could in
  principle reuse a tag; the `crypto.getRandomValues` 8-char tag from a 32-char alphabet
  makes collision unlikely but the design relies on secrecy of the tag, not on identity.

### 3.2 The fix: server-side reconciler cron + push indexer + client poll (UX only)

Three layers, defense-in-depth. The **server reconciler is the authority**; the others
are latency optimizations.

**Layer 1 — Server reconciler cron (authoritative, MUST build).**
A scheduled job (every 30-60s) that:
- Selects all `tg_topups WHERE status='pending' AND created_at > now() - interval '24h'`
  (24h grace, not 10 min — funds that arrive late still get credited).
- For each, queries an **on-chain indexer paginated over the full window** (not just last
  20) for inbound txs on the receiver, matching native TON by `comment_tag` and jetton by
  `transfer_notification` + allowlisted master + `forward_payload` comment.
- On match: the **same atomic confirm+credit** the route already does
  (`UPDATE tg_topups SET status='confirmed' … WHERE status='pending' RETURNING` then
  ledger credit), now also writing a `tg_ledger_entries` row. Idempotent via the status
  guard + the ledger unique index.
- Expires topups `> 24h` to `status='expired'` (informational; a late deposit can still
  be reconciled by an admin/sweeper because the on-chain tx is permanent).

Where to run it: the repo already has a worker cron pattern (`apps/worker/src/jobs/…`,
`aiag_ensure_request_partition` is called by a worker cron) and BullMQ in the agent-worker
on `:3101`. A **BullMQ repeatable job in agent-worker** (or a `node-cron` in the gateway)
is the least-new-infra option on the 2GB VPS. Do **not** add a new service.

**Layer 2 — Push via TonAPI webhook (low-latency, SHOULD build).**
TonAPI Webhooks API (the Streaming/SSE API is deprecated in favor of webhooks):
- Create once: `POST https://rt.tonapi.io/webhooks {"endpoint":"https://…/api/tma/topup/ton-webhook"}`
  → `{"webhook_id": N}`. Auth via Bearer API key from tonconsole.com.
- Subscribe the receiver: `POST https://rt.tonapi.io/webhooks/{id}/account-tx/subscribe
  {"accounts":[{"account_id":"0:…"}]}`.
- On a tx, TonAPI POSTs `{account_id, lt, tx_hash}` to our endpoint. Our handler
  **does not trust the payload** — it uses `tx_hash` to fetch the full tx from the
  indexer, validates it (amount, comment/master), and runs the same atomic confirm+credit
  as the cron. The webhook just **wakes us up faster**; the cron is the safety net if the
  webhook is missed.
- Testnet: `https://rt-testnet.tonapi.io/`.

**Layer 3 — Client poll (UX only, KEEP but demote).**
The existing poll stays purely to update the UI ("✓ зачислено") quickly when the user is
present. It must **never** be the only thing that credits — and ideally it calls a
read-only status endpoint, with crediting moved entirely to layers 1+2 so there is one
write path.

**Indexer choice:** keep **TonCenter v3** as the deposit-scan source you already use (free,
`/transactions?account=…&limit&offset` supports pagination for the full-window scan), and
add **TonAPI** for the webhook push + as a second corroborating source. Using two
independent indexers for confirm reduces single-vendor-outage risk. Both are read paths;
the on-chain tx is the ground truth.

## Part 4 — Jetton USDT-on-TON handling

USDT on TON is the **recommended primary deposit asset** because a USDT deposit maps 1:1
to USD credits (no FX risk on the credited amount).

**Facts (sourced):**
- Official USDT-on-TON jetton master: `EQCxE6mUtQJKFnGfaROTKOt1lZbDiiX1kCixRv7Nw2Id_sDs`
  (Tether USD₮, launched 2023-04-18). **Decimals = 6** (`1 USDT = 1_000_000` base units).
- Jettons do **not** move value in `in_msg.value`. The receiver's **jetton wallet**
  receives an `internal_transfer` and emits a **`transfer_notification`** (op
  **`0x7362d09c`**) to the owner address — *only if* `forward_ton_amount > 0`. A transfer
  is "successful" from the recipient's POV only when this notification arrives.
- The notification body (TL-B) carries: `query_id`, `amount` (base units, not decimals),
  `sender` (original sender), `forward_payload` (the comment / invoice tag).

**Deposit flow (concrete):**
1. **Derive our deposit jetton wallet** once: call the USDT master's
   `get_wallet_address(OUR_RECEIVER)` → that is the address that will receive
   `internal_transfer`s and emit notifications to `OUR_RECEIVER`. Store
   `master → our_jetton_wallet → receiver` in DB.
2. **Watch `OUR_RECEIVER`** (the same account the cron + webhook already watch) for inbound
   messages with op `0x7362d09c`.
3. **Validate against fake jettons (critical):**
   - Maintain an **allowlist** of jetton masters (start with just the official USDT master).
   - On a notification, call `master.get_wallet_address(OUR_RECEIVER)` on the *allowlisted*
     master and verify the **notification's source jetton wallet == that derived address**.
     This proves the tokens are real USDT, not a look-alike jetton with the same name/symbol.
   - Reject anything from a non-allowlisted master. Never trust metadata (name/symbol).
4. **Match + credit:** read `forward_payload` for the `topup:<tag>` comment, match the
   `tg_topups` row, verify `amount >= expected` (in 6-decimal base units), then atomic
   confirm + ledger credit. With the USD anchor, `credit_micro_usd = amount_base_units`
   (6-decimal USDT base unit == micro-USD, conveniently) minus the platform fee.
5. **Top-up init for jetton:** the invoice must build a **jetton transfer** message (TON
   Connect "send" to the user's jetton wallet, carrying a `forward_ton_amount > 0` and the
   comment in `forward_payload`), not a plain TON comment transfer. Reference
   implementation: `ton-community/tma-usdt-payments-demo` (official TMA USDT demo).

**Keep native TON as a secondary option** (existing flow), FX-converted at confirm via the
Part-2 TON→USD source, rate snapshotted into the ledger.

## Part 5 — HOT Wallet integration

**What HOT Wallet is:** a non-custodial, **MPC-based, multichain** wallet living inside
Telegram (30M+ wallets), supporting TON, EVM, Solana, NEAR, Stellar. SDK org: `hot-dao`
on GitHub; package **`@hot-wallet/sdk`**.

**Two integration paths:**

1. **As a TON Connect wallet (recommended for MVP — near-zero work).** The TMA already
   uses `@tonconnect/ui-react` (`TonConnectButton`, `useTonAddress`,
   `useTonConnectUI().sendTransaction` in `topup/page.tsx`). HOT exposes a TON Connect
   bridge, so it can appear in the wallet picker. If it is not auto-listed, add it via
   `TonConnectUIProvider`'s **`walletsListConfiguration.includeWallets`** with HOT's
   `appName/name/imageUrl/universalLink/bridgeUrl/platforms`. No new SDK, no new payment
   flow — the existing `sendTransaction` (extended to jetton transfers per Part 4) works.

2. **Via `@hot-wallet/sdk` (multichain, later).** If the product later wants deposits from
   chains beyond TON (USDT-on-TRON/EVM/Solana), HOT's SDK gives one connect surface:
   - `import "@hot-wallet/sdk/adapter/ton"` — TON Connect-compatible adapter.
   - `import "@hot-wallet/sdk"` + `HOT.setupEthProvider(...)` for EVM (web3modal/rainbowkit).
   - Per-chain send methods: `ton:send`, `solana:signAndSendTransaction`,
     `near:signAndSendTransaction`, EVM via the eth provider — all under the unified
     `HOT.request()` low-level API.
   - When the mini app is opened *inside* HOT, the SDK auto-detects the HOT wallet.

**Recommendation:** for the credit/wallet MVP, treat HOT as **one more TON Connect wallet**
(reach, not new integration) and bill exclusively in **USDT-on-TON**. Defer the
multichain `@hot-wallet/sdk` path until there is demand for non-TON deposits; when it
comes, HOT's omnibridge + MPC model is the cleanest way to accept multichain USDT into the
single USD-anchored credit ledger without us running per-chain indexers.

## Concrete recommendation (build order)

1. **Schema (one migration, via `sudo -u postgres psql aiag`):** add `tg_ledger_entries`
   (double-entry, idempotent), add `balance_micro_usd BIGINT` to `tg_user_balances`,
   backfill from `balance_rub` at a snapshot CBR rate with a `kind='migration'` ledger row.
   Keep `tg_user_balances` as the projection.
2. **Credit unit = USD (micro-USD integers).** Delete `USD_TO_RUB = 90`; cost is computed
   directly in USD from token×price. Make `settleRun` and the topup-credit path write a
   `tg_ledger_entries` row in the same `sql.begin` and update the projection with the
   existing guarded-UPDATE.
3. **FX:** expose the gateway's `fetchUsdRubRate()` (CBR) via an internal endpoint for ₽
   *display* only; add a TON→USD source mirroring `cbr.ts` (retries/cache/spread/sanity)
   for native-TON deposits; snapshot every rate into `rate_meta`.
4. **Deposit reconciler cron** in agent-worker (BullMQ repeatable, 30-60s): full-window
   indexer scan over all `pending` topups < 24h, atomic confirm+credit, idempotent. This
   is the authoritative fix for all four loss modes.
5. **Jetton USDT support:** derive our jetton wallet from the official master, parse
   `transfer_notification` (op `0x7362d09c`), enforce a **jetton-master allowlist**, credit
   1:1 to USD. Build jetton top-up invoices (`forward_ton_amount>0` + comment). Reference
   `tma-usdt-payments-demo`.
6. **TonAPI webhook** (`rt.tonapi.io`) as the low-latency push that wakes the same
   confirm+credit logic; validate by re-fetching the tx (don't trust the webhook body).
7. **Demote the client poll** to a read-only UX status check; move all crediting to the
   server (cron + webhook).
8. **HOT Wallet:** add to `walletsListConfiguration` so it shows in the TON Connect picker.
   Defer `@hot-wallet/sdk` multichain until non-TON deposits are demanded.

## Risks

- **Migration of a LIVE balance.** `tg_user_balances` is live (R0 shipped). The ₽→USD
  cutover must be a single auditable, idempotent migration with a ledger row per user; a
  wrong rate or double-run silently mis-credits real users. Prod migrations are manual and
  untracked (`packages/database/CLAUDE.md`) — high operational care required.
- **Double-debit during transition.** Today a billable run can settle on *both* the gateway
  org ledger and `tg_user_balances`. Until the gateway is explicitly demoted to "house COGS
  ledger" for TMA, there is a real risk of charging twice or disagreeing on truth. The
  Option-B boundary must be made explicit in code, not assumed.
- **Fake-jetton theft of credits.** If the allowlist/`get_wallet_address` validation is
  skipped, an attacker deposits a worthless look-alike "USDT" jetton and is credited real
  USD. This is the highest-severity correctness risk in jetton handling — non-negotiable.
- **Indexer trust / single vendor.** Crediting on indexer data (not a full node) means an
  indexer bug/outage can mis-credit or stall. Mitigate with two independent sources
  (TonCenter + TonAPI) corroborating before credit, and re-fetching the tx on webhook.
- **2GB VPS capacity.** The reconciler cron + webhook endpoint add load; keep them in the
  existing agent-worker/gateway processes (no new pm2 service) per the documented constraint.
- **TON comment authenticity.** `comment_tag` matching is unauthenticated; pairing it with
  sender == linked-wallet and a sufficiently random tag is required, and even then the
  deposit identity rests on the tag. Consider per-user sub-wallets / memo-less address
  derivation long-term.
- **Webhook spoofing.** `rt.tonapi.io` POSTs to a public endpoint; the handler must ignore
  the body's claims and re-verify on-chain, and ideally validate the source / a shared
  secret, or an attacker can trigger spurious confirm attempts (harmless if re-verified,
  DoS-able if not rate-limited).

## Open questions

1. **Gateway role for TMA:** does the TMA worker route through the gateway as a *house org*
   (gateway = COGS ledger) or bypass it entirely to OpenRouter? The chosen answer decides
   whether double-debit risk exists. (Today: routes through gateway when `AIAG_GATEWAY_KEY`
   set, else falls back to OpenRouter — neither path is reconciled against `tg_user_balances`
   as COGS.)
2. **Credit display unit:** show users credits as `$`/`credits`, ₽, or TON? USD anchor is
   recommended for billing; the *display* currency is a product decision (the brief says
   "draw mockups in crypto credits, NOT ₽").
3. **Platform fee model:** flat % on top-up, markup on runs (the existing per-upstream
   `model_upstreams.markup`), or both? With a USD anchor and 1:1 USDT, the natural revenue
   knob is the run markup the gateway already applies — confirm it is preserved end-to-end.
4. **Withdrawals / refunds:** is the wallet deposit-only (credits are non-refundable), or
   must users be able to withdraw remaining credits back to TON/USDT? Withdrawal turns this
   into a custodial flow with materially higher compliance/security weight (hot-wallet key
   management, payout signing) — out of scope here but decides the long-term architecture.
5. **Per-user deposit addresses:** the comment-tag model uses one shared receiver. Moving to
   per-user derived jetton wallets removes the comment-matching weakness but adds wallet
   management. Worth it at scale?
6. **HOT vs TON Connect default:** should HOT be the *promoted* wallet (given its Telegram
   reach) or just one option? Affects onboarding conversion.

## Adversarial review

**Verdict: holds up (partly).** The diagnosis is correct and code-grounded, the
core architecture call (Option B + double-entry ledger + USD anchor) is right,
and every load-bearing external fact verified. But the report under-states one
correctness bug, over-states the 1:1 USDT claim, and ships a top-up *init*
recommendation that is technically wrong on TON. Adopt the recommendation with
the four corrections below.

### What I verified (all confirmed)
- **In-repo claims, exact:** `USD_TO_RUB = 90` at `agent-runner.ts:30` (and
  duplicated in `budget.test.ts:7` — note: a constant change must update both, or
  the test masks the bug); poll `5_000ms × 120 = 10min` window; `limit=20` on the
  check route; `settleRun` uses one `sql.begin` (READ COMMITTED) at `db.ts:341`.
- **Double-debit is real, not hypothetical.** `agent-runner.ts:23-97`: when
  `AIAG_GATEWAY_KEY` is set the run hits the `:4000` gateway (which runs
  `aiag_settle_charge` against an org) *and* `settleRun` debits `tg_user_balances`.
  Two ledgers, one run. The fallback path hits only `tg_user_balances`. The report's
  "core incoherence" is verified.
- **External facts, all correct:** USDT master `EQCxE6mU…_sDs` + **6 decimals**;
  `transfer_notification` op **`0x7362d09c`**, TL-B `query_id/amount/sender/forward_payload`,
  and the critical caveat that the jetton wallet does **not** validate `forward_payload`
  (the receiver must); TonAPI **Streaming API is deprecated → Webhooks API** at
  `rt.tonapi.io`; the **fake-jetton defense** (`master.get_wallet_address(receiver)`
  must equal the notification's sender wallet) is documented *verbatim* as the report
  states it — this is the report's strongest section. `@hot-wallet/sdk` v1.0.11,
  `/adapter/ton`, 30M+ wallets, TON Connect-compatible: confirmed.

### Key issues

1. **"USDT credits 1:1, no FX risk" is half-true and the gap can lose money on the
   COGS side.** Credit-in is genuinely 1:1 (USDT≈USD). But the report anchors COGS
   to USD ("cost_micro_usd = tokens × price_usd, no FX") while the upstream is paid
   through the **gateway, which charges in ₽** via CBR. So the platform's *revenue*
   is USDT (≈USD-stable) but its *cost of goods* is ₽-denominated at the gateway.
   If USDT/USD de-pegs or the gateway's CBR rate moves between top-up and spend, the
   USD-anchored credit and the ₽-anchored COGS diverge — a margin/FX risk the report
   labels "no FX risk." The anchor choice is still correct; the claim "no FX at all
   on COGS" is wrong. **Fix:** state explicitly that the FX risk moves from the
   *credit* to the *margin*, and that the gateway-as-house-org path (Open Q1) must
   reconcile ₽-COGS against USD-revenue, or set the run markup wide enough to absorb
   peg/rate drift.

2. **The jetton top-up *init* recommendation is wrong as written (Part 4 step 5 /
   build-order 5).** It says build the invoice as a "TON Connect 'send' to the user's
   jetton wallet, carrying `forward_ton_amount > 0` and the comment in `forward_payload`."
   On TON the user does **not** send to *their own* jetton wallet — the TON Connect
   message targets the **sender's own jetton wallet contract** with an op-`0x0f8a7ea5`
   `transfer` body whose *destination* is `OUR_RECEIVER`, and `forward_ton_amount` must
   cover gas for the notification (the demo uses ~0.05–0.1 TON, not "> 0" which is too
   small to land the notification). Underfunding `forward_ton_amount` is itself a 5th
   loss mode: the transfer succeeds but **no `transfer_notification` is emitted**, so the
   watcher never credits — exactly the "lost tokens" failure the cited Medium article
   warns about. **Fix:** specify the `0x0f8a7ea5` transfer message shape and a concrete
   `forward_ton_amount` floor (≥ 0.05 TON), and add "insufficient forward_ton_amount" to
   the Part-3 loss-mode list.

3. **The reconciler-cron loss-mode coverage has a real hole the report glosses.** Loss
   mode 2 (tx scrolls past the window on a *shared busy receiver*) is "fixed" by
   paginating the full window — but on a high-traffic shared receiver, full-window
   pagination every 30–60s over 24h of history is O(deposits) per tick and will not scale,
   and TonCenter/TonAPI rate limits will throttle it. The report's own Open Q5 (per-user
   sub-wallets) is not a "later, at scale" nicety — it is the *actual* fix for loss mode 2
   and for the unauthenticated-comment weakness. **Fix:** track only `lt` (logical time)
   high-watermark per receiver and scan forward from it, not "all pending < 24h" each tick;
   and treat per-user derived deposit addresses as the real solution to comment-tag
   identity, not a deferred question.

4. **Migration risk is named but the procedure is unsafe.** The report says backfill
   ₽→micro-USD "at a snapshot CBR rate" with one `kind='migration'` row per user. On a
   **live** balance with prod migrations that are *manual and untracked*
   (`packages/database/CLAUDE.md`), a snapshot rate chosen at migration time silently
   re-prices every user's existing balance — a user who deposited at ₽/USD=80 gets
   re-valued at the migration-day rate. That is a real, possibly unfavorable, value
   change to live customer balances, not just an audit-trail concern. **Fix:** freeze
   top-ups during cutover, snapshot per-user at the *original deposit rate where known*
   (the ledger doesn't have history yet — so this migration must be one-way-conservative
   and announced), make it idempotent via a guard row, and dry-run the SUM-invariant
   check on a prod dump first.

### Minor / non-blocking
- Webhook spoofing is listed as a risk but the mitigation ("shared secret / validate
  source") is vague — TonAPI webhooks do not sign payloads, so the only real defense is
  the report's own "re-fetch the tx and trust on-chain" plus endpoint rate-limiting.
  State that the secret is *not* available; on-chain re-verification is the sole control.
- "Two independent indexers corroborating before credit" adds latency and a second
  failure mode (one indexer lags → never corroborates → stuck). For an MVP, one indexer
  (TonCenter) as authority + on-chain finality is enough; dual-source is a hardening step,
  not MVP-blocking. The report over-engineers this for a 2GB VPS.
- Open Q4 (withdrawals) is correctly flagged as scope-defining; worth elevating to a
  blocking decision because "deposit-only, non-refundable credits" has consumer-protection
  exposure for a foreign crypto entity that should be confirmed before launch, not after.

### Tightened recommendation
Adopt Option B + `tg_ledger_entries` + USD-micro anchor **as written** — that spine is
correct. Then: (a) reframe the FX claim as "FX risk moves from credit to margin" and make
the gateway-house-org ₽-COGS reconciliation a P0, not an open question; (b) correct the
jetton-init message to the `0x0f8a7ea5` transfer shape with `forward_ton_amount ≥ 0.05 TON`
and add underfunded-notification as loss mode #5; (c) make the reconciler `lt`-watermark
based and commit to per-user deposit addresses as the loss-mode-2 fix rather than deferring
it; (d) treat the live ₽→USD migration as a freeze-window, conservative, dry-run-first
operation, not a snapshot-rate backfill. Ship order otherwise stands: ledger+anchor first,
reconciler cron second, jetton third, webhook/HOT last.
