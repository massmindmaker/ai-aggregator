# R-02 — Hermes control-plane (no remote config API): how our backend programmatically configures & restarts a per-user Hermes

## Summary

The brief's premise was **partly wrong, and the correction is good news**. Hermes does NOT lack a remote config API. The "dashboard" (`hermes dashboard`, default `127.0.0.1:9119`) is a full **FastAPI control-plane with ~50 endpoints**, including writable ones for config, env, skills, MCP servers, cron, messaging channels, credentials, memory provider, and webhooks. The OpenAI-compatible **gateway/API server** (`hermes gateway`, default `127.0.0.1:8642`, Bearer `API_SERVER_KEY`) is the mostly-read runtime surface (chat/runs/sessions/jobs), as the brief said.

The real constraint is **authentication and binding**, not capability:
- The dashboard binds to loopback with **no auth by default**.
- When bound to a **non-loopback** host it engages an **OAuth gate via Nous Portal** (fail-closed: refuses to start without an auth provider) — you cannot point it at our own auth.
- `--insecure` keeps a legacy **single-process session-token** scheme: an **ephemeral** `secrets.token_urlsafe(32)` generated at startup, held in memory as `_SESSION_TOKEN`, injected into the served HTML, and required on every sensitive call via the `X-Hermes-Session-Token` header. It is **not persisted to disk**.

**Recommendation: hybrid of (a) + (b).** Co-locate our authed control-plane sidecar on each instance and have it talk to the dashboard API on `127.0.0.1:9119` for structured writes (config, skills, MCP, cron, messaging) — capturing the ephemeral session token at the moment WE launch the dashboard process (we are the parent, so the token is ours). Use **direct file writes** (`config.yaml`, `SOUL.md`, `.env`) as the fallback for anything the API doesn't cover (notably **SOUL.md/persona has no documented dashboard endpoint**) and for first-boot provisioning before the dashboard is up. **Do NOT fork Hermes (option c).** Restart/reload via the `hermes gateway restart` CLI; many model/compression keys hot-reload, but skill/tool/credential changes require a gateway restart.

For **template export/clone**: `hermes backup` (zip) and `hermes import` exist, AND `hermes profile export`/`import` (tar.gz) exist — this **refutes** our prior internal note that "no official export/import command exists in v0.15.2." But `backup` **includes secrets, sessions, and memory by default**, so it is unsafe as a public-template format as-is. We must build a **sanitizing exporter** that ships only `config.yaml` (provider names, not keys) + `SOUL.md` + skill bundles + cron definitions, with `.env`, `auth.json`, `memories/`, and `sessions/` stripped.

### F2 — Dashboard IS the writable config API (this is the core correction)

| Approve pairing | `POST` | `/api/pairing/approve` |

**Gap:** no documented endpoint to write **SOUL.md / persona**. Persona must be set by **file write** to `~/.hermes/SOUL.md` (slot #1 of system prompt; empty → built-in default). Source: [web-dashboard.md](https://hermes-agent.nousresearch.com/docs/user-guide/features/web-dashboard), [configuration.md](https://hermes-agent.nousresearch.com/docs/user-guide/configuration).

### F3 — Dashboard auth model (decisive for option a)

- **Loopback (default):** no auth. Anyone who can reach `127.0.0.1:9119` has full write access including reading `.env` secrets via `/api/env`.
- **Non-loopback bind without `--insecure`:** OAuth gate via Nous Portal. The bundled `plugins/dashboard_auth/nous` plugin is always installed/auto-loaded; **only Nous Research provider ships**; server exchanges code at `POST /api/oauth/token`, verifies JWT against Portal JWKS, sets `hermes_session_at` cookie. **Fail-closed:** "If the gate would engage but no `DashboardAuthProvider` is registered … `hermes dashboard` refuses to bind." There is **no static-bearer-token alternative** to OAuth on public binds.
- **`--insecure`:** keeps "single-process session-token behaviour — no OAuth dance." Token = `secrets.token_urlsafe(32)`, ephemeral per startup, in-memory `_SESSION_TOKEN`, injected into served HTML, presented via `X-Hermes-Session-Token` header, **not persisted to disk**.

**Implication:** We must never expose 9119 to the internet/LAN with OAuth (we don't control Nous Portal accounts per user) nor with `--insecure` on a shared host (no auth = secret exfiltration). The safe pattern is **dashboard stays on loopback inside each agent's isolation boundary**, and OUR authed sidecar — running inside the same boundary — is the only thing that talks to it.

Sources: [web-dashboard.md](https://hermes-agent.nousresearch.com/docs/user-guide/features/web-dashboard), [DeepWiki dashboard](https://deepwiki.com/nousresearch/hermes-agent/3.4-web-ui-dashboard), WebSearch summary of session-token internals.

### F4 — Token capture is trivial *if we are the parent process*

The token is undocumented for external retrieval and "not persisted to disk," which the docs frame as isolation. But our control-plane **launches** the dashboard, so we own it:
- Launch `hermes dashboard --no-open --insecure --host 127.0.0.1` ourselves and **scrape the served HTML once** (`GET /` → regex the injected `_SESSION_TOKEN`), then reuse it for all subsequent `X-Hermes-Session-Token` calls until restart.
- Or simpler and more robust: skip the dashboard for writes and **write files directly** (F5), reserving the dashboard for operations only the API does atomically (e.g. credential-pool, pairing).

This is why option (a) "proxy to 9119" works **only** when co-located with the agent and when we control the launch — not as a network proxy to a remote box.

### F5 — Config is file-based; writes + restart is fully viable (option b)

`~/.hermes/` layout: `config.yaml` (all non-secret settings), `.env` (secrets), `auth.json` (OAuth creds), `SOUL.md` (identity), `memories/MEMORY.md`, `memories/USER.md`, `skills/`, `cron/`, `sessions/`, `logs/`. `config.yaml` top-level keys: `model`, `agent`, `terminal`, `memory`, `skills`, `compression`, `auxiliary`, `display`, `web`, `browser`, `voice`, `approvals`, `delegation`.

- `hermes config set <key> <value>` auto-routes secrets→`.env`, rest→`config.yaml` (e.g. `hermes config set model anthropic/claude-opus-4`, `hermes config set terminal.backend docker`).
- **Hot-reload (no restart):** `model.context_length`, all `compression.*`, `auxiliary.*` provider settings — gateway rebuilds on cached-signature change.
- **Requires restart/reload:** API keys/credentials, **tool/skill config**, **terminal backend**. Reload via **`hermes gateway restart`** (`--all` for every profile). `hermes update` auto-restarts running gateways.

So "write files + restart" is a first-class, supported path. Source: [configuration.md](https://hermes-agent.nousresearch.com/docs/user-guide/configuration), [cli-commands.md](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/reference/cli-commands.md).

### F6 — Per-agent isolation is config-native (`terminal.backend`)

`terminal.backend` ∈ {`local` (no isolation), `docker` (namespaces, caps dropped), `ssh`, `modal` (ephemeral cloud VM), `daytona` (cloud container), `singularity`}. Profiles isolate via `hermes profile create <name>`: separate `config.yaml`/`.env`, Docker containers labeled `hermes-profile=<name>` invisible across profiles, profile-scoped orphan reaper. Each profile is an independent process instance. This means the founder's two infra options (bigger VPS + Docker sandbox; or on-demand Modal/Daytona) are both **selectable via one config key**, not a code change. Source: [configuration.md](https://hermes-agent.nousresearch.com/docs/user-guide/configuration).

### F7 — Backup/import & profile export EXIST (refutes prior internal note)

- `hermes backup [-o path] [-q|--quick] [-l label]` → **zip** of `config.yaml`, `.env` + auth data, **sessions/history**, installed skills, `SOUL.md`/`MEMORY.md`/`USER.md`. Excludes only SQLite WAL/shm sidecars, checkpoint cache, the codebase. `--quick` = config + credentials + cron + sessions.
- `hermes import <zip> [-f|--force]` → restores into Hermes home, overwriting. **"Stop the gateway before importing."**
- `hermes profile export <name> [-o FILE]` / `hermes profile import <archive> [--name NAME]` → **`.tar.gz`** profile archives.
- `hermes profile create <name> --clone` (config + .env) / `--clone-all` (all state incl. sessions).

This **refutes** line 94 of `2026-06-02-hermes-webui-landscape-and-tma-positioning.md` ("no single official export/import the whole agent command in v0.15.2"). Source: [cli-commands.md](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/reference/cli-commands.md).

### F8 — Backup is NOT a safe public-template format as-is

`hermes backup` and `--clone`/`--clone-all` **carry secrets and private data by default** (`.env`, `auth.json`, `memories/`, `sessions/`, possibly secrets embedded in skill scripts and MCP server definitions). For a **public template** we must strip:

| Must strip | Reason |
|---|---|
| `.env`, `auth.json` | all API keys, bot tokens, OAuth creds |
| `memories/MEMORY.md`, `memories/USER.md` | agent's accumulated knowledge + user profile |
| `sessions/`, response store | conversation history (contains PII + cost/billing data) |
| Inline tokens in `config.mcp_servers` entries | MCP servers can embed bearer tokens/URLs |
| Secrets hard-coded in `skills/*` scripts | skill scripts are arbitrary code — must be scanned |
| Private chat-IDs / file paths in `cron/` and `messaging` | leak deployment + identity |

A safe public template = `config.yaml` (provider/model **names** only, keys referenced as `${VAR}` placeholders) + `SOUL.md` + skill bundles (script-scanned) + cron definitions (scrubbed) + MCP server *definitions* (tokens stripped). This matches the product rule "share the settings, not the knowledge."

## Concrete recommendation

**Adopt a co-located authed sidecar + file-write hybrid (a+b). Reject the fork (c).**

1. **Provisioning model.** One Hermes **profile per user-agent**, isolated. On a bigger VPS use `terminal.backend: docker`; for on-demand scale use `modal`/`daytona`. Our **agent-control-plane sidecar** (extend `apps/agent-worker`) runs inside each agent's boundary and is the ONLY caller of that agent's `127.0.0.1:9119`/`:8642`.
2. **Configure via files first, API second.**
   - **First-boot / bulk:** write `config.yaml`, `SOUL.md` (persona — no API for it), seed `.env` with `AIAG_GATEWAY_KEY` and base URL `http://<our-gateway>:4000/v1` so AIAG-supplied models route through our gateway (markup/billing/white-label) and BYOK routes direct (commission 0). Then `hermes gateway start`.
   - **Live edits:** prefer the **dashboard API on loopback** for structured, atomic ops (skills toggle, MCP add/enable, cron, credential-pool, messaging channels), launching `hermes dashboard --no-open --insecure --host 127.0.0.1` ourselves and capturing `_SESSION_TOKEN` from the served HTML → `X-Hermes-Session-Token`. Fall back to direct `config.yaml` edits + `hermes gateway restart` for anything the API lacks (persona) or when the dashboard isn't running.
3. **Restart policy.** Use hot-reload for `model.*`/`compression.*`/`auxiliary.*`; call `hermes gateway restart` for skill/tool/credential/terminal-backend changes. Never assume a config write is live without checking the hot-reload list.
4. **Templates.** Build a **sanitizing exporter** (do not hand `hermes backup` zips to users): export the F8 whitelist. Build a matching **importer** that runs `hermes profile create <name> --clone` from a clean base profile, lays down the template's `config.yaml`/`SOUL.md`/skills/cron, then injects the new owner's `.env` (their keys or our gateway key). Use `hermes profile export/import` (.tar.gz) as the **internal** clone transport between our own instances; use the sanitized format for the **public** marketplace.

**Why not fork (c):** Hermes already exposes everything we need over loopback; the only missing piece (authed remote access) is solved by our sidecar, not by patching Hermes. Forking creates a permanent merge-conflict tax against a fast-moving MIT project (v0.15 "velocity release" cadence) for zero capability gain, and would fork the security model we'd then own.

## Risks

- **R1 — Loopback dashboard = root key to `.env`.** Anything that can reach `127.0.0.1:9119` reads every secret via `/api/env`. Per-agent isolation (Docker/Modal/Daytona profile boundary) is mandatory; a shared-host `local` backend with our `/srv/aiag/shared/.env` present is an exfiltration path (already flagged in the payment-explainer).
- **R2 — Ephemeral token / process coupling.** `_SESSION_TOKEN` dies on dashboard restart; our sidecar must re-capture after every restart and tolerate the dashboard being down (fall back to file writes). The token only works because we are the launching parent — this design breaks if the dashboard is ever started by something else.
- **R3 — OAuth dead-end for remote.** There is no way to put the dashboard behind OUR auth on a public bind (Nous-Portal-only, fail-closed). Any "remote config" must be our sidecar↔loopback, never the dashboard exposed directly. Rules out a naive "reverse-proxy 9119 with our JWT" shortcut.
- **R4 — Backup leaks by default.** Shipping `hermes backup`/`--clone-all` to a public marketplace would publish keys, chat history, and memory. The sanitizing exporter is a hard gate before any template-sharing feature ships.
- **R5 — Skill scripts are arbitrary code.** Public templates carry executable skill scripts and MCP definitions; needs secret-scanning + sandboxed execution, else templates become a malware/secret-leak vector.
- **R6 — Version drift.** Endpoint paths and the `--insecure` token scheme are from current `main` docs/DeepWiki, not byte-pinned to our installed build. v0.15 ships fast. Pin a version and re-verify `/api/*` paths + token header against the actual installed binary before writing integration code.
- **R7 — Restart races.** `hermes import` and credential changes require stopping the gateway; doing this on a live user agent mid-run drops sessions. Need a drain/restart protocol in the sidecar.

## Adversarial review

**Verdict: PARTLY holds up.** The central thesis is correct and survives scrutiny — the dashboard IS a writable FastAPI control-plane, the endpoint inventory is real (in fact larger than listed), file-write + `hermes gateway restart` is a first-class path, backup/export exist but leak secrets by default, and forking is correctly rejected. But the *mechanism* the recommendation hangs on (token capture) is unverified and probably wrong, the dashboard launch recipe is stale, and the cost model is missing — which together would mislead an implementer if taken as-is.

### What I verified as solid (no change needed)
- **F1/F2 endpoint inventory — confirmed and then some.** Current `web-dashboard.md` lists `PUT /api/config`, `PUT /api/env` (+ `DELETE`), `PUT /api/skills/toggle`, `POST /api/mcp/servers`, `PUT /api/mcp/servers/{name}/enabled`, `POST /api/cron/jobs` (+ pause/resume/trigger/PUT/DELETE), `POST /api/credentials/pool`, `POST /api/webhooks`, `POST /api/pairing/approve`, `PUT /api/messaging/platforms/{id}`, `PUT /api/memory/provider` — all real. Bonus surfaces the doc missed and should use: **`POST /api/gateway/start|stop|restart`** (restart over HTTP — no need to shell out to the CLI) and **`POST /api/ops/backup` / `POST /api/ops/import`** (backup/import over the API). Source: [web-dashboard.md](https://hermes-agent.nousresearch.com/docs/user-guide/features/web-dashboard).
- **F2 SOUL.md gap — confirmed.** No persona endpoint exists; file write to `SOUL.md` is the only path. Fallback design is correct.
- **F5/F7 CLI surface — confirmed.** `hermes gateway restart [--all]`, `hermes backup`, `hermes import`, `hermes profile export/import`, `hermes profile create --clone/--clone-all` all exist; full backup includes `.env`/auth/sessions by default (only WAL/codebase excluded). Source: [cli-commands.md](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/reference/cli-commands.md).
- **F6/F8/R4/R5 — confirmed.** `terminal.backend` isolation is config-native; "one container per profile" is the Nous-recommended production pattern; backup leaks by default, so the sanitizing exporter is a real hard gate.

### Issue 1 (material) — F4 / R2 / Open-Q1: the token-capture mechanism is fabricated detail
R-02 itself sources F4 to "WebSearch summary of session-token internals" and flags it unverified in Open Q1, yet the **recommendation (line 122) states it as fact**: "launching `hermes dashboard --no-open --insecure --host 127.0.0.1` ourselves and capturing `_SESSION_TOKEN` from the served HTML → `X-Hermes-Session-Token`." No current source corroborates an `_SESSION_TOKEN` injected into served HTML or an `X-Hermes-Session-Token` header. The actual current behavior (issue [#34202](https://github.com/NousResearch/hermes-agent/issues/34202), fixed in v0.15.1): on loopback `request.state.session` is **never set**, `GET /api/auth/me` returns 401 "by design," and the fix returns a null-session 200 — i.e. **loopback writable endpoints serve with no session at all.** There is no token to scrape. This does not break the recommendation — it *simplifies* it (the sidecar calls the loopback API directly, no capture, no re-capture-on-restart) — but R2's "re-capture after every restart / breaks if started by something else" and the parent-process coupling in F4 are solving a non-problem. Strike the token-capture machinery.

### Issue 2 (material) — F3 / line 122: stale `--insecure` semantics → wrong launch recipe
The auth model changed: `--insecure` is **no longer inferred from bind host**; it is now an explicit opt-in (`HERMES_DASHBOARD_INSECURE=1`, "bind host is bind host"), and it is specifically the **dangerous public-bind** switch ("exposes API keys on the network"). So the recommended command `hermes dashboard --insecure --host 127.0.0.1` is wrong on two counts: on loopback you must **not** pass `--insecure` (loopback is already auth-off), and pairing `--insecure` with a recipe is exactly the footgun R1 warns against. R6 flags drift abstractly, but the recommendation hard-codes the stale flag. Pin to the installed build and drop `--insecure` from the loopback recipe.

### Issue 3 (material) — missing cost/feasibility model; isolation is the dominant cost, not "one config key"
R-02 frames infra as "selectable via one config key … not a code change," which hides the real scaling constraint. Measured footprint: chat-only ~300–600 MB; **with browser harness 1.2–1.8 GB**; and `terminal.backend: docker` (the doc's recommended default isolation) adds **1–2 GB** for container spin-up. Community-consensus floor is 4 GB RAM and ~1 GB per concurrent active container. So:
- The founder's "bigger VPS + Docker sandbox" option realistically caps at **single-digit concurrent agents on a 4 GB box** — fine for R0/R1 pilot, not for a marketplace.
- R-02 simultaneously recommends **process isolation per agent** (R1: Docker/Modal/Daytona profile boundary) **and** `terminal.backend: docker` as the default — that is Docker-in-Docker / nested isolation, compounding RAM and adding privileged-container or DinD complexity it never mentions. Pick one isolation layer per tier.
- Conclusion: Modal/Daytona ("ephemeral cloud VM," pay-per-run, zero idle cost) should be the **default for any concurrency beyond a handful**, not the "on-demand scale" afterthought. The economics flip: 10 idle Docker profiles waste 3–6 GB of paid VPS; 10 idle Modal profiles cost ~$0.

### Minor / unresolved
- **Open-Q3 answered:** dashboard and gateway are **separate processes** (`hermes dashboard` needs `pip install hermes-agent[web]`; distinct from `hermes gateway`). So `hermes gateway restart` does **not** kill the dashboard — good for supervision topology; update Open-Q3 from "unverified" to resolved.
- **Open-Q5 (per-profile ports):** still unanswered in docs — you must manage `--port` assignment yourselves; treat as an implementation TODO, not a blocker.
- **R3 still correct and important:** there is genuinely no way to put OUR auth on a public dashboard bind (Nous-Portal-only OAuth, or the dangerous `HERMES_DASHBOARD_INSECURE=1`). Sidecar↔loopback remains the only safe pattern. This is the strongest part of the analysis.
- **No security hole introduced by the recommendation itself**, provided the loopback dashboard truly never leaves the per-agent isolation boundary (R1). The one new risk the doc understates: with loopback auth-off, **any code running inside the agent's own sandbox — including a user-supplied skill script or MCP server (R5) — can read every secret via `GET /api/env`.** Public-template skill scripts + loopback `/api/env` is a direct key-exfiltration chain. The sandbox boundary must also constrain the agent's own tools' egress, not just isolate agents from each other.

### Tightened recommendation
Keep (a)+(b) hybrid; reject the fork — that conclusion is sound. Adjust:
1. **Sidecar talks to the loopback dashboard API directly — no token capture.** Drop the `_SESSION_TOKEN`/HTML-scrape design (F4) and the re-capture-on-restart logic (R2). Use HTTP `POST /api/gateway/restart` instead of shelling out to the CLI.
2. **Fix the launch recipe:** `hermes dashboard --no-open --host 127.0.0.1` (NO `--insecure`). Never set `HERMES_DASHBOARD_INSECURE=1`. Pin the installed Hermes version and re-verify `/api/*` paths + the loopback no-session behavior against the actual binary before writing integration code.
3. **Make isolation tier explicit and budgeted:** `terminal.backend: local` *inside* a per-agent container (do not nest Docker-in-Docker) for the VPS tier; **Modal/Daytona as the default for marketplace-scale concurrency.** Budget ~1.5 GB/active agent with browser tools; size the VPS tier for a hard, small concurrent cap and document it.
4. **Treat the agent's own tools as untrusted w.r.t. secrets:** since loopback `/api/env` is unauthenticated, restrict what `.env` holds inside a user agent's boundary (only that agent's own gateway key, never `/srv/aiag/shared/.env`) and constrain skill/MCP egress.
5. Sanitizing exporter (F8) unchanged — still a hard gate.
