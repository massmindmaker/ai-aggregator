## R19 — MCP-серверы по OAuth

**Один вывод:** OAuth-подключение MCP — это просто несколько HTTPS-вызовов плюс наша HTTPS-страница-callback под `/tg`; воркер остаётся stateless (он и так подключается per-run), Hermes не нужен — настоящая работа не в OAuth, а в «выходе» из вебвью Telegram в системный браузер и возврате обратно.

**Вердикт:** **строится сейчас** (тонкий v1: только authorization-code + PKCE, одна таблица токенов, ленивый refresh в воркере).

**Следующий шаг:** заложить таблицу `agent_mcp_oauth` (миграция через `sudo -u postgres psql` по рецепту деплоя) + один callback-роут под `/tg`; начать с самого узкого: серверы с RFC 9728-метаданными и либо DCR, либо вручную вставленным `client_id`. По правилу комиссии — это «свой провайдер», поэтому **0 кредитов**.

## R20 — Agent-to-Agent (A2A / ERC-8004 / AP2 / x402)

**Один вывод:** четыре стандарта дополняют друг друга (найти → доверять → авторизовать → оплатить) и **не заменяют наш кредитный леджер** — они «прицепляются» к его краям; нам не нужен горячий крипто-кошелёк на каждого агента.

**Вердикт:** **строится сейчас** — но только один тонкий ломоть: внутренний A2A как чистый перевод кредитов (один наш агент нанимает другого, автор получает кредиты, ноль крипты). Внешний A2A через x402 — **нужна инфра** (едет на уже запланированном v2 tool-broker). ERC-8004 идентичность/репутация и полные AP2-мандаты — **далёкое будущее** (R&D за иностранным юрлицом).

**Следующий шаг:** обобщить в плане v2-брокера понятие «инструмент» до «платной внешней способности» = {x402-инструмент | внутренний агент | внешний A2A-агент} с единым путём списания; сначала отгрузить **внутренний наём агента агентом** на существующем леджере (усиливает author-rent, без крипты).

## R21 — Исполняемые SKILL-скрипты (`scripts/`)

**Один вывод:** скилл-скрипты исполняются просто через `bash` (вывод → в контекст, код — нет); вся безопасность — это ГДЕ запускается bash; на нашем 2 ГБ prod-боксе с живым money-path запускать чужой код **нельзя никогда** (общий kernel с секретами).

**Вердикт:** **строится сейчас** — но только безопасное подмножество: (A) декларативные «скрипты» = упорядоченный рецепт из наших уже-провеоренных встроенных инструментов + read-only MCP (данные, не код), (B) делегировать реальные `scripts/` собственному Hermes пользователя (его машина, его доверие, BYO = 0 комиссии). Общий случай (произвольный авторский код для любого юзера) — **нужна инфра** (отдельный безсетевой одноразовый хост с gVisor → Firecracker, тот же, что для eval-runner из R-14).

**Следующий шаг:** отгрузить Subset A (replay-рецепты через существующий `executeTool`) + Subset B (BYO-Hermes) под лейблом `live`; общий `scripts/` держать под `R&D`/«скоро» до появления отдельного gVisor-хоста.

## Итоговая сводка (для основателя)

Из трёх ресёрчей **на текущей инфре сейчас (без Hermes, без нового сэндбокса) реально строятся все три — но каждый только в тонком, честном v1-ломте**: R19 даёт полноценный OAuth-MCP (несколько HTTPS-вызовов + один callback-роут под `/tg` + одна таблица токенов), R20 даёт внутренний наём «агент-нанимает-агента» как чистый перевод кредитов (ноль крипты, усиливает author-rent), а R21 даёт декларативные tool-рецепты и исполнение скриптов на собственном Hermes пользователя. Всё крипто-расчётное (внешний A2A/x402, ERC-8004, AP2) и произвольное исполнение чужого кода требуют либо запланированного v2-брокера, либо отдельного изолированного хоста — и корректно остаются R&D. **Главная рекомендация: первым отгрузить внутренний A2A (наём агента агентом через кредитный леджер)** — он не требует ни OAuth-возни с вебвью, ни сэндбокса, прямо усиливает монетизацию author-rent и полностью вписывается в существующий план; R19 (OAuth-MCP) — сильный второй, как самостоятельная фича без денежных рисков.
