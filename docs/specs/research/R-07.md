# R-07 — Real agent runtime (beyond the stateless loop)

> Research item: evolve `apps/agent-worker/src/agent-runner.ts` (today a stateless
> BullMQ→gateway loop) into a real multi-step agent with memory, real streaming, and
> per-call observability — **without breaking the live money path**.
> Author: staff-eng research pass · Date: 2026-06-03 · Status: recommendation

---

## Summary

The current runtime (`agent-runner.ts`) is already a competent **multi-step tool loop**
(up to `MAX_ITERATIONS = 12`, OpenAI tool-calling, a real `memory` tool backed by the
`agent_memory` KV table). What it lacks is: (1) **semantic / long-term memory** (it only
replays the last 10 completed runs verbatim + a flat KV store with no recall); (2) **real
streaming** — the TMA WebApp `setInterval(load, 1500)` polls `agent_runs` every 1.5 s and
the Telegram bot posts one final message at the end; (3) **observability** — there is zero
per-call tracing; cost is a hand-rolled `PRICING` table estimate.

**Recommendation in one line:** do **not** rip out the loop. Layer in three independent,
low-risk pieces that each preserve the `isExternal`/`settleRun` money path:

1. **Memory** → add **pgvector to our existing Postgres** + a thin semantic-recall layer.
   Adopt **Mastra's `@mastra/memory` + `@mastra/pg`** *only if* we also move the loop onto
   the Vercel AI SDK; otherwise ship a ~150-line homegrown recall on top of `agent_memory`.
2. **Streaming** → adopt the **Vercel AI SDK (`ai` + `@ai-sdk/openai-compatible`)**
   `streamText` pointed at our `:4000` gateway via a custom `baseURL`, surfaced to the TMA
   as **SSE** (replacing the poll) and to Telegram via **throttled `editMessageText`**
   (or `sendMessageDraft`, Bot API 9.3+).
3. **Observability** → **OpenTelemetry** spans (the AI SDK emits them natively via
   `experimental_telemetry`) exported to a lightweight backend. **Helicone self-host is
   ruled out by the 2 GB VPS** (it needs ClickHouse + Postgres + MinIO). Use Helicone
   **Cloud** as a zero-infra proxy *or* OTel→**Grafana Cloud free tier**; SigNoz self-host
   only if a second box appears.

The single hard constraint that decides most of this is the **2 GB single VPS** and the
**load-bearing `settleRun` atomicity**. Every option below is filtered through "does it run
in <150 MB extra RAM and does it keep markup/debit correct for AIAG-supplied models while
charging ZERO for BYOK/external".

## Key findings (with sources)

### 1. Current runtime — what we actually have (code-grounded)

- `apps/agent-worker/src/agent-runner.ts:319` — already a `for (i < MAX_ITERATIONS=12)`
  tool-calling loop; appends `tool_calls`/`tool` messages and re-calls the model. This is a
  *bounded ReAct loop*, not a single shot. So "beyond the stateless loop" means **memory +
  streaming + traces**, not "add a loop".
- `apps/agent-worker/src/db.ts:205-243` — `agent_memory (agent_id, key, value)` KV table +
  `memorySet/Get/List`, exposed as the `memory` tool (`tools.ts:288`). Memory exists but is
  **flat KV with no semantic recall and no embeddings**.
- `apps/agent-worker/src/agent-runner.ts:305` — "history" = `loadHistory(agent.id, runId, 10)`:
  last 10 *completed* runs replayed verbatim into `messages[]`. No summarization, no recall,
  no per-conversation thread; it will blow the context window as runs accumulate.
- **Money path (do not break):** `resolveUpstream` (`agent-runner.ts:42`) sets
  `isExternal`; `settleRun` (`db.ts:328-376`) does `markCompleted` + guarded daily-spend
  `UPDATE … WHERE spent_today+cost<=budget RETURNING` + guarded balance debit, all inside
  one `sql.begin` (READ COMMITTED). `if (isExternal) return` short-circuits both the debit
  and the daily guard — BYOK/external = **ZERO charge** (`/SECURITY.md`, `agent-worker/CLAUDE.md`).
- **Streaming surfaces today:** TMA WebApp polls every 1.5 s
  (`apps/tg-miniapp/app/agents/[id]/page.tsx:139-144`); the bot sends a single
  `buildRunCompletedMessage` at the end (`bot-api.ts`). Both are *terminal*, not streaming.
- **Latent bug to fix regardless:** `DEFAULT_MODEL = 'nousresearch/hermes-4-405b'` is **not**
  in the `:4000` gateway registry (`agent-worker/CLAUDE.md`) → 400 "Unknown model". Any
  real-runtime work should fix/register the default first.
- Worker deps are tiny today: `bullmq`, `ioredis`, `postgres` only
  (`agent-worker/package.json`). Anything we add lands on a 2 GB box that also runs web,
  gateway, tma, Postgres, Redis.

### 2. Mastra — memory & multi-step (mastra-ai/mastra)

- **License Apache-2.0** for core (enterprise `ee/` dirs are source-available); hit **1.0
  stable in Jan 2026**, `@mastra/core` ~1.37 by May 2026; production users incl. Replit,
  PayPal, Sanity ([GitHub](https://github.com/mastra-ai/mastra),
  [generative.inc guide](https://www.generative.inc/mastra-ai-the-complete-guide-to-the-typescript-agent-framework-2026)).
- **Runtime fit:** runs on **any Node runtime including Bun and Deno**, and can be **embedded
  into an existing server via adapters** — Mastra Cloud is optional. So it can live *inside*
  the agent-worker; we are not forced to run the Mastra dev server
  ([mastra.ai/ai-agent-framework](https://mastra.ai/ai-agent-framework)).
- **Memory model** = 3 layers: **message history**, **semantic recall** (embeddings over past
  messages, `topK`/`messageRange`), **working memory** (structured persistent user facts);
  plus "observational memory" that compresses old messages
  ([Memory overview](https://mastra.ai/docs/memory/overview),
  [Memory class ref](https://mastra.ai/reference/memory/memory-class)).
- **Postgres/pgvector:** package **`@mastra/pg`** with **`PostgresStore`** (message store) +
  **`PgVector`** (vector store via the pgvector extension). Connection via
  `connectionString` or host/port; supports **HNSW** and **IVFFlat** indexes
  ([@mastra/pg npm](https://www.npmjs.com/package/@mastra/pg),
  [PG vector ref](https://mastra.ai/reference/vectors/pg)). **It can target our existing
  Postgres** — no new DB.
- **Semantic recall requires an embedder** (e.g. `openai/text-embedding-3-small`); it is
  *mandatory*, not optional ([Memory class ref](https://mastra.ai/reference/memory/memory-class)).
  We would route that embedding call through our `:4000` gateway too (so it is billed/markup'd
  consistently) — embeddings are cheap (~$0.02 / 1M tokens).
- **Mastra is built on the Vercel AI SDK**: its model router wraps AI-SDK providers, so
  streaming, tool loop (`maxSteps`), and OTel come "for free" from the SDK layer. This is the
  decisive point: **adopting Mastra ≈ adopting the AI SDK plus a memory/agent abstraction on
  top.** Adopting the AI SDK alone is the smaller blast radius.

### 3. Vercel AI SDK — streaming + custom gateway + OTel (vercel/ai)

- **Custom gateway routing:** `createOpenAICompatible` from **`@ai-sdk/openai-compatible`**
  takes `{ name, apiKey, baseURL, headers }` and works with `streamText`/`generateText`,
  tool-calling and model switching — **i.e. we point `baseURL` at `http://127.0.0.1:4000/v1`
  and keep the white-label + markup path intact**
  ([vercel/ai discussion #4070](https://github.com/vercel/ai/discussions/4070),
  [openai-compat docs](https://vercel.com/docs/ai-gateway/sdks-and-apis/openai-compat)).
  This is the cleanest way to gain streaming *without* changing where money is made.
- **Streaming:** `streamText` yields `textStream` (token deltas) + a final `usage` promise
  → we drive both SSE-to-TMA and throttled bot edits, and still call `settleRun` once at the
  end with the **real** `usage.completion_tokens` (more accurate than today's `PRICING`
  estimate) ([AI SDK Core](https://ai-sdk.dev/docs/ai-sdk-core/telemetry)).
- **Observability is native:** set `experimental_telemetry: { isEnabled: true }` on a
  `streamText`/`generateText` call → SDK emits **OpenTelemetry spans** with prompt, response,
  token counts, latency, tool calls. Uses the **global OTel tracer**, so for a Hono/Bun/Node
  worker you just init an OTel SDK (or `@pydantic/logfire-node`) and spans flow to any OTLP
  backend — SigNoz, Grafana, Langfuse — with **no instrumentation-code change** when you
  switch backends ([AI SDK telemetry](https://ai-sdk.dev/docs/ai-sdk-core/telemetry),
  [SigNoz Vercel AI SDK](https://signoz.io/blog/opentelemetry-vercel-ai-sdk/),
  [Langfuse AI SDK](https://langfuse.com/integrations/frameworks/vercel-ai-sdk)).

### 4. Streaming into Telegram — the surface-specific reality

- **Two surfaces, two mechanisms.** The TMA **WebApp** (Next page) is a normal browser
  context → use **SSE** from a Next route reading the worker's token stream (replace the
  `setInterval` poll). The **bot message** path needs Telegram's API.
- **Telegram edit limits:** `editMessageText` shares a **~20 edits/sec** bucket (separate
  from send). Best practice = send one message on first tokens, then **throttle edits to
  ~1/sec or every ~50 tokens**, with a final clean edit
  ([tdlib #3034](https://github.com/tdlib/td/issues/3034),
  [gramio rate-limits](https://gramio.dev/rate-limits)).
- **New primitive:** **`sendMessageDraft`** (Bot API **9.3**, Dec 2025; GA for all bots in
  9.5, Mar 2026) is purpose-built for partial streaming and avoids edit-bucket abuse —
  prefer it if our bot stack exposes 9.5 ([openclaw #32180](https://github.com/openclaw/openclaw/issues/32180)).
- **Verdict:** real streaming is highest-value on the **TMA WebApp (SSE)**; bot streaming is
  a nice-to-have gated on edit throttling / Bot API version.

### 5. Observability — Helicone vs OTel→SigNoz, filtered by the 2 GB VPS

- **Helicone self-host is a non-starter here.** Its stack = **ClickHouse + Postgres + MinIO**;
  ClickHouse alone wants **≥4 cores / 8 GB RAM** for basic workloads. On a single 2 GB box
  already running Postgres+Redis+4 Node apps this is impossible
  ([Helicone self-host docker](https://docs.helicone.ai/getting-started/self-host/docker),
  [Helicone self-host journey](https://www.helicone.ai/blog/self-hosting-journey)).
- **Helicone Cloud** (proxy, one-line `baseURL` swap, 300+ model pricing DB) is viable and
  zero-infra, BUT it would sit **in front of** or **behind** our `:4000` gateway — adding a
  hop and sending prompts to a third party. Acceptable for *internal debugging only*, and it
  competes conceptually with our own white-label gateway. **Not recommended as the primary
  path** ([Helicone guide](https://www.helicone.ai/blog/the-complete-guide-to-LLM-observability-platforms)).
- **OTel is vendor-neutral and free-tier-friendly.** The AI SDK already emits OTel; ship spans
  to **Grafana Cloud free tier** or **Langfuse** (self-host or free cloud) with no code lock-in;
  **SigNoz self-host** is the "own everything" option but, like any OTel backend with
  ClickHouse, needs its **own box** — not the 2 GB prod VPS
  ([SigNoz LLM tools](https://signoz.io/comparisons/llm-observability-tools/)).
- **Cheapest correct first step:** since `settleRun` already records `cost_rub/tokens_in/out`
  per run in `agent_runs`, our **cost ledger already exists in Postgres**. Observability's job
  is *latency + failure + step traces*, which a thin OTel exporter to a free hosted backend
  covers without new infra.

## Concrete recommendation

**Stack (in dependency order, all Apache-2.0 / MIT, all run inside the existing worker):**

| Concern | Pick | Why |
|---|---|---|
| Model calls + multi-step + streaming | **`ai` + `@ai-sdk/openai-compatible`** (`baseURL=:4000`) | Streaming + native OTel; keeps gateway/markup/white-label; real `usage` for billing |
| Long-term memory | **pgvector in our Postgres** + recall layer | No new DB; reuses `agent_memory`; ~150 MB RAM ceiling respected |
| Memory framework | **Mastra `@mastra/memory`+`@mastra/pg`** *(optional, phase 3)* | Working memory + semantic recall + summarization out of the box; only worth it once on AI SDK |
| Traces | **OTel spans → Grafana Cloud free / Langfuse** | Vendor-neutral, free tier, no ClickHouse on the 2 GB box |
| Cost | **keep `settleRun` ledger as source of truth** | Already atomic and live; OTel is for latency/traces, not money |

**Explicitly NOT chosen:** Helicone self-host (8 GB ClickHouse — impossible on 2 GB);
SigNoz self-host on prod box (needs its own node); ripping out the existing loop.

### Integration plan (4 phases, money path preserved at every step)

**Phase 0 — pre-req (1 PR).** Fix the `DEFAULT_MODEL` registry bug (register
`nousresearch/hermes-4-405b` in `:4000` or change default to a registered slug). Apply
migration: `CREATE EXTENSION IF NOT EXISTS vector;` + a `agent_memory_vectors` table
(`agent_id, run_id, content, embedding vector(1536), created_at`) with an HNSW index. This
is additive — no behavior change.

**Phase 1 — AI SDK swap (loop-internal, money path untouched).** Replace the hand-rolled
`callWithFallback`/`postChat` with `streamText({ model: openaiCompatible(...), messages,
tools, maxSteps: 12 })` where the provider's `baseURL = http://127.0.0.1:4000/v1` and
`apiKey = AIAG_GATEWAY_KEY`. **Keep `resolveUpstream` exactly as-is** to choose
gateway vs external vs provider_id and to set `isExternal`; the AI SDK provider is just
constructed from that result. At stream end, read `usage` and call the **unchanged**
`settleRun(...)` with `isExternal` and real token counts. The gateway→OpenRouter 404
fallback survives as a custom `fetch` on the provider. *Net: same money path, real `usage`,
streaming now available.* Cover with the existing `__tests__/run-settle.integration.test.ts`
plus a streaming-usage test.

**Phase 2 — real streaming to the user.** (a) TMA WebApp: add an SSE Next route under
`/tg/api/tma/agents/[id]/stream` that relays the worker's `textStream`; replace
`setInterval(load,1500)` with an `EventSource`. (b) Bot: throttled `editMessageText`
(~1/sec) or `sendMessageDraft` if Bot API ≥9.5. Both are display-only — they do **not**
touch settlement, which still fires once at completion.

**Phase 3 — memory upgrade (the actual "real agent" part).** Two options:
- **3a (lean, recommended first):** homegrown semantic recall — embed each completed run's
  input+output via the gateway embedding model, store in `agent_memory_vectors`, and on each
  run inject top-K relevant past snippets instead of the blind last-10 replay. ~150 lines,
  zero framework, full control of the money path.
- **3b (framework):** adopt **Mastra `@mastra/memory` + `@mastra/pg`** pointed at our
  Postgres, with its model router configured for our `:4000` gateway via the AI SDK
  openai-compatible provider. Gains working-memory + summarization + threads, at the cost of
  a larger dep tree and re-asserting the `isExternal`/`settleRun` invariants around Mastra's
  generate call. Do this **only after** 3a proves recall value and only if we want managed
  working-memory without writing it.

**Phase 4 — observability.** Init a minimal OTel Node SDK in the worker; turn on
`experimental_telemetry` on the `streamText` calls; export OTLP to Grafana Cloud free tier
(or Langfuse). Dashboards: per-run latency, step count, tool-call failures, model-not-found
fallbacks. Keep `agent_runs` as the cost ledger.

## Risks

- **Money-path regression is the top risk.** The AI SDK swap (Phase 1) must keep
  `resolveUpstream`→`isExternal`→`settleRun` byte-for-byte semantically identical. Mitigation:
  Phase 1 changes only *how the HTTP call is made*, not *who is billed*; gate the merge on the
  existing `run-settle.integration.test.ts` staying green + a new test asserting `isExternal`
  external runs still debit ZERO.
- **Token accounting drift.** AI SDK `usage` may differ from the current `PRICING` estimate.
  This is actually a *fix* (real counts), but it changes charged amounts — flag to founder,
  and keep `estimateCostRub` as a fallback when `usage` is absent (some providers omit it on
  stream).
- **2 GB RAM ceiling.** AI SDK + pgvector is fine (~tens of MB). **Mastra's full dep tree is
  the watch item** — measure RSS before/after Phase 3b; if it pushes the worker past budget,
  stay on 3a. pgvector index build on a big `agent_memory_vectors` also costs RAM — use HNSW
  with conservative `m`/`efConstruction` and cap rows per agent.
- **Helicone temptation.** Self-host will look attractive in docs but is physically impossible
  on the prod box; don't let it onto the roadmap without a dedicated node.
- **Telegram edit bans.** Unthrottled `editMessageText` streaming will hit the 20/sec bucket
  and get the bot rate-limited. Throttle hard or use `sendMessageDraft`.
- **Streaming + BullMQ semantics.** A streamed run still completes as one job; ensure a
  dropped SSE/bot connection does not abort settlement (settle on stream-finish server-side,
  independent of the client connection).
- **pgvector load on shared Postgres.** Embedding queries compete with the live money-path
  queries on the same instance. Keep recall `topK` small and index tight.

## Open questions

- **Threads vs runs.** Memory recall wants a conversation/thread id; today everything keys off
  `agent_id` + per-run rows. Do we introduce a `thread_id` (per user-agent conversation), or
  keep recall scoped to `agent_id`? Affects both 3a and Mastra's schema.
- **Embedding provider.** Route embeddings through `:4000` (consistent billing/white-label) or
  call OpenRouter/OpenAI directly? Routing through the gateway is preferred but the gateway
  must register an embedding model.
- **Does BYOK/external get memory + streaming too?** Memory and streaming cost *us* compute
  and (for embeddings) tokens. For `isExternal` runs we charge ZERO for the model — do we also
  eat embedding cost for their memory, or gate semantic recall behind AIAG-supplied runs?
- **Bot API version on prod** — is the grammY/bot stack on ≥9.5 so `sendMessageDraft` is
  available, or are we stuck on throttled `editMessageText`?
- **Mastra vs homegrown final call.** If 3a (homegrown recall) already delivers the product
  feel, is the Mastra dependency ever worth its footprint on a 2 GB box, or is it only for a
  future multi-node deployment? Decide after Phase 3a metrics.
- **Where does "managed Hermes" fit?** This plan upgrades the *stateless loop*; it does not
  itself stand up a managed Hermes runtime (still R&D). Confirm this is the intended scope.

## Adversarial review

**Date:** 2026-06-03 · Reviewer: adversarial verification pass · **Verdict: PARTLY holds up.**

The architecture is sound and the big external facts check out — but the report has **one
billing-correctness hole that, if implemented as written, would charge real AIAG runs ₽0**,
plus a RAM claim that's wrong at the index-build step and a bot-streaming plan aimed at the
wrong process. The direction (layer, don't rip out; AI SDK + pgvector + OTel free-tier;
no Helicone self-host) survives. The Phase-1 details do not, as written.

### What I verified and confirms (the report is right here)
- **Code grounding is accurate.** `agent-runner.ts` is a real bounded ReAct loop
  (`MAX_ITERATIONS=12`), `resolveUpstream`→`isExternal`→`settleRun` is exactly as described,
  history is a blind last-10 replay (`loadHistory(agent.id, runId, 10)`), and the
  `DEFAULT_MODEL = 'nousresearch/hermes-4-405b'` registry bug is real (confirmed in
  `agent-worker/CLAUDE.md`). Phase 0 is correctly the prerequisite.
- **Helicone self-host = non-starter on 2 GB: CONFIRMED.** ClickHouse wants ≥4 cores / 8 GB
  for non-trivial workloads; runs "as low as 2 GB" only with heavy tuning and low ingest —
  impossible alongside Postgres+Redis+4 Node apps. Ruling it out is correct.
- **`sendMessageDraft`: CONFIRMED against the authoritative source.** Telegram's official
  Bot API changelog: *"Added the method sendMessageDraft, allowing partial messages to be
  streamed"* — **Bot API 9.3, 2025-12-31**; GA 9.5 (2026-03-01). (Drop the `openclaw/*`
  citations — those repos are low-quality SEO/AI-spam; cite `core.telegram.org/bots/api-changelog`.)
- **Mastra: CONFIRMED.** Apache-2.0, 1.0 stable Jan 2026, `@mastra/pg` ships `PgVector`
  (pgvector) + `PostgresStore`, production users real. The "AI SDK alone is the smaller blast
  radius" call is the right one.
- **AI SDK OTel: CONFIRMED.** `experimental_telemetry: { isEnabled: true }` emits spans with
  `ai.usage.{prompt,completion}Tokens` + `gen_ai.usage.{input,output}_tokens`, exportable to
  any OTLP backend. Vendor-neutrality claim holds.

### Key issues (where it does NOT hold up)

1. **CRITICAL — streaming silently zeroes the bill unless usage is force-enabled.** Phase 1
   says "real `usage` for billing." But an OpenAI-compatible **stream** returns `usage: null`
   on every chunk **unless `stream_options: { include_usage: true }` is set** — then usage
   arrives only in a *trailing chunk after `finish_reason`*. If the AI SDK / our gateway stops
   the stream before that chunk (a known, documented failure — see LiteLLM #16112, #11004),
   `usage` is absent → today's code path computes `tokensOut = 0` → `estimateCostRub(...) = 0`
   → a billable AIAG run settles at **₽0**. The report files this only as soft "Risk #2
   (token drift)." It is not drift; it is a **revenue leak and a money-path regression**, the
   exact thing Phase 1 swears to preserve. The current non-streaming `callWithFallback` does
   not have this problem.
   - Our primary money path is the **`:4000` LiteLLM gateway**, and LiteLLM's *streaming*
     usage is the documented-buggy surface, not OpenRouter's. OpenRouter now auto-includes
     usage in the final SSE chunk (and *deprecated* `include_usage`), so the **fallback** path
     is fine — but the **primary** path's streaming-usage fidelity is **untested by this plan**.
     "Real usage > PRICING estimate" is therefore unproven; a streaming gateway can hand back
     *estimated* counts, which may be **worse** than the current conservative `PRICING` table.

2. **WRONG — "pgvector ~tens of MB / ~150 MB ceiling respected" conflates query RAM with
   build RAM.** HNSW **index build** consumes `maintenance_work_mem`; Postgres default is
   64 MB and below the graph size it silently falls back to a **10–50× slower disk build**,
   and for good query latency the index wants to be **resident**. On a box already running
   Postgres+Redis+4 Node apps, an unbounded `agent_memory_vectors` HNSW is a latent OOM/IO
   risk that competes with the **live money-path queries on the same instance** (the report's
   own Risk list admits this but the recommendation table asserts the ceiling "respected"
   unconditionally — contradiction).

3. **Bot streaming targets the wrong process.** `agent-worker/src/bot-api.ts` is a **raw
   `fetch` wrapper that only sends terminal DM notifications** — there is **no grammY**, and
   the conversational bot is a *separate* Next webhook app. So (a) the open question "is the
   bot stack ≥9.5?" is moot (no library gate; `sendMessageDraft` is just one more `fetch`),
   and (b) "relay the worker's `textStream` to the bot" means the **worker** must run a
   long-lived per-token edit/draft loop or push deltas cross-process — neither is designed.
   This makes bot streaming materially harder than the report implies. The report's own
   "TMA-SSE is the high-value surface, bot is nice-to-have" verdict is correct — lean into it
   and **defer bot streaming entirely.**

4. **AI SDK tool-loop ≠ free re-bill.** Phase 1 maps the loop to `streamText({ maxSteps: 12 })`.
   But today the loop also accumulates **tool cost** (`exec.cost_rub`) and enforces **mid-run
   monthly+daily cutoffs between iterations**. The AI SDK's internal multi-step loop hides
   those iteration boundaries, so the per-step budget guard and tool-cost accrual must be
   re-implemented via `onStepFinish`/`prepareStep` or kept as an outer manual loop. "Just set
   `maxSteps: 12`" silently drops the mid-run budget enforcement. Not mentioned.

5. **Minor:** AI SDK telemetry has open gaps for some call types (vercel/ai #12801: missing
   usage attributes on certain spans) — don't make the **cost ledger** depend on OTel spans
   (the report is right that `agent_runs` stays the ledger; just keep it firm).

### Tightened recommendation
Keep the layering thesis, the stack picks (AI SDK + pgvector + OTel→free tier), and the
