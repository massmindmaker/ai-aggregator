# R-09 — MCP gateway (OAuth 2.1)

> Research item from the AIAG TMA product backlog. Author: staff-eng research pass, 2026-06-03.
> Scope: design AIAG's MCP integration — a Hono MCP gateway (Streamable-HTTP, per-agent bearer) using
> `@modelcontextprotocol/typescript-sdk`, optionally `IBM/mcp-context-forge` as a registry, with
> OAuth 2.1 + PKCE + RFC 8707 for third-party MCP servers; first-party MCP skips OAuth. Recommend
> architecture + token storage/encryption.

---

## Summary

AIAG should ship MCP in **two layers that the spec keeps separate, and we should keep separate too**:

1. **Inbound (AIAG-as-MCP-server):** an MCP *resource server* that exposes AIAG's own tools
   (`web_search`, `image_gen`, `calc`, `memory` from `apps/agent-worker/src/tools.ts`) over
   **Streamable-HTTP** to external MCP clients (Claude Desktop, Cursor, other agents). Auth = the
   per-agent bearer we already mint, validated locally. **First-party / our-own-tools: no OAuth dance.**

2. **Outbound (AIAG-as-MCP-client):** the agent runtime (`apps/agent-worker`) connects *out* to
   third-party MCP servers (Notion, Google Sheets/Drive, GitHub) **on behalf of a user**. This is the
   only place the full **OAuth 2.1 + PKCE (S256) + RFC 8707 `resource` + RFC 9728 discovery** flow
   is actually required, because we are the OAuth *client* and we must obtain and store **per-user,
   per-server, audience-bound** access/refresh tokens.

**Recommended build:** use the official **`@modelcontextprotocol/sdk` (npm, v1.29.0, MIT)** for *both*
the inbound server (`StreamableHTTPServerTransport` + `requireBearerAuth`/`mcpAuthRouter`) and the
outbound client (`Client` + `StreamableHTTPClientTransport` + `OAuthClientProvider` + `auth()`), mounted
inside the existing **Hono** process (it already runs `:4000`). The SDK's auth helpers implement RFC 8707 /
RFC 9728 / PKCE correctly out of the box, so we do not hand-roll the security-critical parts.

**Do NOT deploy `IBM/mcp-context-forge` on the current box.** It is a Python/FastAPI app that *requests
1 core / 2 GiB and limits to 2 cores / 4 GiB*, runs 8 Gunicorn workers by default, and wants
Postgres + Redis for its full feature set. On a **single 2 GB VPS already running gateway + agent-worker +
Postgres + tg-miniapp**, it will not fit. Adopt its **data model and concepts** (a `mcp_servers` registry
table, virtual-server composition, REST→MCP wrapping) as a thin TypeScript registry in our existing
Postgres instead. Revisit context-forge only if/when AIAG moves to a multi-node deployment.

**Token storage:** reuse the existing, proven pattern — **AES-256-GCM at rest** exactly as
`apps/agent-worker/src/crypto.ts` already does for BYOK upstream keys (`iv | ciphertext | authTag`,
key from a 32-byte env secret), stored as Postgres `bytea`. Add a new `mcp_oauth_credentials` table keyed
by `(user_id, mcp_server_id)`; store encrypted `access_token` + `refresh_token` + `expires_at` + the
`issuer` and granted `scope`. This is a strictly additive migration, consistent with migration 0026's
provider-credentials approach.

## Key findings with sources

### 1. The MCP authorization spec is OAuth 2.1, and it is precise about the four RFCs

The current spec (`modelcontextprotocol.io/specification/.../authorization`, changelog dated
**2025-06-18**, draft tracking **OAuth 2.1 draft-ietf-oauth-v2-1-13**) makes auth **OPTIONAL** overall,
but when an HTTP transport implements it the following are **MUST**s
([source: MCP Authorization spec](https://modelcontextprotocol.io/specification/draft/basic/authorization)):

- **Roles.** The *MCP server is an OAuth 2.1 Resource Server*; the *MCP client is an OAuth 2.1 client*;
  the *Authorization Server* is a separate entity (may be Notion's, Google's, or our own). The spec
  explicitly keeps these three roles distinct — this is why our inbound and outbound layers differ.
- **PKCE is mandatory.** Clients **MUST** implement PKCE and **MUST** use `S256` when capable, and
  **MUST** verify PKCE support via AS metadata (`code_challenge_methods_supported`) before proceeding —
  refuse if absent.
- **RFC 8707 Resource Indicators are mandatory for clients.** The `resource` parameter **MUST** be sent
  in *both* the authorization request *and* the token request, **MUST** be the **canonical URI** of the
  target MCP server (e.g. `https://mcp.example.com/mcp`, no fragment, no trailing slash), and **MUST** be
  sent *regardless of whether the AS advertises support*. This binds the token's audience to one server.
- **RFC 9728 Protected Resource Metadata is mandatory for servers.** The MCP server **MUST** serve
  `/.well-known/oauth-protected-resource[/<path>]` listing its `authorization_servers`, and/or return a
  `WWW-Authenticate: Bearer resource_metadata="…", scope="…"` header on `401`. Clients **MUST** parse
  that header and fall back to well-known probing.
- **RFC 8414 / OIDC Discovery** for AS metadata; **RFC 9207 `iss`** validation to prevent mix-up attacks
  (client records expected `issuer`, compares the `iss` returned with the auth code).
- **Audience validation is mandatory for servers and token passthrough is forbidden.** "MCP servers
  **MUST** only accept tokens specifically intended for themselves … **MUST** reject tokens that do not
  include them in the audience claim." And critically: *"If the MCP server makes requests to upstream APIs …
  The MCP server **MUST NOT** pass through the token it received from the MCP client."* (confused-deputy).
- **Dynamic Client Registration (RFC 7591) is now only MAY / "backwards compat".** The 2025-06-18 revision
  promotes **OAuth Client ID Metadata Documents** (an HTTPS URL as `client_id`) as the preferred no-prior-
  relationship mechanism; DCR is a fallback.

> Practical consequence for AIAG: for **Notion/Google** we are the *client*, and those providers run their
> own AS. We must do PKCE + `resource` + `iss` validation. We are NOT operating an Authorization Server in
> phase 1 — that avoids the hardest, most security-sensitive code (we do not issue OAuth tokens; we consume
> them). Our *inbound* server uses our own opaque bearer, not OAuth, which the spec permits because auth is
> OPTIONAL and a closed first-party token is a valid resource-server scheme.

Corroborating analyses: [Auth0 — MCP spec update, June 2025](https://auth0.com/blog/mcp-specs-update-all-about-auth/),
[WorkOS — RFC 8707 Resource Indicators](https://workos.com/blog/oauth-resource-indicators-rfc-8707),
[VoidCat — MCP security baselines OAuth 2.1 & RFC 8707](https://voidcat.org/blog/mcp-security-baselines/).

### 2. The official TypeScript SDK already implements the security-critical machinery

`@modelcontextprotocol/sdk` — **npm name `@modelcontextprotocol/sdk`, latest `1.29.0`, MIT license**
([npm registry metadata](https://registry.npmjs.org/@modelcontextprotocol/sdk/latest)). The package uses a
wildcard `./*` export map, so deep subpaths resolve directly. Relevant pieces
([repo: modelcontextprotocol/typescript-sdk](https://github.com/modelcontextprotocol/typescript-sdk)):

**Server side (inbound, our tools):**
- `StreamableHTTPServerTransport` (`@modelcontextprotocol/sdk/server/streamableHttp.js`) — the
  Streamable-HTTP transport with session management (`sessionIdGenerator`, `Mcp-Session-Id` header) and an
  optional stateless mode (`sessionIdGenerator: undefined`) that maps cleanly onto our stateless worker.
- `McpServer` (`/server/mcp.js`) — register tools with `server.registerTool(name, schema, handler)`.
- Auth helpers under `/server/auth/*`: `requireBearerAuth` (Bearer middleware + `TokenVerifier`),
  `mcpAuthRouter` (mounts `/.well-known/oauth-protected-resource`, `/.well-known/oauth-authorization-server`,
  and DCR endpoints), `getOAuthProtectedResourceMetadataUrl`, `OAuthServerProvider`, and
  `ProxyOAuthServerProvider` (delegates to an external AS — useful only if we later want to *front* a
  third-party AS). For phase-1 inbound we only need `requireBearerAuth` with a trivial `TokenVerifier`
  that validates our per-agent token against Postgres.

**Client side (outbound, third-party MCP servers):**
- `Client` (`/client/index.js`) + `StreamableHTTPClientTransport` (`/client/streamableHttp.js`).
- `OAuthClientProvider` interface + `auth()` function (`/client/auth.js`) — implements the *entire* spec
  flow: RFC 9728 discovery from the `401` challenge, AS metadata discovery, PKCE (S256) generation,
  the `resource` parameter (RFC 8707), `iss` validation, token + refresh-token exchange. We implement the
  `OAuthClientProvider` storage callbacks (`tokens()`, `saveTokens()`, `redirectToAuthorization()`,
  `codeVerifier()`/`saveCodeVerifier()`, `clientInformation()`) and wire them to our encrypted Postgres
  table. The SDK does the protocol; we only provide persistence + the redirect.

This is the decisive reason to use the SDK rather than hand-rolling: PKCE, `resource`, `iss`, and
audience validation are exactly the bits that are easy to get subtly wrong and are security-load-bearing.

### 3. `IBM/mcp-context-forge` is excellent — and too heavy for the current box

[github.com/IBM/mcp-context-forge](https://github.com/IBM/mcp-context-forge) (PyPI
`mcp-contextforge-gateway`, **v1.0.0-RC-3**, **Apache-2.0**) is a Python/FastAPI **AI gateway + registry +
proxy**: federates MCP/A2A/REST/gRPC, composes **virtual MCP servers**, converts REST→MCP and between
transports (stdio/SSE/Streamable-HTTP), 55+ table schema, JWT + Basic + SSO (Google/GitHub/Entra) auth,
per-gateway bearer tokens with `Authorization` forwarding, `X-Upstream-Authorization` passthrough,
`AUTH_ENCRYPTION_SECRET` for secret encryption, Postgres + Redis for federation/caching
([README](https://github.com/IBM/mcp-context-forge/blob/main/README.md),
[architecture](https://ibm.github.io/mcp-context-forge/architecture/)).

**Footprint is the blocker.** Its own scaling guide recommends container **requests 1 CPU / 2 GiB and
limits 2 CPU / 4 GiB**, with **8 Gunicorn/Uvicorn workers** by default
([scaling docs](https://ibm.github.io/mcp-context-forge/manage/scale/)). The AIAG production host is a
**single 2 GB VPS** already running the Hono gateway, the BullMQ agent-worker, Postgres, and the
tg-miniapp (see repo `CLAUDE.md` reality table). Standing up a second 2 GiB Python service + its own Redis
is not viable there. It is also a *Python* process — a second runtime alongside our Bun/Node stack,
violating the "one stack" simplicity we currently enjoy.

**What to take from it instead:** its *concepts and schema shape* — a `mcp_servers` registry, "virtual
servers" (a named subset of tools the agent is allowed to call), tags/visibility, and the REST→MCP wrapper
idea. We can reproduce the 10% of context-forge we need as ~200 lines of TypeScript on our existing
Postgres, with no new runtime. (`Glama`/`mcpservers.org` listings confirm the feature set:
[Glama](https://glama.ai/mcp/servers/@IBM/mcp-context-forge).)

### 4. Our codebase is already shaped for this

Verified by reading the repo:

- **Gateway is Hono** (`packages/api-gateway/src/server.ts`): `app.use('/v1/*', requireApiKey)` etc.
  Adding `app.route('/mcp', mcpRoutes)` is mechanically identical. The auth middleware
  (`packages/api-gateway/src/middleware/auth.ts`) already does SHA-256-hash-on-lookup of bearer keys —
  the exact pattern our inbound MCP bearer verifier needs.
- **The tools already exist** as a dispatcher (`apps/agent-worker/src/tools.ts`: `TOOL_DEFS`,
  `executeTool(name, args, ctx)`, `pickToolDefs(allowed)`). Exposing them as MCP tools is a thin adapter:
  one `server.registerTool` per `ToolDef`, delegating to `executeTool`. The per-agent allow-list
  (`pickToolDefs`) maps directly to MCP "virtual servers".
- **Encryption is already solved** (`apps/agent-worker/src/crypto.ts`): AES-256-GCM, `iv(12)|ct|tag(16)`,
  32-byte key from `TMA_KEY_ENCRYPTION_KEY`. The outbound OAuth token store should reuse
  `encryptSecret`/`decryptSecret` verbatim (or a shared `packages/crypto`).
- **Credential-table precedent exists**: `resolveUpstream()` in `apps/agent-worker/src/agent-runner.ts`
  already loads `loadProviderCredential(agent.auth_ref)` and `decryptSecret(cred.enc_key)`. The MCP OAuth
  store is the same pattern, keyed per-user-per-server instead of per-provider.
- **The agent loop is the natural call site.** `runAgent()` already collects `tool_calls` from the model
  and dispatches via `executeTool`. Outbound MCP tools slot in as additional entries in that dispatch:
  resolve the user's MCP credential, refresh if expired, call the remote tool via the SDK `Client`.

## Concrete recommendation

### Architecture (phase 1, fits the 2 GB box, no new runtime)

```
                 ┌─────────────────────────────────────────────┐
 external MCP    │  Hono gateway (:4000, Bun)  — EXISTING       │
 clients ───────▶│   /v1/*        (LLM proxy, unchanged)        │
 (Claude, Cursor)│   /mcp         (NEW: inbound MCP server)     │
   Bearer per-   │     · StreamableHTTPServerTransport          │
   agent token   │     · requireBearerAuth → TokenVerifier      │
                 │       (SHA-256 lookup, reuse auth.ts pattern)│
                 │     · registerTool() per TOOL_DEFS           │
                 │     · NO OAuth — first-party closed token    │
                 └─────────────────────────────────────────────┘

 agent-worker (:3101, BullMQ)  — EXISTING runAgent() loop
   on a tool_call for a third-party MCP tool:
     1. look up mcp_server + user's mcp_oauth_credentials
     2. if no token → emit "authorize" deep link to TMA (user does OAuth in browser)
     3. if token expired → SDK auth() refresh (rotates refresh token)
     4. MCP SDK Client + StreamableHTTPClientTransport.callTool()
        · OAuthClientProvider supplies decrypted tokens
        · SDK enforces PKCE + resource(RFC8707) + iss(RFC9207)
                 │
                 ▼
   third-party MCP servers (Notion, Google Sheets) — their own OAuth 2.1 AS
```

**Inbound (first-party MCP server) — skip OAuth.** Mount one Streamable-HTTP route on the existing Hono
gateway. Validate the **existing per-agent bearer** (the `sk_aiag_…`-style key, hashed lookup like
`middleware/auth.ts`) via a `TokenVerifier`. Use **stateless mode** (`sessionIdGenerator: undefined`)
to match the stateless runtime and avoid per-session memory. Register AIAG's existing tools; gate the
tool set per agent with the existing `pickToolDefs` allow-list = a "virtual server" per agent. Because the
client and resource server are both AIAG, the spec's OAuth requirements do not apply (auth is OPTIONAL;
a closed bearer is a legitimate scheme). Still serve `/.well-known/oauth-protected-resource` (cheap, via
`mcpAuthRouter`) so spec-strict external clients discover the auth scheme gracefully.

**Outbound (third-party MCP client) — full OAuth 2.1.** Use the SDK `Client` + `auth()` +
`OAuthClientProvider`. We register AIAG once per provider (prefer **Client ID Metadata Document** — host
`https://ai-aggregator.ru/.well-known/mcp-client.json` with `client_id`, `redirect_uris`,
`token_endpoint_auth_method:"none"`; fall back to DCR/pre-registration per provider). The browser leg of
PKCE happens in the **TMA** (Telegram Mini App opens the provider consent page; redirect URI is an
AIAG web callback that stores the code → exchanges via SDK). The agent-worker never sees the user's
browser; it only reads the resulting encrypted tokens. **Never** forward the inbound AIAG bearer to a
third-party server, and never forward a third-party token back to the model (spec: no token passthrough).

### Token storage / encryption

Additive migration (`mcp_oauth_credentials`), encryption identical to `crypto.ts`:

```sql
CREATE TABLE mcp_servers (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  slug          text UNIQUE NOT NULL,          -- 'notion', 'google-sheets'
  display_name  text NOT NULL,
  base_url      text NOT NULL,                 -- canonical MCP URL (RFC 8707 resource)
  auth_kind     text NOT NULL DEFAULT 'oauth', -- 'oauth' | 'first_party' | 'none'
  scopes        text[] NOT NULL DEFAULT '{}',
  enabled       boolean NOT NULL DEFAULT true
);

CREATE TABLE mcp_oauth_credentials (
  id             uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tg_user_id     text NOT NULL,
  mcp_server_id  uuid NOT NULL REFERENCES mcp_servers(id),
  issuer         text NOT NULL,                -- recorded AS issuer (RFC 9207 mix-up defense)
  enc_access     bytea NOT NULL,               -- AES-256-GCM: iv|ct|tag
  enc_refresh    bytea,                        -- nullable: AS may not issue one
  scope          text NOT NULL DEFAULT '',     -- granted scopes (for step-up)
  expires_at     timestamptz,
  updated_at     timestamptz NOT NULL DEFAULT now(),
  UNIQUE (tg_user_id, mcp_server_id)
);
```

- **Cipher:** AES-256-GCM via `encryptSecret`/`decryptSecret` (`apps/agent-worker/src/crypto.ts`).
  Reuse the **same 32-byte env key** family (e.g. a dedicated `MCP_TOKEN_ENCRYPTION_KEY`, or share
  `TMA_KEY_ENCRYPTION_KEY`). GCM gives integrity (auth tag) — tamper = decrypt throws.
- **At rest only.** No plaintext token columns; no token in logs (white-label/PII rules already enforced
  in gateway middleware). Show only an `***xxxx` hint via `hintFromSecret` if a UI needs it.
- **Refresh-token rotation:** the spec requires public clients to rotate refresh tokens; the SDK's
  `auth()` returns rotated tokens — `saveTokens()` must overwrite `enc_refresh` atomically
  (`UPDATE … WHERE (tg_user_id, mcp_server_id) RETURNING`, matching the repo's atomic-DB convention).
- **Short-lived access tokens** preferred; rely on refresh. Treat any decrypt/refresh failure as
  "re-authorize" (emit TMA deep link), never as a hard agent failure.

### Sequenced plan
1. **Registry + schema** (`mcp_servers`, `mcp_oauth_credentials`) — additive migration, no prod risk.
2. **Inbound MCP server** on Hono `/mcp` (SDK `StreamableHTTPServerTransport`, stateless, per-agent
   bearer, tools from `TOOL_DEFS`). First-party, no OAuth. Ship behind a flag; verify on prod.
3. **Outbound client for ONE provider** (Notion — clean MCP+OAuth story) via SDK `Client` + `auth()` +
   encrypted `OAuthClientProvider`; TMA does the browser leg. Prove PKCE + `resource` + refresh end-to-end.
4. **Generalize** to Google Sheets/Drive; add per-agent virtual-server allow-lists; billing hook
   (third-party tool calls are "external" → keep the `isExternal` zero-markup rule unless we resell).
5. **Defer** `mcp-context-forge` until multi-node; if adopted, run it as a *sidecar registry only*, not
   on the 2 GB app box.

## Risks

- **Footprint creep.** Even our own outbound SDK `Client` instances and any per-session inbound transports
  add heap on a 2 GB box. Mitigate: stateless inbound transport; create outbound `Client`s on demand and
  dispose them; never hold a long-lived `Client` per user.
- **Confused-deputy / token passthrough.** Easy to accidentally forward the inbound AIAG bearer to a
  third-party server, or a third-party token back to the model. Spec forbids both. Enforce with a code
  invariant + test: the inbound `TokenVerifier` output and the outbound credential store are different
  types and never cross.
- **OAuth browser leg in Telegram.** TMA in-app browser + provider consent + redirect URI handling is
  fiddly (Telegram WebView quirks, redirect back into the Mini App). Risk of dead-end auth. Mitigate:
  use an AIAG web callback page that completes the exchange server-side and deep-links back to the bot.
- **Provider MCP maturity.** Not every "Notion/Sheets MCP" is a first-party, OAuth-2.1-compliant remote
  server; many are community stdio shims needing a static API key. For those, fall back to the existing
  **BYOK encrypted-key** path (already built) rather than OAuth.
- **SDK churn.** `@modelcontextprotocol/sdk` moves fast (v1.29.0 now); auth APIs (`auth()`,
  `OAuthClientProvider`) have changed across minors. Pin the version and re-verify on bump.
- **DCR confused-deputy.** If we ever run a proxy AS (`ProxyOAuthServerProvider`), the spec **MUST**:
  obtain explicit user consent per dynamically-registered client before forwarding to a third-party AS.
  Avoid by *not* operating an AS in phase 1.
- **`resource` canonicalization mismatches.** RFC 8707 audience checks fail silently if our `resource`
  string (trailing slash, port, case) differs from what the AS expects. Store the *exact* canonical URL
  in `mcp_servers.base_url` and reuse it verbatim.

## Open questions

1. **Do we operate an Authorization Server at all?** Recommendation says no for phase 1 (consume tokens,
   don't issue). Confirm we never need *external* agents to OAuth *into* AIAG with delegated user scopes
   (vs. the closed per-agent bearer). If yes, that's a separate, larger workstream.
2. **Billing model for third-party MCP tool calls.** Are remote MCP tool calls billable (markup) or free
   like BYOK? Today `isExternal ⇒ cost 0`. Notion/Sheets calls cost AIAG ~nothing, so likely free — but a
   "managed connectors" paid tier is a product decision (ties to the Hermes-core commission rule).
3. **Inbound exposure scope.** Do we expose `/mcp` publicly (any external MCP client) or only to our own
   agents? Public exposure means we *are* an OAuth resource server others may want to OAuth into → pulls
   in question 1. Likely start internal-only.
4. **Key management.** Separate `MCP_TOKEN_ENCRYPTION_KEY` vs. reuse `TMA_KEY_ENCRYPTION_KEY`? Separate
   key = blast-radius isolation but one more secret to rotate. Need a key-rotation story (envelope
   encryption / versioned key id column) before we hold many users' Google/Notion tokens.
5. **Where does the OAuth redirect land?** TMA deep-link vs. dedicated `ai-aggregator.ru/mcp/callback`
   web page. Affects which redirect URIs we register with each provider.
6. **Context-forge re-entry criteria.** At what scale (number of connectors / multi-node) does adopting
   `mcp-context-forge` as a dedicated registry service become worth a second Python runtime?

## Adversarial review

**Verdict: HOLDS UP — partly.** The strategic spine is correct and well-grounded; the
external facts re-verified clean; but one load-bearing premise of the *inbound* design is
factually false, and two design choices need tightening before they reach a plan. None of
this overturns the recommendation — it sharpens it.

### What I re-verified (all confirmed)
- **SDK metadata** (npm `@modelcontextprotocol/sdk@latest`): version **1.29.0**, license
  **MIT**, exports map uses a wildcard `./*`. Exactly as claimed.
- **`mcp-context-forge` footprint** ([scaling docs](https://ibm.github.io/mcp-context-forge/manage/scale/)):
  requests **1 CPU / 2 GiB**, limits **2 CPU / 4 GiB**, requires **Postgres + Redis**. Claim
  stands. (One nit: the worker count is `(2×cores)+1` → ~5 default for a 2-core pod, capped
  at 16, *not* a flat "8 by default." Doesn't change the "won't fit on a 2 GB box" conclusion.)
- **MCP spec MUSTs** (re-read the 2025-06-18 authorization spec in full): PKCE+S256 with
  `code_challenge_methods_supported` pre-check, `resource` (RFC 8707) in **both** auth+token
  requests **regardless of AS advertisement**, server-side audience validation, and the
  explicit **"MUST NOT pass through the token"** confused-deputy rule — all quoted accurately.
- **Codebase grounding**: `crypto.ts` (AES-256-GCM, `iv|ct|tag`, `TMA_KEY_ENCRYPTION_KEY`),
  `auth.ts` (SHA-256 hash-on-lookup of the bearer), `tools.ts` (`TOOL_DEFS`, `pickToolDefs`,
  `executeTool`), `agent-runner.ts` (`resolveUpstream`/`loadProviderCredential`), and the
  `db.ts:353` `if (isExternal) return;` short-circuit — all real and as described.

### Key issues
1. **"The per-agent bearer we already mint" does not exist (the one real error).** The report
   leans on this phrase 4× for the inbound design. Grepped the whole repo: there is **no
   per-agent token**. `auth.ts` validates the *gateway/user API key* (`apiKeyData.userId`), and
   agent→gateway traffic uses a single **shared service key** `AIAG_GATEWAY_KEY` (`sk_aiag_live_…`,
   confirmed in `agent-runner.ts` + `resolve-upstream.test.ts`). So the proposed inbound
   `TokenVerifier` cannot resolve a token to *one agent* today — the per-agent allow-list
   ("virtual server") that the whole inbound value-prop rests on **requires a new
   `agent_tokens` table + minting endpoint first.** This is a missing prerequisite, not a
   reuse. Re-scope step 2 accordingly.
2. **Inbound tools are NOT free, which guts Open Question 2's lean.** The report exposes
   `web_search` + `image_gen` inbound, but `tools.ts` shows `image_gen` calls **Kie.ai**
   (`KIE_API_KEY`, paid) and `web_search` hits a paid backend. Exposing these over MCP to an
   external client (Claude Desktop/Cursor) is **uncapped AIAG spend with no run-level
   `settleRun` debit on the path** — the money-path invariant only fires inside `runAgent`.
   This is a billing/abuse hole, not merely a "product decision." Inbound must either expose
   only zero-cost tools (`calc`, `memory`) in phase 1, or route paid tools through a metered,
   balance-guarded path before exposure.
3. **`iss` validation is slightly over-stated.** Spec has AS `iss` inclusion as **SHOULD**
   (a future revision upgrades to MUST); client validation is MUST only *conditional* on
   `authorization_response_iss_parameter_supported`. The report frames it as a flat client
   MUST. Harmless (the SDK handles the table correctly) but don't cite it as a hard MUST in a plan.
4. **DEFAULT_MODEL latent bug compounds inbound.** Per `agent-worker/CLAUDE.md`, the default
   `nousresearch/hermes-4-405b` is **not in the gateway registry** → 400. Any inbound MCP tool
   call that triggers an LLM hop inherits this. Fix/register the slug before inbound ships.
5. **Footprint risk is real and under-budgeted.** A 2 GB box already runs gateway +
   agent-worker + Postgres + tg-miniapp. The mitigations (stateless inbound, dispose outbound
   `Client`s) are right, but there is **no memory headroom number** in the report. Add a hard
   ceiling check before enabling outbound, or the first concurrent OAuth refresh storm OOMs prod.

### Non-issues (defended against my own objections)
- Hand-rolling vs SDK: correct to use the SDK; PKCE/`resource`/`iss`/audience are exactly the
  foot-guns, and the SDK implements them. No DIY.
- "Don't operate an AS in phase 1": correct and materially de-risks (avoids confused-deputy /
  DCR-consent obligations). Keep.
- AES-256-GCM reuse + additive `mcp_oauth_credentials` keyed `(tg_user_id, mcp_server_id)`:
  sound, consistent with migration 0026 and the atomic-`UPDATE…WHERE…RETURNING` convention.

### Tightened recommendation
Keep the two-layer architecture, the SDK, the "no context-forge / no AS in phase 1" calls,
and the encrypted token store **as-is**. Change the sequencing:
- **Re-order step 2:** *first* ship `agent_tokens` (mint + hashed lookup) — the per-agent
  bearer the report assumes; *then* the inbound `/mcp`. Without it there is no virtual-server
  isolation.
- **Phase-1 inbound = zero-cost tools only** (`calc`, `memory`). Defer `web_search`/`image_gen`
  inbound until they run through a balance-guarded, metered path; treat them as billable, not free.
- **Outbound stays the showcase** (Notion first, SDK `auth()`, TMA browser leg, encrypted
  store) — it is the part that genuinely needs OAuth 2.1 and the report nails it.
- Add a **prod memory ceiling gate** and **fix/register `DEFAULT_MODEL`** as explicit
  pre-conditions in the plan, and downgrade the `iss` "MUST" to its conditional form.
