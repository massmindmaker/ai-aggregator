# R-08 — Tool broker + x402 outbound

> Research item: design the paid-tool broker (in-process metered tool calls, Firecrawl first, atomic deduct + refund-on-error against the existing credit ledger) and the x402 OUTBOUND rail (self-hosted x402-rs facilitator, USDC on Base) for agents paying external services; ingest the agentic.market / x402 Bazaar tool catalog.
> Author: staff-eng research pass. Date: 2026-06-03. Status: design, not built.

---

## Summary

The agent-worker already has a **correct, battle-tested money primitive** — `settleRun()` in `apps/agent-worker/src/db.ts` does `markCompleted + daily-spend guard + balance debit` in one `sql.begin` using guarded `UPDATE … WHERE <guard> RETURNING`. But **tool calls are NOT metered today**: `executeTool()` returns `cost_rub`, the runner accumulates it into `totalCostRub`, and that total is only debited *once, at the very end of the run*, inside `settleRun`. There is **no per-tool atomic deduct, no refund-on-error, and no tools/tool_calls ledger**. `image_gen` (Kie, ~6.5₽) is the only tool with non-zero cost and it is billed implicitly through the end-of-run debit — meaning a tool that succeeds (and costs us money upstream) but whose run later fails on `max_iterations` or an upstream error is **never charged** (`markFailed` writes no debit). That is the core gap R-08 must close.

I recommend a **two-rail design**:

1. **Inbound paid-tool broker (build first, ~1 week).** A small in-process broker module in agent-worker that, for each metered tool call: (a) **reserves** credits with a guarded debit *before* the upstream call, (b) executes the tool, (c) **refunds** on error / partial-refund on price delta, and (d) writes immutable `tools` (catalog) and `tool_calls` (ledger) rows. Firecrawl is the first real metered tool. This reuses the existing `tg_user_balances` debit pattern and the `gateway_transactions`-style idempotency unique index. **No crypto needed** — agents pay us in the same RUB/credit balance they already top up via TON.

2. **Outbound x402 rail (build second, behind a flag, R&D-tier).** A self-hosted **x402-rs facilitator** (Docker, `ghcr.io/x402-rs/x402-facilitator`) on the VPS, configured for **Base mainnet USDC** (`eip155:8453`, scheme `v2-eip155-exact`), plus an outbound x402 client in the worker so an agent can pay an *external* x402-gated service in USDC. This is how AIAG consumes the **agentic.market / x402 Bazaar** catalog (`GET /v2/x402/discovery/resources`). The Bazaar catalog is ingested into the same `tools` table with `kind='x402'`, so the broker treats "our metered Firecrawl" and "an external x402 endpoint" through one uniform tool-call path.

The unifying idea: **one `tools` registry + one `tool_calls` ledger**, two settlement backends (internal credit-debit vs. outbound x402 USDC payment). The agent-side billing is always our credit balance; whether the *cost* was paid to Firecrawl's API key (we front it) or to an external wallet via x402 (we front the USDC) is an implementation detail of the broker.

## Key findings with sources

### 1. The existing ledger and money invariants (code-grounded)

- **Balance store:** `tg_user_balances (tg_user_id BIGINT PK, balance_rub NUMERIC(14,4), updated_at)` — migration `0019_ton_wallets.sql`. This is the live spendable balance; topups credit it, runs debit it. The DB CLAUDE.md flags that its unit is **migrating from ₽ to a crypto-credit unit** (TMA went crypto-only) — so any new code should treat the column as "credits" and not hardcode ₽ semantics.
- **The atomic debit pattern (mandatory, per `/SECURITY.md` + `packages/database/CLAUDE.md`):**
  ```sql
  UPDATE tg_user_balances
     SET balance_rub = balance_rub - $cost, updated_at = NOW()
   WHERE tg_user_id = $u AND balance_rub >= $cost
  RETURNING balance_rub
  ```
  Zero rows returned ⇒ insufficient funds (`InsufficientBalanceError`). READ COMMITTED, per-row lock + WHERE-guard = double-spend safe. **No SERIALIZABLE, no retry loop.** (`apps/agent-worker/src/db.ts:366-374`.)
- **`settleRun()` is the only thing that debits today** (`db.ts:328-376`). It debits `costRub` (= model tokens + accumulated tool cost) once at run end. `if (isExternal) return` short-circuits BYOK/own-key runs to **zero** charge — the commission rule from agent-worker CLAUDE.md ("AIAG-supplied → debit + markup; user's own key → ZERO").
- **The gap:** in `agent-runner.ts:396-412`, tool results add `exec.cost_rub` to `totalCostRub`, but:
  - tools return `cost_rub: 0` for everything except `image_gen`;
  - the cost only lands in the ledger **if the run reaches the no-tool-calls terminal branch and `settleRun` succeeds**. A run that fails after a costly tool ran (`max_iterations_exceeded`, `upstream_error`, mid-run budget cutoff) calls `markFailed` → **no debit, tool cost lost** (we eat the Kie/Firecrawl cost).
  - there is **no record of individual tool invocations** anywhere (no idempotency, no refund path, no audit).
- **Idempotency precedent to copy:** `gateway_transactions` (migration `0004_gateway_core.sql:207-224`) has a partial unique index `(request_id, source) WHERE type='api_usage'`, and `aiag_settle_charge()` (`packages/database/src/functions/settle-charge.sql`) does the canonical "lock row → idempotency check inside lock → guarded UPDATE → insert ledger rows" pattern. The tool broker should mirror this exactly.

### 2. Current tool surface (code-grounded)

- `apps/agent-worker/src/tools.ts`: `web_search` (DuckDuckGo HTML scrape, free, low quality), `calc` (free), `image_gen` (Kie nano-banana-pro, `KIE_COST_RUB = 6.5`), `memory` (Postgres KV, free). `code_interpreter` intentionally unimplemented. `pickToolDefs()` filters by `agent.tools[]` whitelist.
- `executeTool()` already returns `{ result, cost_rub }` and swallows tool errors into `{ result: { error }, cost_rub: 0 }`. **This is where the broker hooks in** — the broker wraps `executeTool` so metered tools route through reserve→execute→settle/refund.
- **Firecrawl is the natural first metered tool**: it replaces the brittle DuckDuckGo `web_search` with real search/scrape. Firecrawl pricing: **1 credit per page for scrape/crawl/map, 2 credits per 10 results for search; extraction has a ~5× multiplier** ([Firecrawl pricing](https://www.firecrawl.dev/pricing)). We front the Firecrawl API key and charge the agent's balance our marked-up price per call.

### 3. x402 protocol (outbound rail)

The x402 flow ([x402 docs](https://x402.gitbook.io/x402), [coinbase/x402](https://github.com/coinbase/x402)):
1. Client hits a gated resource → server returns **HTTP 402** with a JSON body `{ x402Version, accepts: PaymentRequirements[] }`.
2. **`PaymentRequirements`** fields (verbatim): `scheme` (e.g. `"exact"`), `network` (e.g. `"eip155:8453"` = Base), `maxAmountRequired`, `resource`, `description`, `mimeType`, `payTo` (recipient address), `maxTimeoutSeconds`, `asset` (token contract), `outputSchema`, `extra`.
3. Client builds a signed **`PaymentPayload`** `{ x402Version, scheme, network, payload: { authorization, signature } }` (for `exact` on EVM the authorization is an EIP-3009 `transferWithAuthorization` over USDC) and resends with the `X-PAYMENT` header.
4. Server (or its facilitator) verifies + settles; responds with **`X-PAYMENT-RESPONSE`** `{ success, transaction, network, payer }`.
- First shipping scheme = **`exact`** (fixed price). Primary network/token = **Base + USDC** (canonical Base USDC = `0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913`).

### 4. x402-rs self-hosted facilitator (exact config — verified from repo)

From [`x402-rs/x402-rs` README](https://github.com/x402-rs/x402-rs) and the `facilitator/README.md`:
- **Docker:** `docker run -v $(pwd)/config.json:/app/config.json -p 8080:8080 ghcr.io/x402-rs/x402-facilitator`.
- **HTTP endpoints (verbatim):** `GET /` (greeting), `GET|POST /verify`, `GET|POST /settle`, `GET /supported`, `GET /health`.
- **Env vars (verbatim):** `HOST` (default `0.0.0.0`), `PORT` (default `8080`), `CONFIG` (default `config.json`), `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_SERVICE_NAME`.
- **`config.json`** declares chains keyed by CAIP-2 id, e.g. `"eip155:8453"` with `eip1559: true`, `signers: ["$FACILITATOR_PRIVATE_KEY"]` (env-interpolated), and `rpc: [{ http: "https://mainnet.base.org", rate_limit: 100 }]`; plus `schemes: [{ scheme: "v2-eip155-exact", chains: ["eip155:8453"] }]`. Supports V1 + V2 protocol, EVM/Solana/Aptos via feature flags.
- Implication: AIAG runs **its own facilitator** so it does not depend on Coinbase CDP; it holds a hot Base wallet (`FACILITATOR_PRIVATE_KEY`) funded with USDC + a little ETH for gas. **This is the single biggest risk surface** (a hot key on a 2 GB VPS — see Risks).

### 5. agentic.market / x402 Bazaar discovery (catalog ingest)

From [Coinbase: x402 Bazaar](https://docs.cdp.coinbase.com/x402/bazaar) and [agentic.market](https://agentic.market):
- **Discovery endpoints:** `GET /v2/x402/discovery/resources` (paginated list, `limit`/`offset`), `GET /v2/x402/discovery/search` (semantic search + filters + quality ranking), `GET /v2/x402/discovery/mcp` (MCP server for agents).
- Services are **auto-listed** when they use the CDP facilitator + enable the bazaar extension (no manual registration). **agentic.market** is the public UI over the same index — categories: Inference, Data, Media, Search, Social, Infrastructure, Trading (~70 curated + thousands raw).
- Each Bazaar entry carries the `PaymentRequirements` (price, asset, network, payTo, resource URL, outputSchema), so ingest is a straight map into our `tools` table.

## Concrete recommendation

### A. Data model (2 new tables + reuse existing ledger)

Add migration `0027_tool_broker.sql` (idempotent, `CREATE TABLE IF NOT EXISTS`; remember prod ALTER needs `sudo -u postgres psql aiag` per DB CLAUDE.md).

```sql
-- 1. tools — the unified tool catalog (internal metered + ingested x402 Bazaar)
CREATE TABLE IF NOT EXISTS tools (
  id            VARCHAR(96) PRIMARY KEY,        -- e.g. 'firecrawl.scrape', 'x402:<host>:<path>'
  kind          VARCHAR(16) NOT NULL,           -- 'internal' | 'x402'
  name          TEXT NOT NULL,
  description   TEXT NOT NULL,
  category      VARCHAR(32),                    -- bazaar category (search/data/media/...)
  enabled       BOOLEAN NOT NULL DEFAULT true,
  -- pricing (what WE charge the agent's balance, in credits = current balance unit)
  price_model   VARCHAR(16) NOT NULL DEFAULT 'per_call', -- per_call | per_page | per_unit
  price_credits NUMERIC(14,4) NOT NULL DEFAULT 0,        -- our marked-up price
  markup        NUMERIC(5,4) NOT NULL DEFAULT 1.30,      -- applied over our upstream cost
  -- json-schema for the tool's args (fed to the model as the function `parameters`)
  parameters    JSONB NOT NULL DEFAULT '{}'::jsonb,
  -- x402 routing (NULL for internal tools)
  x402_resource TEXT,                           -- the gated URL to call
  x402_network  VARCHAR(32),                    -- 'eip155:8453'
  x402_asset    TEXT,                           -- USDC contract
  x402_pay_to   TEXT,                           -- payTo address from PaymentRequirements
  x402_max_amount NUMERIC(20,0),                -- maxAmountRequired (atomic units)
  source        VARCHAR(24) NOT NULL DEFAULT 'builtin', -- builtin | bazaar
  metadata      JSONB NOT NULL DEFAULT '{}'::jsonb,      -- raw bazaar entry / outputSchema
  created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at    TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX IF NOT EXISTS tools_enabled_kind_idx ON tools(enabled, kind);

-- 2. tool_calls — immutable per-invocation ledger (reserve / settle / refund)
CREATE TABLE IF NOT EXISTS tool_calls (
  id             UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  run_id         UUID NOT NULL,                 -- agent_runs.id
  agent_id       UUID NOT NULL,
  tg_user_id     BIGINT NOT NULL,
  tool_id        VARCHAR(96) NOT NULL REFERENCES tools(id),
  -- idempotency: model emits a tool_call id per call; (run_id, llm_call_id) is unique
  llm_call_id    TEXT NOT NULL,
  status         VARCHAR(16) NOT NULL DEFAULT 'reserved', -- reserved|settled|refunded|failed
  reserved_credits NUMERIC(14,4) NOT NULL DEFAULT 0,
  charged_credits  NUMERIC(14,4) NOT NULL DEFAULT 0,
  refunded_credits NUMERIC(14,4) NOT NULL DEFAULT 0,
  -- x402 settlement evidence (NULL for internal)
  x402_tx_hash   TEXT,
  x402_payer     TEXT,
  args           JSONB,
  result_summary TEXT,                          -- truncated, NO secrets
  error          TEXT,
  created_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  settled_at     TIMESTAMPTZ
);
CREATE UNIQUE INDEX IF NOT EXISTS tool_calls_idem_uniq ON tool_calls(run_id, llm_call_id);
CREATE INDEX IF NOT EXISTS tool_calls_run_idx ON tool_calls(run_id);
CREATE INDEX IF NOT EXISTS tool_calls_user_created_idx ON tool_calls(tg_user_id, created_at DESC);
```

Notes:
- Reuse `tg_user_balances` as the single source of truth for agent-facing spend; **do not** introduce a second ledger (the founder's "single billing authority" concern from R1). `tool_calls.charged_credits` is the per-call detail; `tg_user_balances.balance_rub` is the authority.
- The `(run_id, llm_call_id)` unique index gives idempotency identical in spirit to `gateway_transactions_api_usage_uniq`. A worker retry of the same BullMQ job re-uses the existing `tool_calls` row instead of double-charging.
- `price_credits` is **what we charge**; for x402 tools it is derived from `maxAmountRequired × markup × usd→credit`, refreshed at ingest.

### B. Broker module — `apps/agent-worker/src/broker.ts`

In-process (no new HTTP service — keep the single-VPS footprint). Public surface:

```ts
// Called by agent-runner in place of the raw executeTool for metered tools.
export async function brokeredToolCall(args: {
  tool: ToolRow; runId: string; agentId: string; tgUserId: string;
  llmCallId: string; toolArgs: Record<string, unknown>; isExternalRun: boolean;
}): Promise<ToolExecResult>;
```

Flow (the reserve → execute → settle/refund state machine):

1. **Free / BYOK short-circuit.** If `tool.price_credits === 0` *or* `isExternalRun` (own-key run = ZERO, same rule as the model path) → just `executeTool`, write a `tool_calls` row with `status='settled', charged_credits=0`. Return.
2. **Reserve (atomic, before the upstream call).** In one `sql.begin`:
   - `INSERT INTO tool_calls (... status='reserved', reserved_credits=price)` `ON CONFLICT (run_id, llm_call_id) DO NOTHING RETURNING id`. If no row returned → idempotent replay; load existing and return its cached `result_summary`/error.
   - guarded debit: `UPDATE tg_user_balances SET balance_rub = balance_rub - $price WHERE tg_user_id=$u AND balance_rub >= $price RETURNING balance_rub`. Zero rows → throw `InsufficientBalanceError` (the call is refused; model gets `{ error: 'insufficient_balance_for_tool' }`, run continues without the tool).
3. **Execute.** Internal tool → call Firecrawl/Kie. x402 tool → run the outbound x402 client (§C). Capture the *actual* upstream cost/units.
4. **Settle / refund (atomic).** In one `sql.begin`:
   - success, price unchanged → `UPDATE tool_calls SET status='settled', charged_credits=reserved_credits, settled_at=NOW(), x402_tx_hash=…`.
   - success, but real cost < reserved (e.g. Firecrawl returned fewer pages) → partial **refund**: `UPDATE tg_user_balances SET balance_rub = balance_rub + $delta …`; set `refunded_credits=$delta, charged_credits=reserved-delta`.
   - **error → full refund-on-error**: `UPDATE tg_user_balances SET balance_rub = balance_rub + reserved_credits …`; `tool_calls.status='refunded'`. Return `{ result: { error }, cost_rub: 0 }` so the runner is unaffected.
5. The runner **no longer accumulates tool cost into `totalCostRub`** — the broker has already moved the money. This removes the "run fails after costly tool ⇒ never charged" bug, because the debit happens at call time, not run end.

`agent-runner.ts` change: in the `for (const call of toolCalls)` loop, look up `tool = await loadTool(call.function.name)`; if `tool && tool.kind metered` → `brokeredToolCall(...)`, else fall back to the current free `executeTool`. Pass `call.id` as `llmCallId`.

### C. Outbound x402 rail (phase 2, flagged off by default)

- **Facilitator:** run `ghcr.io/x402-rs/x402-facilitator` as a 6th pm2/docker service, bound to `127.0.0.1:8402` (never public). `config.json` with `"eip155:8453"`, `signers: ["$FACILITATOR_PRIVATE_KEY"]`, `rpc` → a Base RPC (own node or Alchemy/Base public), `schemes: [{ scheme: "v2-eip155-exact", chains: ["eip155:8453"] }]`.
- **Outbound client in the worker.** When a `kind='x402'` tool is called, the broker: `GET x402_resource` → on 402 parse `accepts`, pick the `exact`/Base/USDC requirement ≤ our `x402_max_amount` guard → build the signed `PaymentPayload` (EIP-3009 over USDC, signed by the facilitator's key, *or* a dedicated per-agent spend key) → call our facilitator `POST /verify` then `POST /settle`, attach `X-PAYMENT`, resend the request, read `X-PAYMENT-RESPONSE` for `{ success, transaction, payer }` → store `x402_tx_hash`. The Rust client crate `x402-reqwest` does this transparently if we put a thin Rust sidecar in front; for a Bun/TS worker, port the `exact`-scheme signing (viem `signTypedData` for EIP-3009) and call our facilitator's `/verify` + `/settle` directly.
- **Funding model:** AIAG fronts USDC. The agent's balance is debited in credits (`price_credits`); the actual USDC leaves the facilitator wallet. We reconcile USDC-out vs credits-charged off-line. **Cap exposure**: a hard `x402_max_amount` per tool + a per-run and per-day USDC ceiling enforced in the broker before `/settle`.

### D. Bazaar catalog ingest (phase 2)

A cron job in `apps/worker` (the general BullMQ worker, not agent-worker): `GET https://api.cdp.coinbase.com/.../v2/x402/discovery/resources?limit=…&offset=…`, map each entry → `tools` row with `kind='x402', source='bazaar'`, `x402_resource/network/asset/pay_to/max_amount` from its `PaymentRequirements`, `price_credits = maxAmountRequired × usd→credit × markup`, `parameters` from the entry's `outputSchema`. `ON CONFLICT (id) DO UPDATE` to refresh price/enabled. Gate which categories are exposed to agents (start with Search/Data only). Curate: only `enabled=true` tools are offered to models via `pickToolDefs`.

### E. Broker "endpoint" design

The broker is **in-process** (a function), but expose a thin read/admin HTTP surface on the existing TMA/web API (not a new server), all behind TMA auth:
- `GET /api/tools` — list `enabled` tools (id, name, description, category, price_credits) for the agent-builder UI tool picker.
- `GET /api/tools/:id` — detail + parameters schema.
- `GET /api/agents/:id/tool-calls` — per-agent `tool_calls` history (status, charged/refunded, tx hash) for the spend ledger UI.
- Admin: `POST /api/admin/tools/sync-bazaar` — trigger Bazaar re-ingest; `PATCH /api/admin/tools/:id` — toggle enabled / override price/markup.
There is **no public broker HTTP endpoint** that moves money — billing is internal to the worker, which is the secure posture (matches "webhook zero-auth" lessons from R1).

### F. Phasing

1. **R-08a (build now):** tables `tools`+`tool_calls`, `broker.ts` reserve/settle/refund, register Firecrawl as `firecrawl.search`/`firecrawl.scrape` internal metered tools, wire `agent-runner` to route metered calls through the broker, backfill `image_gen` into the broker. Fixes the unbilled-tool bug. **No crypto.**
2. **R-08b (R&D, flagged):** self-host x402-rs facilitator, outbound `exact`/Base/USDC client, Bazaar ingest cron, expose curated `kind='x402'` tools.

## Risks

- **Hot wallet on a 2 GB VPS.** The x402-rs facilitator needs `FACILITATOR_PRIVATE_KEY` (USDC + gas) hot in memory/config on the same box as everything else. A compromise drains the wallet. Mitigate: tiny hot float (auto-topped-up from cold), hard per-tool/per-run/per-day USDC caps in the broker *before* `/settle`, facilitator bound to `127.0.0.1` only, key in `/srv/aiag/shared/.env` (already the secret store) not in `config.json` (use `$VAR` interpolation). Strongly consider deferring R-08b until there is real demand.
- **Double-charge / lost-charge under BullMQ retries.** The whole reason for `(run_id, llm_call_id)` idempotency + reserve-before-execute. If a job is retried after a tool succeeded but before settle, the reserve row must be found and the tool result reused, not re-run (re-running a paid scrape = double USDC spend). Must be covered by an integration test mirroring `run-settle.integration.test.ts`.
- **Refund-on-error trust boundary.** For internal tools we control success/failure cleanly. For x402, an external service can take the USDC (settle succeeds) then return an error/empty body — **we cannot claw back the on-chain payment.** Refund-on-error therefore applies to the *credit reservation only when settle has NOT happened*; once `/settle` returns `success`, the agent is charged regardless of the resource's output quality. Document this explicitly in the tool's description shown to the user.
- **Balance unit drift.** `tg_user_balances.balance_rub` is mid-migration from ₽ to crypto-credit (DB CLAUDE.md). The broker must use whatever the live unit is and not assume ₽; coordinate with the TMA money code so `price_credits` is in the same unit as `balance_rub`.
- **`DEFAULT_MODEL` latent bug interaction.** agent-worker CLAUDE.md notes `nousresearch/hermes-4-405b` is not in the gateway registry. Tool-heavy runs amplify model calls (one per iteration up to `MAX_ITERATIONS=12`); fix the default/registration before agents lean on tools or every tool-using run 400s.
- **Firecrawl credit multipliers.** Firecrawl's 5× extraction multiplier and per-page crawl pricing mean a naive `per_call` price under-charges. Use `price_model='per_page'` for crawl/map and meter actual pages returned, settling the real cost (partial-refund path handles over-reservation).
- **Bazaar = unvetted external endpoints.** Ingesting thousands of third-party x402 services exposes agents to malicious/expensive/SSRF endpoints. Start with a curated allowlist (Search/Data), enforce `x402_max_amount`, and never let an agent call an arbitrary URL — only catalogued `tools.x402_resource` values.

## Open questions

1. **Single billing authority (R1-4 founder decision):** is `tg_user_balances` the only ledger, with `tool_calls` as detail rows — or do tool charges need to also flow into `gateway_transactions`/`aiag_settle_charge` (org-scoped) for accounting parity with API-gateway usage? The TMA path (`tg_user_balances`) and the gateway path (`organizations.payg_credits`) are two different ledgers today; R-08 should not deepen that split.
2. **Do we front USDC, or require the agent owner to fund an x402 sub-wallet?** Fronting is simplest for UX but concentrates risk in our hot key. A per-user TON→USDC bridge is out of scope for R0/R1.
3. **Markup transparency:** is the marked-up `price_credits` shown to the end user before a tool runs (consent), or only in the post-run ledger? Affects UI and the "refund-on-error doesn't apply post-settle" disclosure.
4. **Protocol version:** x402-rs supports V1 and V2 and ships `v2-eip155-exact`; the Bazaar/CDP facilitator may advertise a different version/scheme string. Need to confirm our self-hosted facilitator's `/supported` matches what Bazaar resources expect, or run both schemes.
5. **TS vs Rust on the outbound signing path:** port the `exact` EIP-3009 USDC signing into the Bun/TS worker (viem), or stand up a small `x402-reqwest` Rust sidecar? The Rust crates are the reference implementation; a TS port is less code to operate but must be kept in sync with the spec.

## Adversarial review

**Verdict: PARTLY holds up.** The Phase-1 inbound broker (R-08a) is correct, well-grounded, and ready to build essentially as written — the code claims are all verified true. The Phase-2 x402 outbound design (R-08b) rests on a **material misunderstanding of the x402 trust/custody model** that, left uncorrected, would lead to building the wrong wallet architecture and mis-stating the headline risk. Two of the document's own justifications (BullMQ-retry idempotency, hot-wallet-drain) are aimed at threats that are either non-existent today or assigned to the wrong key.

### Verified-correct (the strong core)
- Every code claim checked out verbatim: `settleRun` debits only at run end inside one `sql.begin` with the guarded `UPDATE … WHERE balance_rub >= cost RETURNING` pattern (`db.ts:341-375`); `isExternal` short-circuits to zero charge; the runner accumulates `exec.cost_rub` into `totalCostRub` (`agent-runner.ts:404-406`) and `markFailed` (`:381,415`) writes **no debit**. The "costly tool runs, run later fails on `max_iterations_exceeded` → cost never charged" bug is **real and confirmed** — `image_gen` at 6.5₽ is genuinely lost on any failed run. ### Key issues
1. **Custody model is wrong — this is the load-bearing error.** x402's `exact`-EVM scheme is **non-custodial**: the *payer/client* signs the EIP-3009 `transferWithAuthorization`, the `authorization.from` is the payer's address, and USDC flows **buyer→seller directly**. The facilitator "cannot modify the amount or destination… serve only as the transaction broadcaster" and pays **only gas**, never the USDC (verified: coinbase/x402 `specs/schemes/exact/scheme_exact_evm.md`). Consequences for §C and the Risks section:
   - "the actual USDC leaves the facilitator wallet" / "AIAG fronts USDC [from the facilitator]" is **false**. The facilitator key needs a little **ETH for gas**, not a USDC float. The "drain the wallet" risk against `FACILITATOR_PRIVATE_KEY` is overstated — worst case is gas theft.
   - The doc omits the component that actually holds money: a **payer/spend wallet** (per-agent or AIAG-shared) that holds USDC and signs each authorization. *That* is the genuine hot-key drain surface, and it must be a key separate from the facilitator's. The "sign with the facilitator's key *or* a dedicated per-agent spend key" aside in §C conflates these two distinct roles. Tighten: facilitator = gas-only broadcaster (127.0.0.1); a separate, capped, auto-topped-up spend wallet = USDC source signed by viem `signTypedData`.
   - Silver lining the doc misses: because settlement is a direct on-chain transfer the facilitator can't redirect, you can self-host facilitator + spend-wallet on one box without a custodian, and you don't need a cold→hot USDC float pipeline at all — just keep the spend wallet thin.

2. **The BullMQ-retry idempotency justification is currently moot.** The Worker is constructed with no `attempts` option (`index.ts:14-23`) → BullMQ default `attempts: 1`, **no retries**. The doc's recurring rationale ("a worker retry of the same BullMQ job re-uses the existing tool_calls row", Risk #2) defends against a path that does not exist today. The `(run_id, llm_call_id)` index is still worth building (cheap, and mandatory the day retries are enabled), but the threat model is **hypothetical, not live** — say so, and either (a) keep `attempts: 1` and document that the broker's safety depends on it, or (b) if retries are ever added, the reserve-row replay must also re-use the *external x402 tx* (re-running a settled on-chain payment = real double-spend with no clawback). Frame idempotency as "required before enabling retries," not "fixes a current double-charge."

3. **Reserve-then-refund interacts badly with `settleRun`'s daily-budget guard — possible double-counting.** R-08 moves tool money out of `totalCostRub` (good, §B.5), but tool spend then **bypasses the per-agent `agents.spent_today_rub` daily-budget guard** that `settleRun` enforces (`db.ts:356-363`). A tool-heavy agent could blow far past `daily_budget_rub` because only model tokens hit that guard. The broker's per-call debit must **also** atomically increment `spent_today_rub` with the same guarded `UPDATE … WHERE spent_today_rub + price <= daily_budget_rub RETURNING` — otherwise the daily cap is silently defeated. This is missing from §B and is a correctness gap, not a nicety.

4. **`InsufficientBalanceError` for a tool is swallowed into "run continues without the tool" (§B.2) — verify this is intended.** Refusing one tool but letting the run keep looping (and keep making *billable model calls* up to `MAX_ITERATIONS=12`) means a near-empty balance still burns model spend. Either refuse the tool *and* let the model proceed (current proposal) or hard-fail the run; the doc should pick one and note that model calls remain billable regardless.

5. **Refund-on-error on the success/partial path is fine; the post-settle x402 case is correctly called out** (once `/settle` returns `success`, no clawback). Good. But combine with #1: since the payer is the agent's spend wallet, an external service that settles-then-returns-garbage drains *the agent's* USDC, so the consent/disclosure (Open Q #3) is not cosmetic — it's a real money-loss disclosure.

6. **Minor factual nits.** Bazaar discovery base URL is `https://api.cdp.coinbase.com/platform/v2/x402/discovery/resources` (doc drops `/platform/`); `limit` max is **1000**. Both cheap to fix in the ingest cron.

### Tightened recommendation
Ship **R-08a as specified, with one addition**: the broker's per-call debit must run in the *same* `sql.begin` as a guarded `spent_today_rub` increment (mirror `settleRun:356-363`), so tool spend respects the daily budget. Keep `(run_id, llm_call_id)` idempotency but document it as "retry-safety prerequisite," and keep `attempts: 1` until that path is tested. This closes the verified unbilled-tool bug with no crypto and minimal risk — high-confidence go.

**Defer R-08b** until there is real demand, and when built, **correct the wallet model first**: (1) facilitator key = gas-only, 127.0.0.1, holds ~no USDC; (2) a *separate* thin, hard-capped USDC spend wallet signs EIP-3009 authorizations (per-run + per-day USDC ceilings enforced *before* `/verify`/`/settle`); (3) treat the spend wallet — not the facilitator — as the primary drain surface in the risk register. Resolve Open Q #1 (single billing authority) before, not during, R-08b, since x402 charges add a third money flow on top of the existing `tg_user_balances` vs `organizations.payg_credits` split. Net: the design's bones are sound; fix the custody model and the daily-budget bypass and it's solid.
