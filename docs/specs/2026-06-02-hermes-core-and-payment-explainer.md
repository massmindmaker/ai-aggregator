## Сначала — исправление прежней ошибки

Раньше в заметках «Hermes» называли просто названием модели. **Это было неверно.**

Hermes — это **сам AI-агент** (движок-агент), а не модель. Это отдельный открытый продукт от NousResearch (`hermes-agent`, лицензия MIT, свежий релиз v0.15.2 от 29 мая 2026). Он именно та штука, которая «думает», помнит, пользуется инструментами и выполняет задачи. Модель (мозги) он берёт со стороны — может работать с любой.

Да, у Nous есть ещё и отдельные модели с именем «Hermes» (Hermes-4 и т.п.) — но это другое, это веса модели. Наш герой — **агент-движок Hermes**, и он не привязан к одной модели.

## 1. Что такое Hermes и как мы его используем

**Что это (в трёх предложениях).** Hermes — это самостоятельный AI-агент, который живёт на сервере, помнит прошлые разговоры, умеет пользоваться инструментами (поиск в вебе, файлы, код, картинки), сам пишет себе «навыки» и переиспользует их, ставит задачи по расписанию и может запускать под-агентов. Сам он не содержит «мозгов» — модель он вызывает по сети (через OpenRouter, через наш шлюз, через любой совместимый адрес). С пользователем он общается через чат (Telegram/Discord и т.п.) или через обычный HTTP-интерфейс.

**Как это ложится на наш продукт.** Два пути:

1. **Пользователь создаёт агента у нас** → на нашей инфраструктуре поднимается экземпляр Hermes с его настройками (характер, модель, набор инструментов). Этот экземпляр и есть «его агент».
2. **Пользователь подключает СВОЕГО агента** → он приносит свой уже готовый эндпоинт/ключ, мы просто ходим к нему.

**Очень важная хорошая новость для архитектуры.** Hermes умеет ходить за моделью на *любой* адрес. Это значит, что каждый наш экземпляр Hermes можно направить на наш собственный шлюз (`:4000`). А раз так — **вся наценка, биллинг и «белый лейбл» автоматически срабатывают** для моделей, которые поставляем мы. А когда пользователь приносит свой ключ — направляем его экземпляр напрямую к OpenRouter/Gonka, и наш шлюз обходится стороной → **комиссии ноль**. Это ровно то правило комиссии, которое вы хотите, и оно ложится без переделок.

**Чего у Hermes по факту НЕТ (развеиваю прежние мифы).** В прежних доках был выдуман «пульт управления» Hermes по сети — команды вида `PUT /api/config`, `POST /api/model/set`, `/api/skills/toggle`, `/api/cron/jobs`. **Таких команд у настоящего Hermes нет.** Модель, характер, навыки и MCP настраиваются **не по сети, а через файлы конфигурации и команды в терминале** на сервере. По сети у Hermes есть только: обычный чат-вызов (OpenAI-совместимый), запуск задач, сессии и «задачи по расписанию» (Jobs). То есть управлять им «дистанционно кнопками» как мы рисовали — нельзя; нужно править конфиг на сервере.

## 2. Реальность: потянет ли это наш сервер

Честный ответ: **наш текущий VPS (2 ГБ памяти + 2 ГБ подкачки) НЕ потянет это как продукт.**

Вот почему, по пунктам:

- **Каждый агент-Hermes — это отдельный живой процесс на сервере** (отдельная программа, свой кусок памяти, свой порт). Дешёвого режима «один процесс на всех» у Hermes пока **нет** — он только в планах разработчиков, рассчитывать на него сегодня нельзя.
- **Сколько памяти ест один агент:** примерно **300 МБ в покое**, до **~1 ГБ во время активной работы** (если браузер выключен). Если включить браузер (Chromium) — **1–2 ГБ на агента**. Браузер — главный пожиратель памяти.
- **Сама модель работает не у нас.** «Мозги» (инференс) вызываются по сети — за них платим токенами наверх (OpenRouter и т.п.). У нас на сервере крутится только «цикл агента». Это хорошо: тяжёлого железа/видеокарт нам не нужно.
- **Сколько агентов влезет:** на текущем 2-ГБ сервере уже работают 5 наших сервисов (web, шлюз, worker, tma, agent-worker), они съедают почти всю память. Свободного места — на **0, максимум 1–2** агента, и то с риском «уронить» основные сервисы. **Для маркетплейса агентов это не годится.**

Сколько влезает на сервер побольше (браузер выключен): 8 ГБ ≈ 10–12 агентов; 16 ГБ ≈ 25–30 агентов. С включённым браузером — делите на 3–4.

**Отдельный серьёзный риск — безопасность.** У Hermes профили агентов **не изолированы по файлам**. Агент пользователя, запущенный «как есть» на нашем сервере, технически может прочитать наш файл с ключами (`/srv/aiag/shared/.env` — там все ключи OpenRouter/Kie/шлюза/хранилища). Поэтому пользовательских агентов **категорически нельзя** гонять на той же машине, где лежат наши секреты, без песочницы.

**Что с этим делать (два пути):**

1. **Поднять сервер побольше** (8–16 ГБ) и запускать агентов в Docker-песочнице с лимитами. Просто, остаётся на нашем РФ-юрлице, но потолок ~10–30 агентов и всё ещё надо аккуратно с изоляцией. Годится для закрытого бета-теста.
2. **Запускать каждого агента как временную песочницу «по требованию»** на облачном сервисе (Daytona/Modal) — Hermes это уже умеет «из коробки». Агент включается, когда нужен, и засыпает, когда простаивает. Стоит копейки: для лёгкого агента ~**$0,30 в месяц** на вычисления, в простое почти ноль. Это масштабируемый и безопасный путь. Важный плюс: эти сервисы платятся в долларах → ложатся на зарубежное юрлицо (см. ниже про два юрлица).

**Главная идея экономии:** агенты почти всё время простаивают (запустился, поработал секунды-минуты, потом часы спит). Платить за «постоянно включённый процесс на каждого пользователя» — неправильно и дорого. Правильно — **поднимать агента только когда он реально работает, и гасить в простое.**

Ключевые правила исправленного видения:

- **Пользователи не продают агентов.** Они публикуют **переиспользуемые шаблоны**. У каждого шаблона сразу видно: какую модель он использует и примерно сколько стоит его прогон.

## 4. Как будет работать оплата

Сразу важный факт: **в коде есть две раздельные «кассы», и сегодня они НЕ связаны:**
- **Кошелёк пользователя в Telegram-приложении** — рублёвый баланс конкретного человека. Это та касса, что касается агентов. О ней и говорим ниже.
- **Балансы организаций в шлюзе** — это B2B-слой для корпоративного API, к человеку в Telegram он сейчас не подключён. Не путать.

### Шаг 1. Пользователь пополняет баланс — **работает уже сейчас**

Деньги входят как TON (крипта через TON Connect), но **на балансе хранятся в рублях** по курсу на момент пополнения. Для пользователя это просто «я закинул 500 ₽», TON — только транспорт. Сумма от 100 до 50 000 ₽. Зачисление атомарное, с защитой от двойного начисления.

Честно о слабых местах (всё это известно и помечено как доработки на потом): пополнение «ведёт» само приложение — если пользователь закрыл его до подтверждения платежа, зачисление подвиснет, пока он не вернётся. Серверного «дозорного», который сам досверяет платежи, пока нет.

### Шаг 2. Агент списывает за прогон — **работает уже сейчас**

За каждый прогон агента **на нашей модели** мы списываем рубли с баланса по факту. Сверено с кодом: перед запуском три проверки (месячный бюджет агента, дневной бюджет, и баланс — если меньше 1 ₽, запуск не стартует). В конце одной транзакцией: помечаем прогон выполненным + увеличиваем дневной расход + списываем с баланса. Любой сбой откатывает всё — не бывает «выполнено, но не оплачено». Это уже реальный код (`settleRun` в `db.ts`).

### Шаг 3. Агент платит за инструменты — **механика уже есть, рельса брокера — потом**

У каждого инструмента есть поле «стоимость», и она **уже прибавляется** к стоимости прогона и списывается тем же движением. Сегодня платный инструмент один — генерация картинок (~6,5 ₽/шт), остальные (поиск, калькулятор, память) бесплатны. То есть **«агент платит за инструменты» — это не новая касса, а расширение существующей.** Чего нет — отдельного «брокера» для платных внешних сервисов (например Firecrawl) и MCP-инструментов с поштучной оплатой; но это встаёт ровно в готовый шов.

### Что такое x402 и где он нужен

**x402 простыми словами:** это стандарт «оплата за один сетевой запрос». Внешний платный сервис отвечает «нужна оплата», агент тут же шлёт микроплатёж (обычно стейблкоином) и получает доступ — **без человека в цикле и без договора с каждым сервисом**.

- **Где x402 нужен:** когда **наш агент платит наружу** — чужому платному сервису. Это исходящие микроплатежи агента.
- **Где x402 НЕ нужен (не перепутать):** это **не** способ пополнения баланса (пополнение — это рубли через TON, шаг 1) и **не** внутреннее списание за прогон (внутри всё считается в рублях, шаг 2). x402 включается только на границе «наш агент → чужой платный сервис».
- **Статус:** в коде x402 **пока нет вообще**, это исследовательский трек. Честная формулировка: «так агенты *будут* платить наружу; пока не построено».

### «Свой кошелёк пользователя» — отложено

Идея «у пользователя свой крипто-кошелёк, агент тратит прямо из него» откладывается по трём причинам: (1) проверка подписи кошелька ещё не доделана по-настоящему; (2) нет единой денежной единицы — сейчас смешаны рубли, нанотоны и т.д., сначала нужно выбрать одну; (3) это крипто-расчёты, их нельзя вести с РФ-юрлица. Поэтому пока — **простой рублёвый предоплаченный баланс** (уже работает), а «свой кошелёк» — позже.

### Правило комиссии — **уже соблюдается в коде**

Сверено дословно. В коде каждый прогон помечается флагом «внешний»:
- **свой ключ пользователя** → флаг «внешний» = да → в списании стоит строка `if (isExternal) return; // user pays their own provider — nothing to debit`. То есть **ноль списания, ноль комиссии**. Это ровно «свой ключ → бесплатно».
- **наша модель** → флаг «внешний» = нет → списываем с баланса.

Важная оговорка про наценку: наценку/«белый лейбл» по-настоящему накладывает **только** путь через шлюз `:4000`. Но сейчас на сервере **не задан ключ шлюза** (`AIAG_GATEWAY_KEY`), поэтому наши прогоны временно идут напрямую в OpenRouter — списание с баланса при этом работает (по грубой оценке токенов), но наценка шлюза выключена. **Наценка включится, как только ключ шлюза пропишем на сервере.** Правило «свой ключ = бесплатно» соблюдается в любом случае. Про Gonka: отдельной ветки в коде пока нет — когда появится, она по правилу пойдёт как «свой провайдер» (без комиссии).

### Граница двух юрлиц (флаг, важно для юриста)

- **РФ-юрлицо** — всё рублёвое: пополнения, чеки, баланс, списания за прогоны (шаги 1–2, можно жить как есть).
- **Зарубежное юрлицо** — всё крипто-агентное: x402, прямые крипто-траты (шаги 3–4). До оформления структуры это не запускаем.

## 5. Что это меняет по сравнению с тем, что работает СЕЙЧАС

**Честный разрыв:** сегодня «агент» — это **строка в базе данных**, которую обрабатывает один общий, «беспамятный» цикл-обработчик. Никакого живого Hermes на сервере нет — слово «Hermes» сегодня это просто название модели, которую мы шлём в OpenRouter. Конкретно:

- **Нет живого Hermes-движка.** Каждый прогон — «холодный»: берётся последние 10 пар вопрос-ответ из базы и подмешивается в запрос. Постоянного процесса с памятью нет.
- **Инструментов всего 4 на всех** (поиск, калькулятор, картинки, простая память). Нет MCP, нет навыков, нет расписаний, нет под-агентов — всего того, что умеет настоящий Hermes.
- **Нет provisioning'а.** Нет кода, который поднимает/гасит экземпляр Hermes на агента. Текущий обработчик — наоборот, **один общий на всех**.
- **Шлюз `:4000` подключён, но «приглушён»:** ключ не прописан → наценка/«белый лейбл» сейчас не работают для прогонов агентов.
- **«Подключи свой эндпоинт» — реально работает** и корректно бесплатно. А вот «подключи свой *Hermes*-рантайм» и «публикуемые шаблоны (с моделью и ценой)» — **как таблиц и кода НЕ существует**.

**Самые крупные стройки, чтобы видение стало явью:**
1. Научиться поднимать/гасить экземпляр Hermes на агента (в песочнице, по требованию).
2. Прописать ключ шлюза на сервере → включить наценку и «белый лейбл».
3. Сделать таблицу публикуемых шаблонов (владелец, модель, оценка стоимости, счётчик установок) + кнопку «установить шаблон → создать себе агента».
4. Достроить «свой ключ через каталог провайдеров» так, чтобы он тоже был бесплатным (сейчас один из путей этого каталога ошибочно списывает).
5. Доработать конфиг-инъекцию в реальный Hermes (характер/модель/инструменты пишутся в файлы на сервере, не «кнопками по сети»).

## 6. Что перерисовать в макетах (вокруг Hermes-ядра, без NFT)

- **Витрина шаблонов:** на каждой карточке шаблона показать **модель и примерную цену прогона** — это центральная новая идея.
- **Экран создания агента:** добавить настоящий выбор провайдера (наша модель / свой ключ), и рядом — честную пометку «своя модель = комиссия, свой ключ = бесплатно».
- **Карточка агента:** показать, что это **живой экземпляр Hermes** (статус: спит/работает), его инструменты и навыки, расписания.
- **Экран баланса:** «пополнить рублями», история списаний с разбивкой «прогон» и «инструменты».
- **Подключение своего агента:** отдельный поток «подключи свой эндпоинт/ключ» с тестом соединения.
- **Убрать везде NFT** — экраны минта, бейджи, всё связанное.
- **Не рисовать «пульт Hermes по сети»** (кнопки `set model`, `toggle skill` и т.п.) — такого API у Hermes нет; управление идёт через серверный конфиг.

## Что бы я строил первым (оплата — пока только объяснение, не стройка)

1. **Прописать ключ шлюза на сервере** (`AIAG_GATEWAY_KEY`) — мелкая операция, но именно она включает наценку и «белый лейбл» для прогонов на наших моделях. Самый дешёвый и быстрый выигрыш по деньгам.
2. **Решить инфру под Hermes: песочница по требованию (Daytona/Modal).** Текущий 2-ГБ сервер агентов-Hermes не держит. Это блокирует всё «живое» видение — без этого Hermes на нашей инфре не запустить безопасно.
3. **Один настоящий экземпляр Hermes в песочнице, направленный на наш шлюз** — доказать сквозной путь «создал → поднялся Hermes → сходил за моделью через `:4000` → списали с баланса». Самая рискованная неизвестность, проверить раньше всего.
4. **Таблица публикуемых шаблонов** (модель + оценка цены видны заранее) + «установить шаблон → мой агент». Это и есть продукт «библиотека шаблонов».
5. **Починить путь «свой ключ через каталог провайдеров»**, чтобы он был бесплатным (сейчас ошибочно списывает) — приводим код в полное соответствие правилу комиссии.

- **Точные адреса/контракты сетевого API Hermes не подтверждены** против нашего пина версии. «Форма» (чат, сессии, задачи, конфиг через файлы) — реальна; конкретные пути перед написанием кода надо перепроверить на установленной сборке.
- **Оценки памяти на агента (300 МБ / 1 ГБ / 2 ГБ)** — это триангуляция (официальные минимумы Docker + типичный расход Python-сервиса), а не опубликованная Hermes цифра. Реальный расход надо измерить на нашем железе.
- **Дешёвый режим «один процесс Hermes на много агентов»** разработчиками только проектируется и не выпущен — на него нельзя закладываться сегодня.
- **Цифры стоимости облачных песочниц** (Daytona ~$0,067/час, Modal и т.д.) — по ценникам 2026 года; перед бюджетом стоит перепроверить актуальные тарифы.
