## Решение в одну строку

**Строим следующей «Подключение провайдера» (provider-picker) — экран, где пользователь выбирает, ОТКУДА берётся модель агента: наш шлюз (с наценкой) или свой ключ / свой провайдер (бесплатно, 0 комиссии).**

Это единственный из трёх кандидатов, который (а) можно собрать прямо сейчас — без недостроенного денежного фундамента, (б) двигает «мечту основателя» по пути *подключи провайдера → управляй → кошелёк → плати только за своё*, и (в) почти безопасен для живого денежного воркера, потому что **достраивает уже наполовину собранную ветку биллинга и тем самым УМЕНЬШАЕТ риск, а не добавляет его**.

---

## Почему именно это (три критерия)

### (а) Можно собрать сейчас, без денежного фундамента
Самое важное и неожиданное открытие из исследования: **серверная «читающая» половина provider-picker уже построена и работает в живом воркере.** Когда у агента проставлен провайдер, воркер уже умеет: загрузить зашифрованный ключ, расшифровать его, направить запрос на нужный провайдер, и — для нашего шлюза — взять наценку, а для чужого ключа списать ноль. Это не мечта, это код, который сегодня крутится на проде.

Чего реально не хватает (и память проекта тут частично устарела — она называла «доделать resolve в воркере», но он УЖЕ доделан):
1. **Записи ключа** — нет ни одного места, которое сохраняет ключ пользователя в защищённое хранилище провайдера. Создание агента сегодня умеет писать только «старый» способ (свободный URL + ключ), но не новый каталог провайдеров.
2. **Каталога в TMA** — список провайдеров (`GET /api/providers`) построен, но **в чужом продукте** — в веб-агрегаторе (`apps/web`), а не в Telegram-приложении. TMA его не зовёт и своего эндпоинта не имеет.
3. **Экрана выбора** — в форме создания агента есть блок «🌐 Свой агент» (сырой URL + ключ), но нет красивого пикера провайдеров из дизайн-системы.

Ничего из этого не зависит от D-0 (маржа) или D-1 (кредитный реестр). Это чистая достройка существующей механики.

### (б) Двигает путь мечты основателя
Путь *подключи-Hermes → управляй → навесь скиллы/MCP → кошелёк → купи агента* начинается с **подключения источника модели**. Provider-picker — это и есть первое звено: «откуда твой агент берёт мозги». Он напрямую кодирует фирменное правило комиссии («свой ключ/провайдер = 0 комиссии»), которое сейчас обещано в продуктовых текстах, но через UI недостижимо — то есть обещание есть, а пользователь до него дотянуться не может. Это «дырка когерентности»: интерфейс обещает то, чего не даёт. Provider-picker её закрывает.

### (в) Риск для живого воркера и 2GB VPS — низкий
Provider-picker **не плодит процессов, не держит резидентных подов, не добавляет исходящих к недоверенным хостам сверх того, что уже есть.** Чужие URL провайдеров уже проходят полную SSRF-проверку (`safeFetch`: только HTTPS, блок приватных диапазонов, пин сокета, ре-валидация редиректов). Шифрование ключей (AES-256-GCM) — та же машинерия, что уже работает для «старого» способа. Мы **достраиваем наполовину собранную ветку биллинга** — а это снижает риск рассинхрона «читает одно, пишет другое», который существует прямо сейчас.

## Почему НЕ два других кандидата

### Кандидат 2 — Навесить скиллы / MCP-сервер на агента (отклонён как «второй шаг»)
Хорошая, дифференцирующая функция, и она чисто ложится в тот же цикл инструментов. Но:
- **Построено 0%.** Новая зависимость (MCP SDK), новый модуль клиента, новая схема в БД, новая ветка диспетчера, **новая поверхность атаки.**
- **Свежий риск безопасности, которого у provider-picker нет:** MCP SDK ходит обычным `fetch` в обход нашего SSRF-щита — это «ловушка», которую надо аккуратно закрыть. Плюс описания и результаты инструментов с чужого сервера — это текст, управляемый атакующим, который едет прямо в модель (prompt-injection).
- **Служит «power users», а не основному сценарию.** Канон-портрет TMA-пользователя — «готовый полезный агент в 2 клика», а не «подключи свой MCP-сервер». По `/CLAUDE.md` скиллы/MCP-хаб помечены как **R&D / не построено** и должны показываться с лейблом «скоро/R&D».

**Вердикт: сильный ВТОРОЙ шаг.** Делать строго ПОСЛЕ provider-picker (он переиспользует то же шифрование и тот же SSRF-щит). Порядок: provider-picker → MCP read-only v1 → MCP auth/OAuth.

### Кандидат 3 — Купить / арендовать агента (author-rent) — ОТКЛОНЁН: заблокирован денежным фундаментом
Это **настоящая монетизация** (главное решение основателя, author-rent: автор ставит цену, пользователь платит точную сумму, AIAG берёт 0% с аренды). Но строить сейчас **нельзя — он жёстко заблокирован двумя кусками фундамента, которых нет:**

- **D-1 (кредитный реестр в USD) — НЕ построен.** Аренда списывает у арендатора и начисляет автору **в кредитах для траты**. Единицы такой кредитной валюты ещё не существует: код до сих пор списывает **рублёвый** баланс (`tg_user_balances`), и константа `USD_TO_RUB = 90` живёт в двух местах. «X кр/мес» аренды **не в чём считать**, пока D-1 не мигрирует баланс в USD-привязанную единицу. **Это твёрдый блокер без обходного пути.**
- **D-0 (шлюз отдаёт реальную маржу) — собран, но НЕ задеплоен.** Даже сама аренда фиксированная и её *можно* посчитать до D-0 — но СОБСТВЕННАЯ выручка AIAG на арендованном агенте (наценка на модель + инструменты + деплой) считается с *себестоимости*, а не с маржи, потому что воркер сегодня выдумывает свою цену (`PRICING × 90`) и **выбрасывает реальную стоимость от шлюза.** Запустить аренду до D-0 = «платить авторам правильно, а свою долю биллить с себестоимости» — ровно тот полусобранный денежный путь, против которого прямо предупреждает синтез (RK-2).
- **Плюс отсутствует субстрат:** таблицы публикации/клонирования/линии-происхождения, отдельный проход выплат автору, исключение самосделок, BYOK-нулевое-начисление.

**Вердикт: НЕ выносить «купить/арендовать» как живое.** Зависит от двух кусков фундамента — один не построен (D-1), второй не задеплоен (D-0). Все три экрана (профиль автора, публикация, ремикс) на бордах правильно помечены «скоро / демо». Последовательность по канону основателя: **сначала чинить денежный путь (D-0 deploy + D-1 ledger), потом аренда.**

## Выбранный подход (3 варианта рассмотрены, один выбран)

Цель функции: в форме создания/редактирования агента пользователь выбирает провайдера из каталога (наш шлюз / OpenRouter / OpenAI / Anthropic / … / свой URL), при «своём ключе» вводит ключ → ключ шифруется и сохраняется → агент начинает ходить через выбранный источник; для своего ключа списывается 0 комиссии.

### Вариант A — «Полный пикер из каталога» (новый путь 0026, отдельный от старого)
Добавить в TMA эндпоинт каталога, новый write-роут (пишет в `agent_provider_credentials` + проставляет `provider_id/auth_ref/model_id` агенту), и заменить блок «🌐 Свой агент» полноценным `<select>` провайдеров.
- **Плюсы:** ровно тот путь, который уже умеет воркер; «правильная» целевая архитектура; чистое разделение «наш шлюз / чужой ключ»; UI совпадает с дизайн-системой (компонент «Provider picker»).
- **Минусы:** надо аккуратно вычистить или сосуществовать со «старым» блоком `external_openai`, чтобы не было двух способов делать одно и то же; редактирование агента сегодня вообще не показывает поля подключения — нужно добавить.
- **Риск воркера:** низкий — читающая ветка уже живёт.
- **Оценка: 9/10.**

### Вариант B — «Переключить старый блок на каталог» (минимальная хирургия)
Не трогать структуру формы; просто над существующим блоком «Свой агент» добавить `<select>` провайдеров, а на submit вместо `external_*` писать колонки 0026.
- **Плюсы:** наименьшее число изменённых строк; быстро.
- **Минусы:** провайдеры с фиксированным base_url (OpenAI/Anthropic) и «Custom URL» смешиваются в одном кривоватом блоке; легко оставить мёртвый код старого пути; UX-долг.
- **Риск воркера:** низкий.
- **Оценка: 6/10** — экономит время сейчас, копит долг.

### Вариант C — «Сначала только наш шлюз + OpenRouter, без ввода ключей»
Показать пикер с двумя строками (AIAG-шлюз / OpenRouter-как-провайдер), без пользовательского ввода ключа — только переключение `model_id`/маршрута на уже наших ключах.
- **Плюсы:** ноль работы по шифрованию/записи ключей; самый безопасный для денежного пути.
- **Минусы:** **не выполняет главное обещание** — «свой ключ = 0 комиссии». Без BYOK-записи функция наполовину пустая и не закрывает дырку когерентности. Это не та функция, ради которой стоит ходить.
- **Оценка: 4/10** — слишком урезано, обещание не закрыто.

### Выбор: **Вариант A**, нарезанный так, чтобы первый ломоть = «BYOK через каталог end-to-end».
Вариант A — правильная цель. Чтобы снять его минус (объём + сосуществование со старым блоком), берём не всё сразу, а самый ценный тонкий срез (ниже). Старый блок `external_openai` НЕ удаляем на первом срезе (он на живом пути) — помечаем как legacy и выпиливаем отдельным шагом после проверки нового пути на проде.

## Самый маленький ценный первый срез (что катим первым)

**Один сквозной сценарий: «создаю агента → выбираю провайдера из каталога → ввожу свой ключ → агент ходит через него → комиссия 0».**

Включает:
1. **TMA-эндпоинт каталога** — `GET /tg/api/tma/providers`, отдаёт включённые провайдеры (id, имя, нужен ли base_url). Своя, авторизованная TMA-копия — не зовём веб-агрегатор.
2. **TMA write-роут** — на создании агента: если выбран провайдер из каталога — зашифровать ключ (AES-256-GCM, тот же `encryptSecret`, что и для старого пути), вставить запись в `agent_provider_credentials`, проставить агенту `provider_id / auth_ref / model_id` (+ `base_url` только для «Custom»).
3. **UI-пикер в форме создания** — `<select>` провайдеров вместо/над блоком «Свой агент»: выбор провайдера → поле ключа (+ поле URL только если провайдер требует base_url) → поле модели. Сабмит по новому пути.
4. **Проверка миграции 0026 на проде** — пункт чек-листа деплоя (миграции ручные/без трекинга), а не предположение.

Сознательно НЕ в первом срезе: редактирование подключения у существующего агента (только создание), удаление/смена ключа, кнопка «проверить соединение» для каталожного пути (у старого она уже есть), выпиливание старого `external_openai`-блока, мульти-ключи, Gonka-строка.

**Критерий «готово»:** typecheck/build зелёный → деплой на VPS → на проде создаю агента с провайдером из каталога и своим ключом, запускаю прогон, в логах/трейсе вижу маршрут через выбранного провайдера и **списание 0** за комиссию (`isExternal`-правило не трогаем — для каталожного пути билл идёт через нас, но это уже существующее поведение воркера; «0 комиссии» — это про BYOK-ветку `external`/own-provider). Затем — SSRF-проба на «Custom URL» (приватный IP должен отлетать до коннекта).

> Уточнение по биллингу для среза: каталожный путь (ветка A воркера) сегодня помечен `isExternal:false` — то есть **биллится через нас**. «Свой ключ = 0 комиссии» в чистом виде живёт на ветке `external_openai` (`isExternal:true`). Первый срез даёт пользователю выбор провайдера и сохранение своего ключа; вопрос «каталожный BYOK тоже должен быть 0 комиссии?» — это founder-level развилка по деньгам, её фиксируем отдельно перед расширением среза (см. ниже).

## Развилка для основателя (одно решение по деньгам, до расширения)
Сегодня в коде: провайдер-из-каталога (ветка A) = **биллится через нас** (`isExternal:false`); «старый внешний endpoint» (ветка B) = **0 комиссии** (`isExternal:true`). Вопрос: когда пользователь приносит **свой ключ** к провайдеру из каталога (OpenAI/Anthropic/OpenRouter) — это «свой ключ → 0 комиссии» или «через нас → наценка»? По правилу комиссии из `/CLAUDE.md` свой ключ = 0. Значит, скорее всего, каталожный путь со своим ключом должен ставить `isExternal:true`. Это не блокирует первый срез (выбор + сохранение ключа работают), но определяет один флаг перед тем, как объявлять «свой ключ = бесплатно» в UI. **Нужно твоё «да» на: «каталожный BYOK = 0 комиссии».**

## Технический раздел

### Что уже построено (read-side, на проде в воркере)
- `resolveUpstream` (`apps/agent-worker/src/agent-runner.ts:57-110`) — три ветки, «самое специфичное первым»:
  - **A. provider_id != null** (`:61-73`) → `loadProviderCredential(auth_ref)` (`db.ts:98-130`) → decrypt `enc_key` → base = `base_url_override ?? cred.base_url ?? cred.api_base` + `/chat/completions`, model = `model_id ?? cred.model_id ?? DEFAULT_MODEL`, **`isExternal:false`**.
  - **B. connection_type='external_openai'** (`:75-88`) → legacy BYO endpoint, **`isExternal:true` → 0 комиссии**.
  - **C. иначе** (`:90-109`) → шлюз `:4000` (наценка) или degraded OpenRouter-fallback если нет `AIAG_GATEWAY_KEY`.
- Схема (миграция `0026_provider_catalog.sql`): таблица `providers` (8 сидов, все OpenAI-совместимые, `api_key`), таблица `agent_provider_credentials` (`enc_key` AES-256-GCM base64, `key_hint`, `base_url`, `model_id`, `UNIQUE(agent_id)`), 4 nullable-колонки на `agents` (`provider_id` FK, `model_id`, `auth_ref` soft-FK, `base_url_override`). Дискриминатор: `provider_id IS NOT NULL`.
- SSRF: чужие base_url уже идут через `safeFetch` с `SAFE_FETCH_ALLOWLIST = ['127.0.0.1:4000','openrouter.ai']` (`agent-runner.ts:193-198`) — user-host'ов в allowlist нет → полная IP-валидация. **User-supplied хост НИКОГДА не добавлять в allowlist.**

### Что строим (write-side + UI — это и есть «оставшаяся работа P0»)
1. **`GET /tg/api/tma/providers`** (новый файл под `apps/tg-miniapp/app/api/tma/providers/`). Сейчас каталожный эндпоинт есть только в `apps/web/src/app/api/providers/route.ts:30-58` — **в чужом продукте.** Нужна TMA-авторизованная копия запроса `SELECT id,name,api_base,auth_kind,requires_base_url FROM providers WHERE enabled ORDER BY sort` (prepared statement).
2. **Write в create-роуте** (`apps/tg-miniapp/app/api/tma/agents/route.ts`, сейчас пишет только `external_*`, `:105-131`): при `provider_id` в теле — `encryptSecret(key).toString('base64')` + `hintFromSecret`, INSERT в `agent_provider_credentials`, затем проставить `agents.provider_id/auth_ref/model_id` (+ `base_url` для custom). Зеркалит уже существующий паттерн `encryptSecret/hintFromSecret/validateExternalUrl` (`route.ts:97-102`). Всё — prepared statements; запись ключа + апдейт агента в одной транзакции.
3. **UI-пикер** в `apps/tg-miniapp/app/agents/new/page.tsx` — заменить/расширить блок «🌐 Свой агент» (`:313-419`): fetch каталога → `<select>` провайдеров → для `requires_base_url=true` (custom) показать URL → поле ключа + поле модели. Компонент дизайн-системы — «Provider picker» (`DESIGN.md`: строки AIAG/OpenRouter/BYOK/Gonka/Custom, «свой = 0 комиссии»).
4. **Деплой-чек:** подтвердить, что `0026_provider_catalog.sql` физически применена на проде (`sudo -u postgres psql aiag`, миграции ручные/без трекинга — `packages/database/CLAUDE.md`).

### Что НЕ трогаем (хирургичность, живой денежный путь)
- `settleRun`, цикл инструментов, биллинг-аккумуляторы, `callWithFallback`, `isExternal`-семантику веток — **не трогаем.** Меняем только write-сторону (create-роут) + UI + новый read-эндпоинт каталога.
- Старый `external_openai`-блок и поля — НЕ удаляем на первом срезе (он на живом пути). Помечаем legacy; выпиливаем отдельным шагом после прод-проверки нового пути.

### Известные риски/долги к учёту
- **R1-7 (трекается, не зафикшен):** ре-валидация `provider_id` SSRF на стадии резолва. Первый срез его не закрывает и не усугубляет, но при расширении (особенно «Custom URL») держать в виду.
- **Латентный баг (зафиксирован):** `DEFAULT_MODEL` ранее был `nousresearch/hermes-4-405b`, которого нет в реестре шлюза → 400 «Unknown model». ### Почему не MCP/аренда — кратко (технически)
- MCP (`feat-4`): 0% кода, новый dep `@modelcontextprotocol/sdk`, **SDK ходит голым `fetch` в обход `safeFetch`** (надо инжектить safeFetch-транспорт или vetUrl-преflight), + поверхность tool-poisoning. Хороший второй шаг, ложится в `executeTool`/`pickToolDefs`, но net-new.
- Аренда (`feat-3`): блок на **D-1 (USD-кредитный реестр — не построен)** + **D-0 (маржа от шлюза — собрана, не задеплоена)**. Шить аренду до D-0/D-1 = биллить свою долю с себестоимости (RK-2). Сначала денежный путь.
