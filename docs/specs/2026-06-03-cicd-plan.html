01

Выбранный подход и ПОЧЕМУ

Сборка на CI-раннере, доставка готового артефакта на VPS, атомарная подмена релиза через симлинк, и самовосстановление pm2 из ecosystem, лежащего внутри current. Это убирает три конкретные боли, которые у нас уже случались.

STEP 1 GitHub Actions Trigger на push в master (или merged PR). Раннер берёт код.
STEP 2 Build on runner Workspace-aware сборка (shared/database/upstream-adapters → apps) на раннере, НЕ на VPS.
STEP 3 Tarball → scp Готовый артефакт уезжает в releases/<ts> на VPS.
STEP 4 Atomic swap Симлинк current → новый релиз. Подмена мгновенная, без полу-собранного состояния.
STEP 5 Self-heal pm2 pm2 поднимается из ecosystem внутри current + health-check + авто-rollback + keep-last-5.

Почему именно так — три убитые боли

Боль 1 — OOM на 2GB VPS

Сборка bun-workspace из 4 приложений + gateway + 8 shared-пакетов на 2GB-боксе упирается в память и валит процесс. Build-on-runner переносит самую тяжёлую фазу на CI-раннер GitHub (где RAM не наша проблема), а на VPS приезжает уже собранный артефакт. OOM при деплое больше не возникает.

Боль 2 — баг с абсолютными путями

Когда pm2 запускается из жёстко прописанного абсолютного пути конкретного релиза, после подмены симлинка процессы продолжают держать старую директорию (или ломаются, если её удалили в keep-last-5). Self-heal pm2 из ecosystem-on-current означает, что конфиг pm2 всегда читается через симлинк current — пути стабильны между релизами, ротация старых релизов ничего не ломает.

Боль 3 — ручная боль

Сегодня деплой = ручной SSH, ручная сборка на VPS, ручной pm2 reload/restart, ручная проверка. Каждый шаг — точка отказа (stale-процессы, забытый билд turbo-либ, расхождение lockfile). GitHub Actions делает всё это детерминированно по одному push, с health-check и авто-rollback, плюс Telegram-нотификация о результате.

Что мы НЕ переписываем

Существующий deploy-production.yml уже делает 80% тяжёлой работы: build-on-CI → tarball → scp → atomic releases/<ts> symlink swap → pm2 reload с health-check + авто-rollback + Telegram-notify + keep-last-5. Это доводка существующего пайплайна, а не новая система.

Оставшиеся пробелы (закрываются за ~1 день)

  1. Сейчас только workflow_dispatch — добавить авто-триггер на push в master (или merged PR) для настоящего автодеплоя.
  2. Тесты non-blocking (bun test || true, gateway build || true) — сделать gate'ом деплоя после стабилизации.
  3. agent-worker и tma не first-class в матрице сборки (gateway build = || true, worker не собирается в CI) — добавить их.
  4. Per-release bun install на VPS пере-резолвит весь workspace — пред-бандлить node_modules в артефакт или кэшировать, чтобы срезать время деплоя и давление на RAM.
  5. Известные операционные грабли (SSH-via-VPN/fail2ban, root-owned dirs, нет workflow-scope у токена, pm2 reload оставляет stale-процесс → pm2 restart) — это VPS-конфиг фиксы, полностью совместимые с тем, чтобы остаться на месте.

Это раздельные deploy-таргеты и домены: рублёвый web и крипто-TMA не смешиваются. Плюс к ним на VPS живут 3 сервиса без HTTP-лица — gateway (порт 4000), worker и agent-worker (фоновые воркеры денежного пути). nginx держит правила /tg basePath + strip. Именно эта топология (2 Next.js-приложения + gateway + 2 не-HTTP воркера + workspace-сборка + nginx-правила + ручные prod-миграции) — то, что Timeweb Apps заставил бы переинженерить с нуля. Подробности — в разделе 03.

03

Timeweb Apps: разбор и рекомендация

РЕКОМЕНДАЦИЯ

(A) Оставить bare VPS + улучшить GitHub Actions. НЕ мигрировать AIAG на Timeweb Cloud Apps. Уверенность: высокая. App Platform архитектурно плохо ложится на этот монорепо, стоимость миграции высока, а выигрыш (автодеплой на push) достижим на существующем VPS примерно за 1 день CI-работы.

Проба Timeweb MCP (ключей нет)

Все четыре read-only Timeweb-тула падают одинаково — у MCP нет API-токена:

get_deploy_settings            → ❌ Не установлены переменные окружения TIMEWEB_TOKEN
get_vcs_providers              → то же
get_allowed_presets            → то же
get_vcs_provider_repositories  → то же

То есть MCP сегодня не может сделать ничего без TIMEWEB_TOKEN от основателя. Он подключён, но не аутентифицирован: ничего не перечислить, а write-тулы (create_timeweb_app / add_vcs_provider) тоже бы упали. (Firecrawl MCP тоже лежал — 404 на search/scrape — поэтому ресёрч шёл через WebSearch + WebFetch по официальной документации.)

Что такое Timeweb Cloud Apps (из официальных доков)

  • Managed PaaS в стиле Heroku / DigitalOcean App Platform. Подключаешь GitHub/GitLab/Bitbucket-репо → он тянет код, ставит зависимости, собирает, запускает. «Build from latest commit» авто-пересобирает на каждый push в выбранную ветку. (Репозитории, подключённые по URL, а не через OAuth, автодеплоя не получают — только ручной redeploy.)
  • Типы приложений: backend (Node, в т.ч. Express/Fastify/Nest, Python, Go и т.д.), frontend (статика — React/Next/Nuxt как статические файлы), или Docker (Dockerfile, Docker Compose или образ из Docker Hub).
  • Эфемерная файловая система: данные контейнера стираются на каждый redeploy — внешний S3/DBaaS обязателен. (У нас уже внешний Postgres + S3, так что эта часть ок.)
  • Ценообразование per-app, по usage-тиру («от 1 ₽» при крошечном объёме запросов до ~5.45 ₽/час при 10M req/мес). Конкретные тиры RAM/CPU не опубликованы на странице цен — нужен аккаунт основателя, чтобы увидеть реальные цифры.

Два fit-breaker'а для нашего монорепо

Fit-breaker 1 — мульти-сервис слабый

Docker Compose поддерживается, но доки явно говорят: проксирование на основной домен работает только для первого сервиса в docker-compose.yml; остальным нужен явный host-port. Плюс длинный список запрещённых директив (volumes, privileged, cap_add, pid, ipc, host networking, порты 80/443 зарезервированы). Наши 5 сервисов (web, gateway, worker, agent-worker, tg-miniapp) включают два не-HTTP фоновых воркера (worker, agent-worker) — App Platform построен вокруг «один HTTP-порт на приложение», и доки нигде не подтверждают поддержанную модель для долгоживущего не-HTTP процесса. Пришлось бы воевать с платформой.

Fit-breaker 2 — нет документированной поддержки монорепо/subdir или кастомной build-команды

Доки про «как это работает», «подключение репозиториев» и FAQ не упоминают сборку из поддиректории и не упоминают кастомную build/run-команду. Нашему деплою нужен workspace-aware порядок (собрать shared/database/upstream-adapters до каждого приложения, bun install --frozen-lockfile, per-app --cwd-сборки). На turbo/bun-workspace с 4 приложениями + gateway + 8 shared-пакетами естественный маппинг в Timeweb = одно App на сервис = 5 отдельных Apps, каждое заново клонирует весь репо и требует рукописного Dockerfile для workspace-сборки. Это выбрасывает модель «rsync-tarball-once», которая у нас уже есть, и умножает стоимость сборки в 5 раз.

Итог: чтобы захостить AIAG на Timeweb Apps, пришлось бы написать 5 Dockerfile'ов, принять эфемерные контейнеры, потерять single-port-предположение для двух воркеров — и всё равно не получить workspace-aware single-build. Это переписывание, а не миграция.

Как это ложится на нашу реальность

ФакторРеальностьВывод
2GB VPS → нужен бокс побольше Это проблема сайзинга сервера, а не механизма деплоя. Фикс одинаков при любом выборе CI: resize Timeweb VPS (~120 ₽/GB RAM, 210 ₽/CPU; напр. 4GB/2CPU ≈ 1000 ₽/мес) или переезд на 4–8GB VPS. Миграция на Apps тут не помогает — платил бы per-app за 5 приложений, вероятно дороже одного правильно-сайзнутого VPS, с меньшим контролем.
2-app (web + TMA) Оба Next.js — единственные две части, что чисто ложатся на Timeweb Apps. Если основатель когда-нибудь захочет managed-хостинг, web и tma — единственные вменяемые кандидаты. Но их же легче всего оставить на текущем VPS — нет принуждающего фактора.
Managed-Hermes на отдельном ~18GB боксе R&D, реально отдельный. Большой, stateful, GPU/RAM-тяжёлый рантайм — ровно то, в чём PaaS вроде Apps хуже всего (эфемерная FS, request-tiered billing, нет persistent-томов). Его место — собственный dedicated VPS/dedicated-сервер (Timeweb VDS или dedicated), независимо от выбора CI. Это не аргумент за Apps.

Почему улучшенный GitHub Actions побеждает

Мы уже имеем пайплайн, делающий тяжёлые 80%. Пробелы малы и чинятся за ~1 день (см. раздел 01). Это сохраняет полный контроль над двумя не-HTTP воркерами, порядком workspace-сборки, nginx /tg basePath + strip и ручными prod-миграциями — всё, что Apps заставил бы переинженерить.

Bottom line

Миграция на Timeweb Apps тяжёлая (5 Dockerfile'ов, воркеры не влезают, нет монорепо-сборки, эфемерная FS, непрозрачное per-app ценообразование) ради выигрыша — автодеплой-на-push — который мы получаем на существующем VPS примерно за день, проапгрейдив уже имеющийся workflow. Resize VPS, доделать GitHub Actions (авто-триггер + worker/tma в матрице + gating-тесты), а managed-предложения Timeweb приберечь только для будущего отдельного managed-Hermes бокса (как dedicated VDS, не Apps).

04

Что должен сделать / предоставить основатель

Конкретный чек-лист для запуска автодеплоя по Path A. Пункты с тегом ОПЦ не блокируют запуск.

1. Выдать gh-токену scope workflow

Без этого нельзя пушить изменения в файлы .github/workflows/*. Команда: gh auth refresh -h github.com -s workflow

Основатель

2. Подтвердить актуальность GitHub-секретов

Проверить, что в репозитории заданы и свежие: DEPLOY_SSH_KEY, DEPLOY_HOST, DEPLOY_USER (=aiag), а также TELEGRAM_ALERT_BOT_TOKEN и TELEGRAM_ALERT_CHAT_ID для нотификаций. Новых внешних аккаунтов не требуется.

Основатель

3. Решить: deploy-user vs chown root-owned директорий

Директории agent-worker и tma на VPS принадлежат root. Либо деплоить под пользователем с правами на них, либо chown их под aiag, чтобы атомарная подмена и pm2-self-heal работали без sudo-прерываний.

Основатель

4. Вайтлистить GitHub-раннер из fail2ban

Подтвердить SSH-достижимость раннера (или добавить его IP-диапазоны в whitelist fail2ban), иначе SSH-шаг деплоя забанится как brute-force — это уже случалось при SSH-via-VPN.

Основатель

5. Решение про апгрейд VPS (2GB → 4GB+)

Под трафик и комфортный запас на 5 pm2-процессов. Build-on-runner снимает OOM при сборке, но для эксплуатации под нагрузкой бокс побольше всё равно желателен (≈ +700 ₽/мес).

ОПЦ · трафик

6. Решить: авто-деплой на push + gating-тесты

Да/нет на авто-триггер при push в master (или merged PR), и гейтить ли деплой на тестах прямо сейчас или после их стабилизации.

Основатель

7. Timeweb API-токен — ТОЛЬКО при managed-пути

Нужен исключительно, если выбираем Path B (Timeweb Apps) или поднимаем managed-Hermes через MCP. Для рекомендованного Path A не требуется — MCP остаётся без токена. Это full-account, high-privilege секрет.

ОПЦ · managed-путь
05

Обработка миграций (ручные / gated)

DB-миграции на проде остаются ручными и вне авто-пайплайна — это сознательный выбор, а не недоработка.

Почему не автоматизируем миграции в деплое

Prod-миграции у нас исторически ручные и без трекинга. ALTER требует sudo -u postgres psql aiag (app-пользователь aiag не может ALTER). Заворачивать это в авто-деплой опасно: schema-изменение на живом денежном пути (billing/identity) должно идти под наблюдением, с возможностью отката, отдельно от подмены кода.

Правило

  • Код деплоится автоматически по push (build-on-runner → atomic swap → self-heal pm2).
  • Миграции применяются вручную / gated — оператором, до или после code-swap, через sudo -u postgres psql aiag, с явной проверкой. Авто-rollback кода не трогает БД.
  • Порядок при breaking-схеме: expand → deploy code → contract. Сначала аддитивная миграция (новые колонки/таблицы), потом совместимый код, и только потом — удаление старого. Это держит авто-деплой кода безопасным даже при ручных миграциях.

Так автодеплой кода (быстрый, частый, авто-откатываемый) и миграции схемы (редкие, под надзором, на денежном пути) остаются развязанными — каждый со своим уровнем риска.

Релевантные файлы: .github/workflows/deploy-production.yml (workflow для доводки), скилл aiag-deploy (документированная release-процедура), и 5 сервисов: apps/web, apps/worker, apps/agent-worker, apps/tg-miniapp + packages/api-gateway.
