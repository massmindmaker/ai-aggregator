## Feasibility verdict

**PARTIALLY FEASIBLE — but the hero is unbuilt and the spec oversells.** What works **today**:
AIAG-as-an-OpenAI-compatible-provider injected into a runtime (the worker already proxies
OpenAI-shaped chat/completions), the **BYOK provider-picker** (P0, grounded in existing
`crypto.ts` + `external-agent.ts`), and an in-process **key-broker tool rail** (we hold the
key, meter, deduct credits). Those are real and low-risk.

Everything that makes this a "Hermes supply marketplace" distinctive is **unbuilt**:

- **NO Hermes exists in the codebase.** The current "agent" is a stateless 12-iteration
  BullMQ OpenRouter loop — see `apps/agent-worker/src/agent-runner.ts:21-52`. There is no
  persistent per-user Hermes pod, no tmux sub-agents, no Swarm, no cron, no `:8642` gateway,
  no `:9119` dashboard API. Dashboard artboard **34** («Мой Hermes · :8642 · CPU 4% · MEM 210M»,
  sub-agents, Swarm, config.yaml, live metrics) is **fiction** relative to what exists.
- **The managed path bypasses our own gateway.** `aiag` agents hit OpenRouter directly with
  a shared `OPENROUTER_API_KEY` (`agent-runner.ts:48-51`), so white-label markup +
  `gateway_transactions` billing are **not actually closed** for the managed path.
- **Managed cloud Hermes per user at scale** is the single biggest cost/ops bet — k3s +
  per-user namespace + PVC + S3 archive + kube-green hibernation + SecComp/NetworkPolicy
  isolation (correctly scoped in phase-17, entirely unbuilt). Hermes runs arbitrary
  self-generated skill code in tmux — multi-tenant isolation of that is a real security
  problem, not a config detail.
- **Per-call TON/USDT settlement** is undefined-as-marketed. On-chain TON per tool call is
  infeasible at micro-amounts/latency; it MUST settle against an **off-chain prepaid TON/USDT
  credit ledger** with atomic-deduct (`UPDATE balance WHERE balance>=cost RETURNING`).
- **MCP-OAuth contradiction.** The supply spec says "no OAuth dance (both sides ours)";
  phase-17 mandates MCP OAuth 2.1 + RFC 8707 from day one. The moment a real 3rd-party MCP
  (Notion/Sheets, artboards 30/31/36) is connected, OAuth is required.
- **Gonka** (gonka.ai) appears **nowhere** in any spec or wireframe — zero design coverage.
- **Crypto-only billing** is an adoption risk: 100% TON/USDT, no fiat path, colliding with
  the project's own credits-primary guardrail and 152-ФЗ / two-entity posture.

**Reframe verdict:** the wireframes still make the **73-model aggregator the HERO** (onboarding
13/33, Маркет 09/23, dashboard 34) — a direct violation of reframe rule #2. The
personal-Telegram rule (#6) is currently **respected** (generic placeholders; fictional
publisher handles) — hold that line and add an explicit guard against future drift.

**NET:** ship **P0** (BYOK provider picker) and the **key-broker tool rail** — they are real.
Treat **managed Hermes per user**, **MCP gateway billed in TON per call**, **Gonka**, and
**x402-external** as R&D bets that are **NOT yet feasible-as-described** and **must not be
marketed in onboarding as already working**.

### Top risks (ranked)

1. **Managed Hermes per user has no infra & no isolation** (high). Don't market as live.
   Phase it: keep the stateless worker as v1 "managed agent" (stop calling it Hermes in UI);
   build k3s/PVC/hibernation as an explicit prerequisite with a capacity model; start with a
   shared scale-to-zero pool + hard CPU/RAM caps + miner detection; AST-scan every skill
   (incl. auto-generated) before activation; egress allowlist; pin Hermes major.minor.
2. **Per-call TON/USDT settlement** (high). Bill against a prepaid **off-chain** credit ledger
   with atomic-deduct; never attempt on-chain TON per call. Ship the in-process key-broker
   rail first. Keep `x402` reserved-only (stub-throw) until a concrete paid resource exists.
3. **Gonka unknown** (high). **Spike first**: does it expose an OpenAI-compatible endpoint?
   p50/p95 latency? settlement model? Until verified, **do not** render it as a live provider
   card — show it as "скоро / бета" or keep behind a power-user flag.
4. **AIAG managed path bypasses the gateway** (med). Route `kind='aiag'` through
   `http://127.0.0.1:4000/v1` with `AIAG_GATEWAY_KEY`, apply `provider.markup`, fall back to
   OpenRouter only if the gateway lacks the model. Verify on VPS.
5. **Crypto-only billing wall** (high). Credits primary, crypto an optional top-up rail; fiat
   on the RF entity, TON/USDT/x402 on the foreign agentic entity; never gate first value
   behind a wallet connect (keep "first run free").
6. **MCP-OAuth contradiction** (high). First-party (ours↔ours) MCP can skip OAuth; any
   externally-owned MCP MUST do OAuth 2.1 + PKCE + RFC 8707. UI must distinguish first-party
   vs third-party tools.
7. **Telegram Business overstated** (med). Business DMs are Premium-gated and capability-limited
   (no reliable full-history read, restricted edit/delete/reaction windows). Keep Bot-API-only
   (channels/groups) as default; gate the Business/DM path behind a Premium check with an
   in-UI capability disclaimer. Never imply MTProto.
8. **"Hermes" branding vs reality** (med). Either integrate real Hermes for BYO power users
   first (read real `/api/config`, `/api/skills`, `/api/mcp`) and show the dashboard only for
   connected real runtimes, or relabel managed-v1 as "AIAG agent" and hide
   Swarm/sub-agent/config affordances until the runtime backs them. **Do not render fabricated
   live metrics.**

## Gonka provider/wallet plan (gonka.ai)

**What it is:** decentralized AI compute on a **Cosmos** chain (coin **GNK**, Bitfury-backed),
GPU hosts serve inference, **OpenAI-compatible API** (via SDK or **GonkaGate**). Wallet =
Cosmos keypair (a `gonka` address), fee-per-token, **gas zero**. UI takeaways: GonkaGate key
**or** native wallet, with **balance + faucet**.

**Where it slots in (two roles, both required by reframe #3):**

1. **As a provider** — IF it exposes an OpenAI-compatible base_url, it slots into the **same
   provider picker** as a `custom_url` + key kind (cheap, reuses the BYOK plumbing in
   `crypto.ts`/`external-agent.ts`). Surfaces: provider chip (05), connected-providers (17),
   per-agent provider picker (18), wizard «На чём работает» (26), Hermes supply mapping (34
   drill-down). Provider card carries its own trust metrics: nodes in network, requests
   processed, network p50/p95 latency, price-per-call in GNK.
2. **As a wallet** — a **second crypto rail** alongside TON Connect/Startonus. Surfaces: a
   Gonka chip on the wallet sheet (14) + a dedicated **Connect Gonka wallet** screen (new #3)
   showing the `gonka` address, GNK/credit balance, and a **faucet** entry. Keep its wallet
   path **out of the ordinary-user flow** — power-user / crypto-native opt-in.

**Spike before any of this is rendered as live (gating R&D):**
- Does Gonka expose an **OpenAI-compatible** endpoint we can treat as a base_url? (GonkaGate?)
- What are **p50/p95 latency** for inference (blockchain-routed compute typically adds high,
  variable latency vs centralized providers)?
- What is the **payment/settlement** model per call, and how does it reconcile with the
  product's TON/USDT off-chain credit ledger (bridge? custodial swap? separate GNK balance)?
- Until verified, render Gonka as **«бета / скоро»**, not a turnkey provider card; keep it
  behind a power-user flag.

**Phasing:** Gonka is a **P3+/R&D** item (per the feasibility audit), **not** P0. Ship the
BYOK provider picker and key-broker rail first; add Gonka once the spike confirms an
OpenAI-compatible endpoint and characterizes latency + settlement.
