# Phase-0 Spike: разворот на РЕАЛЬНЫЙ Hermes (наш UI = control-plane к Hermes REST API)

> Дизайн-документ. Дата 2026-06-12. Вход: `docs/specs/2026-06-12-product-model-hermes-IA-synthesis.md` §3 (у Hermes ЕСТЬ REST API на `:8642`: `POST /api/model/set`, `/api/jobs`, `/api/sessions`; изоляция = `hermes profile`, не pod). Сверка с реальным runtime: `apps/agent-worker/src/agent-runner.ts` (сегодня — stateless BullMQ→:4000-gateway loop).
>
> **Цель документа:** спроектировать ПРОВЕРОЧНЫЙ spike (не продакшен-миграцию), который ответит на вопрос основателя §7.3: «строим ли управляющий слой под реальный Hermes REST API, или продолжаем stateless-loop и имитируем». Spike = измерить, доказать, оценить бюджет — НЕ трогая живой money-path.
>
> **Жёсткое правило (анти-цель):** ни одна строка money/auth-пути (`agent-runner.ts`, `settleRun`, gateway `:4000`) НЕ меняется в рамках Phase-0. Spike работает на ОТДЕЛЬНОМ сервере и ОТДЕЛЬНОЙ очереди. Прод не зависит от результата.

---

## 0. TL;DR для основателя

- Текущий VPS (2GB, 5 pm2-процессов) **не тянет** ни одного Hermes-gateway (резидентно ~300-600MB) → spike нужен **отдельный сервер**.
- Рекомендация Phase-0: **1 временный VPS на 1 месяц, 8GB RAM / 4 vCPU** (Timeweb ~600-900₽/мес или почасово). Этого хватает измерить мультиплексирование 1→N профилей и снять реальную кривую веса.
- Spike отвечает на 4 числа: (а) вес 1 резидентного gateway idle/active; (б) сколько профилей мультиплексируется на X GB до деградации; (в) latency control-plane (provisioning профиля, `/api/model/set`); (г) стабильность API-ключа при ротации токена.
- Архитектурный вывод заранее: **наш agent-worker остаётся**, но получает второй режим — `hermes` provider, который вместо POST в `:4000` дёргает Hermes REST. Биллинг/кредиты/маркап остаются НАШИ (Hermes их не знает). Это аддитивно к `resolveUpstream`, не замена.
- Открытый founder-вопрос на выходе: какой сервер под прод (выделенный на high-payers vs shared ~18GB на $20-tier) и кто несёт custody Hermes-токенов.

## 1. Где поднимать Hermes (сервер под spike)

### 1.1. Почему НЕ текущий VPS
- Прод-VPS = 2GB RAM, уже держит 5 pm2-процессов (`web`, `gateway`, `tma`, `agent-worker`, `worker`) + nginx + Redis. Свободного RAM почти нет.
- Один Hermes `gateway` резидентен ~300-600MB (синтез + `/CLAUDE.md`). Даже один экземпляр вытеснит живые процессы в swap → риск для money-path. **Запрещено ставить Hermes на прод-VPS даже для теста.**
- Money-path инвариант: «money/auth-путь не трогаем, если это не задача» (`coding-behavior.md`). Подселение Hermes на тот же хост = риск OOM-killer убьёт `agent-worker` или `gateway` → косвенная поломка прода.

### 1.2. Рекомендуемый сервер под Phase-0
| Параметр | Значение | Обоснование |
|---|---|---|
| Провайдер | Timeweb (тот же, что прод) ИЛИ любой почасовой VPS | единый биллинг, знакомый деплой; почасовая оплата = выключить после spike |
| RAM | **8 GB** | вмещает 8-12 idle-профилей (~600MB) ИЛИ 3-5 active → достаточно снять кривую мультиплексирования |
| vCPU | 4 | gateway + параллельные jobs + наш control-plane probe |
| Диск | 40-80 GB SSD | профили + модели-кэш + логи |
| ОС | Ubuntu 22.04 (как прод) | воспроизводимость |
| Сеть | публичный IP | чтобы наш agent-worker (на отдельной ветке/локально) мог достучаться до `:8642` |
| Срок | **1 месяц / почасово** | spike — временный; выключаем по итогам |
| Бюджет | ~600-900 ₽ (≈$7-10) за месяц 8GB | копеечный риск против founder-решения |

- **НЕ берём GPU.** Hermes — это runtime-оркестратор; инференс он делает через внешний OpenAI-совместимый endpoint (наш `:4000` gateway / OpenRouter). Локальная модель не нужна для spike — наоборот, проверяем именно «Hermes-gateway указывает на НАШ `:4000`».
- Изоляция от прода: отдельный хост, отдельный публичный IP, **никакого доступа к прод-Postgres `aiag`** (spike пишет в свою sqlite/локальную таблицу). Сетевой доступ только исходящий к `:4000` прод-gateway (read-only, обычный API-ключ как любой клиент).

### 1.3. Что ставим на spike-сервер
1. Hermes (`NousResearch/hermes-agent` v0.15.2) по официальному гайду (`hermes-agent.nousresearch.com/docs`).
2. 1 `hermes gateway` процесс, слушает `:8642`, REST API включён (`docs/api-server`, `docs/security`).
3. Минимальный наш **control-plane-probe** (отдельный node-скрипт, НЕ `agent-worker`) — дёргает REST, провиженит профили, меряет.
4. `htop` / `pidstat` / простой сэмплер RSS по PID gateway — снимать вес.

## 2. Измерение веса профиля и мультиплексирования

### 2.1. Что именно мерим (4 числа)
| # | Метрика | Как снять | Зачем основателю |
|---|---|---|---|
| M1 | RSS gateway **idle** (0 профилей, 1 профиль) | `pidstat -r -p <pid> 5` 10 мин в покое | базовая стоимость присутствия Hermes |
| M2 | RSS gateway на **N профилей idle** | создать профили 1,2,4,8,12 → снять RSS на каждом плато | подтвердить/опровергнуть «1 gateway, profile = лёгкая изоляция» (§3 синтеза) vs «каждый профиль тяжёлый» |
| M3 | RSS + CPU на **K параллельных active jobs** | запустить K одновременных `/api/jobs`, снять пик | сколько ОДНОВРЕМЕННЫХ прогонов держит X GB |
| M4 | Точка деградации | наращивать профили/jobs до swap/латентность >2× | сколько юзеров на сервер → $/юзер |

### 2.2. Ключевая гипотеза к проверке (§3 синтеза)
> «Изоляция юзеров = `hermes profile` (свои порты/память/конфиг), ОДИН gateway-процесс, НЕ pod-на-юзера.»

Spike обязан **подтвердить или опровергнуть** это эмпирически:
- **Если** профиль = лёгкий конфиг-namespace внутри одного gateway (RSS растёт сублинейно) → мультиплексирование высокое, экономика shared-VPS работает (десятки юзеров на 8GB).
- **Если** каждый профиль поднимает свой суб-процесс/порт с ~300-600MB (RSS растёт линейно) → это де-факто pod-на-юзера → экономика как у Daytona-sandbox, мультиплексирование низкое (8GB ≈ 10-12 юзеров idle).

Это РАЗВИЛКА бюджета — поэтому M2 самый важный замер.

### 2.3. Протокол замера (воспроизводимый)
1. Поднять gateway, снять M1 (baseline).
2. Скриптом создать профиль `u1` через REST → снять RSS на плато (60с покоя).
3. Повторить до `u12`, фиксируя RSS(N) → построить кривую RSS=f(профили).
4. Прогнать M3: на 4 профилях запустить 4 параллельных коротких job (`/api/jobs`), снять пик RSS/CPU/latency.
5. Наращивать до деградации (M4): latency p95 одного job >2× baseline ИЛИ swap-in начался.
6. Вывести таблицу: «X GB → N idle-профилей → K параллельных job → $/юзер/мес».

### 2.4. Критерий «годится / не годится»
- **GO (shared-модель реальна):** 8GB держит ≥20 idle-профилей и ≥4 параллельных job без swap. → $20-tier на shared-VPS экономически сходится.
- **NO-GO (нужен pod-подход):** RSS линейна (≈профиль×500MB) → shared не даёт экономии → либо dedicated-инстанс для high-payers, либо остаёмся на stateless-loop.

## 3. Control-plane: как `agent-worker` говорит с Hermes REST вместо stateless-loop

### 3.1. Что есть сегодня (НЕ ломаем)
`agent-runner.ts` → `resolveUpstream(agent)` отдаёт `Upstream{url, apiKey, model, isExternal}` → `callWithFallback` POST'ит в `:4000` gateway (или OpenRouter fallback) → `settleRun` атомарно дебетует кредиты. Никакого состояния между прогонами, память — `loadHistory` из Postgres.

### 3.2. Что добавляет Hermes-режим (аддитивно)
Новый тип агента / провайдера: `connection_type === 'hermes'` ИЛИ `provider kind = 'managed_hermes'`. Для такого агента вместо «один POST → ответ» делаем:

```
agent-worker (Hermes-режим):
  1. ensureProfile(agent)         → есть ли hermes-профиль у этого agent_id?
                                     нет → POST /api/profiles (provision per-user profile)
  2. configureProfile(agent)      → POST /api/model/set (наша chat-модель = base_url НАШЕГО :4000 + ключ)
                                     + toolset/mcp/soul синхронизация из нашей спеки
  3. submitJob(run.input)         → POST /api/jobs  (Hermes сам крутит agentic-loop)
  4. poll/stream job              → GET /api/jobs/{id} до завершения (run-trace, kanban-события)
  5. settleRun(...)               → НАШ биллинг как сейчас (Hermes НЕ знает про кредиты)
```

**Критично:** биллинг остаётся наш и неизменный. Мы заставляем Hermes ходить за инференсом в НАШ `:4000` gateway (через `/api/model/set` base_url = `http://<наш-gateway>/v1`, key = `AIAG_GATEWAY_KEY`-аналог). Тогда:
- gateway по-прежнему применяет маркап и возвращает `x-aiag-charged-usd-micro` → **D-0 маржа сохраняется** даже когда петлю крутит Hermes, а не наш `agent-runner`.
- `settleRun` дебетует кредиты как обычно. BYOK-агент → Hermes-профиль настраивается на провайдера юзера → `isExternal=true` → 0 комиссии (правило не меняется).

### 3.3. Проблема стабильного API-ключа (§3.1 синтеза: «токен ротируется при рестарте»)
Hermes REST-токен ротируется при рестарте gateway → наш `agent-worker` не может хардкодить токен. Spike проверяет 2 варианта решения:
- **Вариант A (предпочтительный):** при старте/рестарте gateway control-plane-probe читает свежий токен из файла/CLI Hermes на хосте (`hermes config get api-token` или конфиг-файл) и кладёт в наш Redis/секрет-стор под ключом `hermes:<server>:token`. `agent-worker` читает оттуда, ретраит при 401 (перечитывает токен). То есть **наш control-plane владеет «получением свежего токена», а не статикой.**
- **Вариант B:** обёртка-сайдкар на spike-хосте, которая держит фиксированный наш статический ключ снаружи и проксирует в Hermes с текущим внутренним токеном (мы добавляем стабильность поверх ротации). По сути мини control-plane-gateway.

Spike измеряет: переживает ли (A) рестарт gateway без ручного вмешательства; задержка ре-аутентификации.

### 3.4. Изоляция money-path в spike
- Spike-`agent-worker` (на ветке, например `spike/hermes-controlplane`) работает с ОТДЕЛЬНОЙ BullMQ-очередью (`agent-runs-hermes-spike`) и пишет прогоны в spike-таблицу/sqlite, НЕ в прод `agents`/`tg_user_balances`.
- Прод-`agent-worker` не знает про Hermes-режим (код за фиче-флагом `HERMES_SPIKE=1`, по умолчанию off).
- Так выполняется «surgical changes»: каждая строка spike-кода трассируется к замеру, прод-петля нетронута.

## 4. Маппинг наш-UI → Hermes (что проксируем)

§3 синтеза даёт таблицу возможностей. В spike проверяем именно те, что мы СЕГОДНЯ имитируем/прячем, а Hermes даёт нативно. Для каждого — какой REST-эндпоинт и как ложится в наш UI (досье агента, §5C синтеза):

| Наш UI-блок | Источник в Hermes | REST / механизм | Что проверить в spike |
|---|---|---|---|
| **Чат-модель + URL** | main model + provider + base_url | `POST /api/model/set` | можем ли указать base_url=наш `:4000` и наш ключ; применяется ли без рестарта |
| **Расширенные настройки модели** | 11 aux-слотов | `/api/model/set` (slot-параметры) | задаются ли vision/compression слоты по REST |
| **Инструменты (тумблеры)** | toolsets (web/browser/image_gen/tts/code) | конфиг профиля по REST | включаются/выключаются ли per-profile |
| **MCP (серверы+тулы)** | MCP stdio/HTTP include/exclude | конфиг профиля | можем ли пробросить наш MCP-URL+токен (мы это уже умеем в `mcp-client.ts`) |
| **Личность (textarea)** | SOUL.md (free text) | запись файла профиля по REST/CLI | редактируем ли SOUL.md удалённо |
| **Память (просмотр/правка текста)** | MEMORY.md + USER.md + FTS5 (НЕ вектор) | чтение/запись файлов памяти | можем ли ОТДАВАТЬ память в наш UI на чтение/правку (честно: текст, не «семантика») |
| **Безопасность (радио)** | approval manual/smart/off | конфиг профиля | переключается ли approval по REST; как Hermes сигналит «жду подтверждения» |
| **Активность → Канбан** | Kanban (богатый) | `/api/jobs` + события | можем ли получить kanban-доску задач и проксировать в наш UI |
| **Активность → run-trace** | run-trace (богатый) | `/api/jobs/{id}` (шаги/тулколы) | формат трейса; мапится ли в наш run-trace timeline (DESIGN.md) |
| **Расписание** | cron (fan-out, skill-инъекция) | cron-конфиг профиля | ставится ли cron по REST |
| **Навыки** | skills (agentskills.io Hub) | skills-конфиг | подключается ли скилл per-profile |
| **Каналы** | 22 платформы из 1 gateway | gateway bridge-конфиг | (показываем только TG; проверить что Hermes сам бриджит TG, мы НЕ строим мост) |

**Принцип маппинга:** наш UI = control-plane-вид. Где Hermes даёт нативно (kanban/run-trace/approval/память) — **проксируем чтение и базовую правку через REST**, НЕ дублируем логику. Где Hermes не знает (биллинг, кредиты, маркетплейс-шаблоны, crypto/TON, transferable-iNFT, budget-card) — это НАШИ надстройки поверх (§3 «Гэпы»). Approval как требует подтверждения юзера — самый нетривиальный: spike должен снять, как Hermes сигналит «pending approval» и как мы пробросим кнопку «подтвердить» в TMA.

## 5. Поэтапный план миграции рантайма без поломки money-path

> Принцип: money-path меняется ПОСЛЕДНИМ и только когда Hermes-путь доказанно даёт ту же D-0 маржу. До этого Hermes — параллельный, опциональный, за флагом.

**Этап 0 — Phase-0 spike (этот документ).** Отдельный сервер, замеры M1-M4, control-plane-probe, маппинг REST. Выход: GO/NO-GO + бюджет. Прод нетронут. **Срок ~1-2 недели.**

**Этап 1 — Hermes-провайдер за флагом (`HERMES_SPIKE=1`, off на проде).** Добавить в `resolveUpstream`/новый путь ветку `connection_type==='hermes'`: ensureProfile→configure→submitJob→poll. Свой queue, свои таблицы. Один внутренний тест-агент. **Прод money-path не вызывается.**

**Этап 2 — Hermes ходит за инференсом в наш `:4000`.** Доказать: gateway возвращает `x-aiag-charged-usd-micro`, `settleRun` дебетует те же кредиты, что и stateless-loop на том же промпте. Diff маржи stateless-vs-Hermes < допуск. Это ГЛАВНЫЙ gate перед прод-включением.

**Этап 3 — Канареечный агент на проде.** 1 реальный агент 1 пользователя (или внутренний) переводится на Hermes-режим под флагом per-agent. Остальные — старый stateless-loop. Мониторим маржу/баланс/латентность неделю.

**Этап 4 — Постепенный перевод.** Новые агенты создаются в Hermes-режиме; старые мигрируют по запросу. stateless-loop остаётся как fallback (как OpenRouter сейчас). Удалять `agent-runner.ts`-петлю — только когда канарейка зелёная ≥месяц.

**Откат на любом этапе:** флаг → агенты возвращаются на stateless-loop, без миграции данных (память Hermes-профилей — отдельный стор; история прогонов как была в Postgres).

**Инвариант на всех этапах:** `settleRun` атомарность, правило «BYOK=0 комиссии», белый лейбл (Hermes-логи не должны протечь upstream-брендом в UI) — НЕ ослабляются.

## 6. Риски и открытые вопросы для основателя

### 6.1. Риски
| Риск | Вероятность | Митигация |
|---|---|---|
| Профиль ≠ лёгкий (RSS линейна) → shared-экономика не работает | средняя | именно это и меряет M2; NO-GO-критерий §2.4 даёт честный ответ ДО трат на прод-сервер |
| Ротация токена ломает control-plane неуправляемо | средняя | §3.3 вариант A/B; spike проверяет переживание рестарта |
| Hermes REST не отдаёт kanban/run-trace в удобном формате → проксирование дорого | средняя | §4 проверяет формат до обещаний в UI; если плохо — оставляем наш run-trace, не проксируем |
| Approval-флоу (pending → подтвердить в TMA) сложнее, чем кажется | средняя | snять механику в spike; если дорого — approval=off на первом этапе |
| Hermes-gateway упадёт/зависнет → агенты юзеров встанут | высокая для shared | нужен supervisor/health + откат на stateless-loop (Этап 4 fallback) |
| Утечка: память одного профиля видна другому | низкая, но критично | проверить namespace-изоляцию профилей (OWASP LLM06); GO только если изоляция доказана |
| Custody Hermes-токена / ключа нашего `:4000` на чужом хосте | — | founder-вопрос ниже |

### 6.2. Открытые вопросы — нужны решения основателя
1. **Какой сервер под прод (не spike)?** Варианты: (а) shared ~18GB VPS на $20-tier юзеров (как в `/CLAUDE.md` D-6), (б) dedicated-инстанс на high-payers + shared на дешёвых, (в) остаёмся на stateless-loop если spike NO-GO. → Решение зависит от M2/M4, но направление выбрать заранее.
2. **Бюджет на Phase-0 spike-сервер:** подтвердить ~600-900₽/мес (8GB, 1 месяц, почасово-выключаемый). Дешёвый риск против founder-уровня решения.
3. **Бюджет на прод-Hermes-сервер** (если GO): прикинуть $/юзер из M2/M4 × план по числу активных агентов. Например: если 8GB = 20 юзеров → ~$0.5/юзер/мес инфры (без инференса, инференс через наш маркап отдельно).
4. **Custody:** на чьём железе и под чьим контролем Hermes-токен и ключ нашего `:4000`? Hermes-хост получает рабочий ключ к нашему биллинг-gateway → если хост скомпрометирован, утечёт ключ маркапа. Нужна изоляция ключа (узкий scope/rate-limit на gateway-ключ для Hermes-хоста).
5. **Сколько UI проксируем vs дублируем?** Если Hermes kanban/run-trace хороши — проксируем и экономим разработку. Если формат плохой — строим своё (DESIGN.md run-trace) и Hermes только исполняет. Решается по §4-замерам.
6. **Память при transfer-iNFT (D-5 STUB):** если агент = Hermes-профиль, передача агента = передача профиля. Как перешифровать/обнулить память Hermes-профиля при transfer? Открытый вопрос, влияет на Phase-16.

### 6.3. Что spike НЕ делает (явно вне scope)
- Не строит мост Telegram (Hermes бриджит сам — §3 синтеза).
- Не меняет gateway `:4000` и `settleRun`.
- Не поднимает GPU/локальные модели.
- Не трогает прод-Postgres и прод-pm2.
- Не обещает «семантическую память» (Hermes = FTS5, не вектор — §3.48 синтеза).

## 7. Definition of Done для Phase-0

Spike считается завершённым, когда есть:
1. Таблица M1-M4 с реальными числами RSS/CPU/latency и кривой RSS=f(профили).
2. Бинарный ответ GO/NO-GO по критерию §2.4 (shared-экономика реальна или нет).
3. Доказанный control-plane-цикл: provision profile → configure (base_url=наш `:4000`) → submit job → получить ответ + run-trace, БЕЗ ручного вмешательства при рестарте gateway (токен §3.3).
4. Маппинг §4 с пометками «проксируем / дублируем / откладываем» по каждому блоку.
5. Цифра $/юзер/мес инфры для founder-решения о прод-сервере.
6. Подтверждение, что прод money-path за всё время spike НЕ вызывался (флаг off, отдельный сервер/очередь).
