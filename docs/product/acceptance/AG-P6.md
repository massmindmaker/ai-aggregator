# AG-6: восстановление и наблюдаемость — состояние и остаток

Дата среза: 30.09.2026. Ветка: `feat/ag-author-version-20260928`. Источник: `70b694b`.
Этап AG-6 роадмапа: «recovery сохранённого результата, подтверждённое отсутствие списания,
спор и возврат без нового inference. Opening balances, общая observability и полноценный
backup/restore rehearsal на отдельном стенде остаются открытыми».

**Это не приёмка release и не подтверждение production-восстановления.**

### Спор, возврат, отсутствие повторного списания
- Возврат создаёт отдельную обратную запись; спор удерживает начисление; старые чеки не меняются
  при обновлении/откате модели (`2026-09-29-author-lifecycle-checkpoint.md`).
- Повтор старого платежа в восстановленной копии возвращает прежний receipt; незавершённый платёж
  можно начислить, не меняя источник (`2026-09-29-ton-roles-and-restore-checkpoint.md`).

### 1. Репетиция восстановления на ОТДЕЛЬНОМ стенде — ЗАКРЫТО

`packages/database/scripts/off-cluster-restore.ts` — source и destination на **разных
кластерах**, роли пересоздаются на destination **до** `pg_restore`.

- **Находка, которую вскрыл отдельный стенд: кластерные глобалы не переносятся.** `pg_restore`
  на приёмнике без ролей падает `role "..." does not exist`; после `CREATE ROLE` проходит, владелец
  таблицы сохраняется. Внутри одного кластера это невозможно увидеть — роли «уже есть».
- Роли **выводятся** из `pg_namespace/pg_class/pg_attribute/pg_proc/pg_type`, не захардкожены;
  атрибуты реплицируются с источника, суперпользователи пропускаются.
- «Два кластера» **доказывается**: сравнивается `system_identifier` из `pg_control_system()`,
  совпадение → `TON_RESTORE_SAME_CLUSTER`.
- Проверка: owners/ACL byte-identical, счётчики таблиц, финансовый дайджест, источник не изменён,
  replay старого платежа через **существующую** `aiag_settle_admitted_gateway_charge` →
  `did_transition=false`, `state=settled`, число квитанций не изменилось. Один request — один
  immutable outcome.
- Гварды: `AIAG_TEST_DATABASE=1`, только loopback, порт совпадает с URL, запрет
  password/search/hash, лимит архива, temp dir 0700 / архив 0600, cleanup сверяет OID БД и
  владельца и дропает **только созданные этим прогоном** роли, и только после удаления БД.

Доказательства: `f98ed41`; нативный прогон **2/2 на двух живых кластерах** (7.75 с); без
драйвер-флага — 2 skipped (корректный skip, не тихий pass); `/tmp` чист.

### 2. Стенд и его управление — ЗАКРЫТО

`packages/database/scripts/restore-stand.sh`: одноразовый PostgreSQL 18, bind только 127.0.0.1,
trust только на loopback, `fsync=off`, `unix_socket_directories` внутри своего PGDATA (без этого
сервер не стартует — `/var/run/postgresql` недоступен). `start` **отказывается** сносить непустой
каталог без `PG_VERSION`/`server.log` — проверено пробой, файл уцелел. Smoke-тест гейтится
драйвер-флагом: 3/3 с флагом (2.53 с), 3 skipped без (676 мс).

Доказательства: `da2cb77` + `36b8cf3` (фикс ревью: гейтинг + защита от `rm -rf`).

### 3. Opening balances при cutover — ЗАКРЫТО

`packages/database/scripts/off-cluster-balances.ts`: снимок балансов, резервов и леджера до и
после restore идентичен; первый расход после cutover списывается с корректного остатка.

Рукотворный quote устранён **структурно**: `pricedCandidate` выводит `maxCredits`,
usage-снапшот и supplier-quote из одного канонического значения, а
`settleChargeViaGatewayAuthority` сам собирает прайсинг и читает фактическую стоимость из
admission. Раньше quote отвергался `aiag_quota_candidate` (миграция 0068): требовался
`requireParameters` и каноническая формула `maxCredits`, поэтому расхождение с прайсингом было
структурно возможно.

Тождество `balance + reserves == grant + credits - debits` требует явной базовой суммы `grant`
от вызывающего: стартовый грант не имеет строки в леджере, иначе тождество самореферентно.
Отражено в runbook.

Доказательства: `8d4468a`; нативный прогон **2/2**, `tsc` exit0, без утечек в `/tmp`.

### 4. Сквозная observability tenant → run → request → charge — МОДУЛЬ ЕСТЬ

`packages/api-gateway/src/billing/trace-context.ts` (1195 строк): один идентификатор на входе —
вся цепочка на выходе (org, admission, квитанция, ledger, media job, author bindings, audit).
Идентификатор валидируется **до** SQL (uuid v4 или `task_<32 hex>`), поэтому инъекционная форма
отсекается в TS, а не экранируется позже.

- **Требует admin-контекст и падает до первого запроса** — тест проверяет, что отказ даёт ноль
  SQL-вызовов, то есть неавторизованный вызывающий не может даже узнать, существует ли
  идентификатор. `orgId` сужает вызывающего до одной организации.
- Никаких миграций, OTel/Jaeger/zipkin, своего HTTP-сервера — план это запрещал.
- Предикаты на денежных таблицах не ломают индексы: metadata-матч вынесен в отдельный statement,
  аудит фильтруется с `resource_type`.
- Найдено и исправлено: при `billingRequestId === null` якорная строка молча терялась, и оператор,
  спросивший про запись в леджере, получал баланс организации без денежной строки.

Доказательства: `70b694b`; `tsc` exit0; набор gateway **1254 passed / 0 failed** (54 теста
модуля), воспроизведено дважды.

## Что осталось открытым

1. **Модуль trace-context не подключён к операторскому эндпоинту.** Нужен маршрут, а для
   эндпоинта с финансовыми записями — решение владельца о политике авторизации и аудите.
   До этого шага модуль оператору недоступен. Продуктовое решение, не регресс.
2. **Это не DR-аттестация.** Стенд локальный: `/tmp`, `fsync=off`, trust на loopback. Регулярные
   backup, RPO/RTO и off-host/cross-cluster регламент не настраивались и не заявляются.
3. **Типизация `packages/database/scripts/` не проверяется.** `packages/database/tsconfig.json`
   включает только `src/**/*`, поэтому `tsc -p` для скриптов восстановления формально даёт
   exit 0, не проверяя их. Существующая дырка конфига. Исправление — отдельная задача:
   расширить `include` или ввести отдельный tsconfig для скриптов.
4. **Native-стенд требует bootstrap+migrate.** Без миграций native-тесты падают с
   `relation "users" does not exist` — это выглядит как красный тест, но им не является.
5. **Полный unit-прогон на актуальном коммите не выполнялся** после волны 30.09: проверены
   typecheck и сфокусированные наборы. Исторические прогоны (2683/2862/2897 PASS) относятся
   к более ранним коммитам.
