# Brainstorm: «ИИ-агенты как основная аудитория» — dual-rail (₽ людям / Gram агентам)

Дата: 2026-10-09. Сессия brainstorm (superpowers:brainstorming), ветка `feat/ag-author-version-20260928`, worktree `.worktrees/ag-author-version-20260928`. Хэндофф: `/tmp/handoff-aiag-agent-brainstorm-2026-10-09.md`.

Статус: **варианты для выбора владельца**. Это не финальный дизайн и не план; после выбора варианта — отдельный design-spec → writing-plans.

---

## 1. Продуктовое решение (от владельца, 09.10)

«Основной аудиторией будут не люди. Люди будут оплачивать рублями, а ИИ-агенты — криптой. Нужна авторизация для ИИ-агентов, либо MCP, чтобы они сами себе оплачивали модели, сами настраивали себе роутинг».

Следствие: **dual-rail** — фиат(₽) для людей (вернуть, когда скажет владелец), Gram/TON для машин. Прошлонедельный TON-only-свитч фактически отменён. Фиат-гейты на проде не трогаем до команды.

Четыре проектируемые способности:
1. **M2M-авторизация** — как агент получает доступ к API.
2. **Самооплата криптой** — депозит+лимиты vs per-request микроплатежи.
3. **Самонастройка роутинга** — какие ручки управления даём агенту.
4. **MCP-интерфейс** — MCP-сервер поверх гейтвея vs plain OpenAI-compatible API.

---

## 2. Фундамент: что уже есть в коде (факты от code-explorer'ов)

### 2.1 Auth гейтвея

- Единственный механизм `/v1` — статический Bearer-ключ `sk_aiag_(live|test)_…`; SHA-256 в `gateway_api_keys.key_hash`, свежий SELECT на каждый запрос, без кэша (`packages/api-gateway/src/middleware/auth-plan04.ts:51-97`). Идентичность на гейтвее — только org, не user.
- Per-key ограничения уже есть: `rpm_limit`, `daily_usd_cap` (Redis, мягкий), `cost_limit_monthly_rub` (в кредитах с 0061), `model_whitelist`, `ru_residency_only`, policies JSONB (`default_mode`, `allowed_providers`, `blocked_providers`, `forbid_non_ru`, `allow_pii_transborder`, `per_session_budget_cap_rub`, `s2s_key_minting`) — `packages/api-gateway/src/routing/engine.ts:80-88`.
- **TTL/ротации ключей нет**; ephemeral-токенов нет.
- **S2S-минт есть**: `POST /v1/organization/keys` с `policies.s2s_key_minting=true` создаёт подчинённый ключ, зажатый по правам к родителю (`clampToIssuer`, `routes/v1/organization-keys.ts:145-293`). Но: revoke/list только через человеческий веб-дашборд; грант `s2s_key_minting` выставляется только SQL.
- Не-человеческих субъектов нет; паттерн агента-рынка = синтетический user+org+ключ (миграция 0060).

### 2.2 Биллинг/адмиссия

- Микрокредиты BIGINT (1 кредит = 1¢ = 1000 микро), тарификация в гейтвее (`lib/pricing.ts`), settle — SQL-функции с guard'ами и идемпотентностью (`0058`, `0067`).
- Stored-режим = durable admission `held → dispatched → outcome_recorded → settled|cancelled` (0067), квоты v2 per-key/per-org/per-session (0068) — **готовые примитивы спендинг-кэпов**, но enrolment явный, продукта-писателя политик v2 нет.
- Нулевой баланс → 402 до вызова upstream (`billing/settle.ts:109-125`).

### 2.3 Роутинг

- Каталог глобальный: `models` × `model_upstreams` (priority ниже=раньше, 0063), circuit breakers (0064, in-memory + PG-гидрация), 5 режимов `aiag_mode` per-request, fallback ≤3 попытки.
- Per-key политики применяются на каждом запросе, **но API записи политик нет** — только прямой SQL (дашборд пишет `{}`).
- Приоритеты fallback — глобальные, не per-org/per-key; latency/uptime статичны (воркер не обновляет).
- Управление реестром — только admin (NextAuth-admin в web / `AIAG_ADMIN_KEY` в гейтвее).

### 2.4 TON/Gram-рельс (0054–0103, готов)

- Депозит: invoice с reference `aiag-ton:<uuid>` в memo, один merchant-адрес; воркер поллит TonCenter v3 (цикл 30 с), финальность MC-depth≥2, settle `aiag_settle_ton_invoice_v1` — атомарно, идемпотентно, 14 причин review; FX CoinGecko (maxFxAge 60 c); режимы disabled|observe|settle; роль `aiag_ton_worker` изолирована (0099).
- Покупка пакета — только через NextAuth-сессию + привязанный TonConnect-кошелёк; `expected_sender` пинится (триггер 0092). **Headless-пути пополнения нет.** Ядро `expected_sender` nullable (0072:23) — ослабление возможно миграцией.
- Identity по кошельку есть (`user_ton_wallets`, ton-proof-item-v2, офлайн-верификация — `packages/shared/src/ton-wallet-proof.ts`), но: testnet-only (`CHECK(network='-3')`, 0091), login не создаёт юзера.
- Вывода крипты нет (приём-only), refunds — ручной ops-процесс.

### 2.5 agents-market (соседний репо)

Готового M2M-контура нет (субъект везде tg_user_id), но переиспользуемы паттерны: TonCenter-reconciler с тройной идемпотентностью; JWT-middleware TMA; сервисный ключ AM→AIAG с fail-closed 402; MCP-клиент с SSRF-guard и MCP-OAuth PKCE; money-CAS `UPDATE…RETURNING`. Прямого код-шеринга не предполагаем (отдельные репо/стеки: npm vs bun).

## 3. Внешний ландшафт (октябрь 2026, от web-ресёрчеров)

- **TON Agentic Wallets** (agents.ton.org, апрель 2026): изолированные Wallet V5-кошельки-агенты (SBT-токены), two-key (master у человека / operator у агента). **On-chain лимитов нет** («fund what you risk»); SDK `@ton/mcp` — alpha, kit-репозиторий архивирован 03.09.2026 → не завязываться. Платёж от такого кошелька мерчанту = **обычный Gram-перевод с memo** → наш контур принимает без изменений.
- **mcp.ton.org**: официальный TON MCP (build→emulate→send, TonProof) — паттерн для нашего MCP-фасада; не зависеть от пакета.
- **TON-финальность**: Catchain 2.0 (апрель 2026) ≈1 с через Streaming API v2; на HTTP-поллинге (наш воркер) — 10+ с. Комиссии ~$0.001/tx.
- **x402** (Linux Foundation, июль 2026; V2-заголовки PAYMENT-*): HTTP-native per-request. TON в спеке есть (`tvm:-239`), но **только TEP-74 jettons (USDT), W5R1-only, native Gram = future extension**, дефолтный фасилитатор TON не покрывает (self-host: ohld/x402-ton-facilitator, Apache-2.0, PoC). Batch-settlement (ответ на «per-request problem») на TVM отсутствует. Заимствуемо без EVM: семантика 402-challenge, verify/settle-разделение, replay-механика, batch-концепт.
- **AP2** (Google) — мандатная авторизация, ортогонален. **Stripe MPP/Tempo** — сессионные стрим-платежи, EVM. **OpenRouter** — prepaid-кредиты + provisioning-API ключей, но аккаунт только через браузер. **Nevermined/Coinbase/Crossmint** — EVM/карты.
- **Белое пятно рынка**: полностью headless-онбординг агента-плательщика (кошелёк → ключ → оплата → инференс без человека) не закрыт никем; «LLM-гейтвей, принимающий Gram per-request/по депозиту без аккаунта» — пустая ниша.
- **Юр (критично, изменилось!)**: помимо 259-ФЗ принят **282-ФЗ** (в силе с 01.09.2026, переходный до 01.07.2027): расчёты криптой за услуги внутри РФ запрещены, штрафы ст. 15.49 КоАП (ИП 300–800 т.₽; законопроект о повторных до 5 млн), обмен — только через реестр ЦБ с 01.07.2027. ЭПР узок и «для обычных ИП не работает». Агент не субъект права — плательщик = владелец ключей кошелька; оферта pay-to-accept + атрибуция плательщика. Рекомендация ресёрча: крипто-рельс decouple на иностранное юрлицо (merchant of record), ИП РФ — только ₽; GEO-фильтр, не принимать от резидентов РФ, скрининг кошельков, налоговая прозрачность.

## 4. Варианты архитектуры

Общее для всех: деньги = микрокредиты BIGINT, settle-воркер не меняем, контракт `sk_aiag_*`/OpenAI-compat для людей не ломаем,dual-rail = два способа пополнения одной кредитной корзины org.

### Вариант A — «Агентский рельс на существующем ядре» (депозит + ключ, headless)

Суть: агент получает **минимальный аккаунт по подписи кошелька** и живёт в текущей модели org+ключ+кредиты. Нового платёжного протокола не изобретаем.

Компоненты:
1. **Agent identity**: публичный headless-эндпоинт `POST /api/agent/register` (или /v1/agent/register на гейтвее): выдаёт challenge → агент подписывает ton-proof → создаётся «агентский принципал»: кошелёк → выделенная org (без человеческого user) → первый ключ. Переиспользуем офлайн-верификацию `ton-wallet-proof.ts`. Оферта pay-to-accept (оплата = акцепт; плательщик = владелец кошелька). Нужна миграция: mainnet-identity (снять `CHECK(network='-3')` для агентского контура или отдельной таблицей), таблица агентских принципалов, `expires_at`/`last_rotated_at` у ключей.
2. **Самооплата**: `POST /v1/agent/topup` (auth: агентский ключ) → возвращает invoice (существующая `aiag_create_ton_invoice_v1`) с **ослабленным expected_sender** (агент платит с любого своего кошелька, в т.ч. TON Agentic Wallet). Settle уже готов. Депозитная модель: одна транзакция → корзина кредитов; списание per-request локально (комиссия сети не per-request). Опционально: детект агентских кошельков по NFT-коллекциям TON — только аналитика/атрибуция.
3. **Лимиты расходов**: enrolment quota v2 для агентских org по умолчанию (per-key месяц, per-session, per-org день) — примитивы 0068 уже есть, нужен писатель политик. Это наш ответ на отсутствие on-chain caps у TON («fund what you risk» → risk управляем мы).
4. **Самонастройка роутинга**: новый API записи per-key политик: `PUT /v1/agent/policy` (default_mode, allowed/blocked_providers, model_whitelist, caps, TTL ключей) + `GET /v1/catalog` уже читаем агентом. Личные fallback-приоритеты НЕ даём (глобальный каталог — зона оператора; YAGNI, иначе переделка модели_upstreams).
5. **Жизненный цикл ключей по API**: rotate/revoke/list для агентского принципала (расширение organization-keys.ts), TTL по умолчанию, `s2s_key_minting` как опция для суб-агентов.
6. **402-семантика при нуле** (заимствование из x402 без EVM): ответ 402 c machine-readable JSON (сумма, ассет Gram, payTo, invoice reference, maxTimeoutSeconds, ссылка на topup) — агент сам разбирает и платит.

Оценка: ~4 новые миграции (agent principals, mainnet identity, key TTL, policy-writer роли), 3-4 новых эндпоинта, воркер не трогаем. Основная инженерия — идентичность и API-поверхность, не деньги.

### Вариант B — «402-native per-request без аккаунта» (x402-inspired на Gram)

Суть: агент без аккаунта/ключа шлёт запрос → `402 PAYMENT-REQUIRED` challenge → платит Gram per-request → повторяет запрос с `PAYMENT-SIGNATURE` → гейтвей = собственный фасилитатор: verify off-chain (подпись+seqno+validUntil+дедуп BoC-hash), ответ после verify, settle асинхронно (приём своим merchant-адресом — уже работает).

Компоненты: challenge-схема на native Gram (вне буквы x402 — там jettons), verify/settle-разделение, dedup-кэш, gasless-экономика не нужна (агент платит газ сам), при стриминге — ответ по verify, settle в фоне.

Гибрид-смягчение (batch-концепт x402 V2): первая транзакция открывает «канал»-депозит, дальше накопительные voucher'ы/локальные списания — но это схлопывается в вариант A с другим онбордингом.

Минусы: per-request сети-комиссии и латентность settle на HTTP-поллинге 10+ с (нужен Streaming API v2); клиентов-агентов на TON-402 на рынке практически нет (W5R1-only, PoC-инфраструктура); анонимные плательщики = максимальный AML/юр-риск именно в РФ-контексте; много нового кода в hot path гейтвея; защита от «ответил-не-оплатили» (hold или ответ после verify).

Роль в портфеле: не v1. Отдельные элементы (402-challenge JSON, pay-to-accept) заимствуются в A.

### Вариант C — «MCP-фасад поверх гейтвея» (канал, не платёжный протокол)

Суть: наш MCP-сервер (streamable HTTP, паттерн mcp.ton.org) как **дополнительный интерфейс** к A (или позже B): tools `list_models_prices`, `get_balance`, `create_topup_invoice` (внутри готовит BOC/plain-перевод с memo — агенту остаётся подписать), `set_routing_policy`, `chat_completion` (прокси в /v1). Auth — агентский ключ в заголовках (serverless-паттерн `@ton/mcp`).

Плюсы: агенты с TON/MCP-скиллами подключаются нативно; MCP-дискавери как канал дистрибуции; монетизация MCP-инструментов — устоявшийся паттерн рынка.
Минусы: MCP-транспорт не заменяет OpenAI-compat для тяжёлых modalities (batches/media, стриминг больших ответов); OAuth 2.1-модель MCP тяжелее статического ключа; overhead.
Вывод: C — не альтернатива A, а тонкий слой над A. Как «основной» интерфейс не рекомендуем.

## 5. Таблица компромиссов

| Ось | A: депозит+ключ (headless) | B: 402 per-request | C: MCP-фасад |
|---|---|---|---|
| Time-to-market | высокий (недели: миграции+API, деньги готовы) | низкий (новый протокол+facilitator) | средний (тонкий слой поверх A) |
| Нового кода в hot path | минимум (endpoints + колонки) | много (challenge/verify/settle/dedup) | ноль (прокси) |
| Переиспользование | максимальное (0054–0103, ключи, квоты v2) | частичное (только приём платежей) | максимальное |
| UX агента | регистрация один раз → ключ → депозит → работа | нулевой онбординг, но платёж на каждый чих | удобен для MCP-нативных агентов |
| Экономика сети | 1 tx на депозит | 1 tx на запрос (+латентность 10 с+ на поллинге) | как A |
| Спендинг-кэпы | наши quota v2 (сильнее TON on-chain, которых нет) | баланс кошелька = лимит | как A |
| AML/юр-риск | средний (атрибуция кошелька, оферта, лимиты) | высокий (анонимные per-request) | как A |
| Совместимость с чужими агентами | нужна интеграция (наш SDK/доки) | формально x402-нарратив, но TON-клиентов нет | MCP-агенты подключаются сразу |
| Конкурентная ниша | headless prepaid для агентов (пустая) | Gram-402 LLM-гейтвей (пустая, но ранняя) | MCP-витрина LLM (почти пустая) |

## 6. Рекомендация

**A как ядро + C как тонкий MCP-фасад (этап 1.5). B не строим в v1**; из x402 заимствуем только 402-challenge-семантику при нулевом балансе (machine-readable JSON) и концепт депозитного канала, уже реализуемый в A.

Обоснование: платёжное ядро и квоты уже построены и проверены (миграции на проде); рынок подтверждает паттерн prepaid+per-key-limits (OpenRouter) как мейнстрим для машин; TON-экосистема сама не даёт on-chain caps — наш слой лимитов становится фичей; B упирается в раннюю инфраструктуру TON-402 и максимизирует юр-риск.

Правовой гейт: приём Gram от внешних агентов на ИП РФ после 282-ФЗ — прямой запрет с штрафами → крипто-рельс оформлять на иностранное юрлицо (или минимум: GEO-фильтр + оферта + не-резиденты, до переезда). Это блокер mainnet-запуска агентского рельса, не дизайна.

## 7. Вопросы владельцу

1. **Юрлицо**: когда создаём зарубежную компанию под крипто-рельс (merchant of record)? До неё — тестовые платежи только testnet? (282-ФЗ: с 01.09.2026 расчёты криптой за услуги в РФ запрещены, штрафы до 800 т.₽+.)
2. **Активы**: только native Gram, или добавляем USDT-jetton (спека x402 и рынок — USDT; наш settle сейчас native-only, jetton-приём — доп. работа)?
3. **Headless self-signup**: подтверждаешь модель «кошелёк = аккаунт агента, оплата = акцепт оферты, плательщик = владелец кошелька»? (без человека в цикле, включая отзыв только через подпись кошелька)
4. **Роутинг агенту**: достаточно per-key политик (режим/провайдеры/whitelist/капы) + aiag_mode per-request? Личные fallback-приоритеты агенту НЕ даём в v1 — ок?
5. **MCP-фасад**: делаем в v1 (этап 1.5) или отложить до спроса?
6. **Лимиты по умолчанию** для агентских ключей: предложить (месячный кап $N, дневной, per-session, TTL ключа 90 дней) или задашь цифры?
7. **Mainnet-identity**: поднимать миграцией сейчас или стартуем агентский контур в testnet параллельно с gram-витриной (включение которой и так ждёт твой адрес)?
8. **Ревью TON-ветки**: ты хотел ещё одно ревью (упоминал «Кейман» = caveman-режим, распознан) — отдельной сессией, каким скоупом?

## 8. Что НЕ входит (границы)

- Не включаем gram-витрину на прод (ждёт адрес кошелька + «включаем testnet» — отдельный гейт Task 8 прошлого плана).
- Не возвращаем фиат сами (TINKOFF_*/YOOKASSA_* env — только по команде).
- Не строим вывод крипты (payout) — приём-only остаётся.
- Не трогаем глобальный каталог/upstreams для агентской самоначинки.

## 9. Следующие шаги (после выбора варианта)

1. Владелец выбирает вариант (рекомендация: A+C) и отвечает на вопросы §7.
2. Design-spec по выбранному варианту (этот файл → `docs/superpowers/specs/<дата>-agentic-rail-design.md`) по правилам brainstorming-скилла.
3. writing-plans → имплементация (миграции → API → 402-JSON → MCP-фасад).
4. Параллельно отдельной сессией: ревью TON-ветки (по указанию владельца).
