# Дизайн: разделение монорепо на TMA и AIAG-Web — 2026-06-12

**Статус:** дизайн (решения приняты автономно по запросу основателя «не спрашивай, делай сам»). Через Superpowers (брейншторм→спек→план→исполнение). Исполнение — отдельная аккуратная операция (необратимая git-хирургия + новая deploy-инфра ×2), не в текущей мега-сессии.

## Цель
Разнести монорепо `aggregator` на два самостоятельных репозитория, чтобы TMA (агент-маркет) и AIAG-Web (₽-аггрегатор) развивались независимо.

## Карта зависимостей (разведано 2026-06-12)
| | apps | packages (workspace @aiag/*) |
|---|---|---|
| **TMA** | tg-miniapp, agent-worker | **shared, database**, typescript-config |
| **Web** | web, worker, api-gateway(в packages) | **shared, database**, email, telegram-alerts, tinkoff, yookassa, upstream-adapters, typescript-config |
| **ОБЩИЕ** | — | **shared · database · typescript-config** (используются обоими) |

История: 74 коммита трогали tg-miniapp, 212 — web; .git = 190M.

## 🔴 Главная сложность (решение принято)
`shared` + `database` нужны ОБОИМ, и **Postgres один на двоих** (оба читают/пишут tg_* и gateway_* таблицы; D-0/D-1 деньги ходят через общий gateway). То есть продукты СВЯЗАНЫ данными и HTTP-контрактом gateway. Полный split не разрывает эту связь — он разрывает только КОД.

**Решение по общим пакетам: ДУБЛИРОВАТЬ** `shared`/`database`/`typescript-config` в оба репо (для команды из 2 человек проще, чем приватный npm-registry/сабмодуль).
- **`database` (Drizzle-схема) — канонична в Web-репо** (там money-path gateway + большинство таблиц), копируется в TMA. При изменении схемы — синк руками (миграции и так ручные/без трекинга на проде, схема стабильна). Зафиксировать в обоих CLAUDE.md.
- **Интеграция остаётся через общий Postgres + gateway :4000 по HTTP** (как сейчас, рантайм). Это не меняется — продукты остаются связаны на уровне данных, репозитории разъезжаются только по коду.

## Решения (автономные)
1. **Два репо:**
   - **`agent-market`** (TMA): tg-miniapp + agent-worker + shared + database + typescript-config. Дефолтная ветка = текущая рабочая (consolidated → переименовать в main при split).
   - **`aiag-web`**: web + worker + api-gateway + shared + database + email + telegram-alerts + tinkoff + yookassa + upstream-adapters + typescript-config.
2. **История:** сохранить через `git filter-repo` на свежем клоне (по путям каждого продукта). Если filter-repo недоступен (Windows) → допустим чистый снапшот (потеря per-file истории, но снапшот текущего состояния; 2-человечный ранний продукт это переживёт). Решение при исполнении по факту наличия инструмента.
3. **Deploy:** каждый репо получает СВОЙ `deploy-production.yml` (наследует уже-починенный пайплайн: scp-bypass артефактов + sudo-pm2 + cleanup-до-pm2). VPS-пути `/srv/aiag/<app>/` остаются те же (бокс общий). Секреты (DEPLOY_*) копируются в оба репо. **Сначала поднять deploy в новом репо и проверить, что он деплоит ТОТ ЖЕ бокс, и только потом депрекейтить монорепо-пайплайн** — чтобы прод ни секунды не остался без рабочего деплоя.
4. **Монорепо `aggregator`:** НЕ удаляем сразу. Остаётся как архив/резерв, пока оба новых репо не подтвердят рабочий деплой на прод. Потом — пометить deprecated (README) или заархивировать.
5. **graphify/AGENTS.md/.planning:** `.planning/` и docs релевантные TMA → в agent-market; web-специфичные → в aiag-web; общие доки (CLAUDE.md split на два).

## Безопасный порядок исполнения (план верхнего уровня)
Фаза 1 — **agent-market (TMA)**, без касания живого монорепо:
1. Свежий клон → filter-repo (или снапшот) только TMA-путей → новый GitHub-репо `agent-market`.
2. Переписать `package.json`/workspace под новый набор, `bun install --frozen-lockfile`, typecheck 0.
3. Добавить `deploy-production.yml` (наследие починенного), завести DEPLOY_*-секреты.
4. Тест-деплой tma+agent-worker из НОВОГО репо → тот же бокс, тот же релиз-механизм → health 200.
Фаза 2 — **aiag-web** аналогично (web+worker+gateway).
Фаза 3 — переключить «боевой» деплой на новые репо, монорепо → deprecated/archive.
Каждая фаза: typecheck + тест-деплой + прод-health, прежде чем идти дальше.

## Риски / митигации
- **Схема-дрифт** (database дублирована) → канон в web, синк руками, зафиксировать в CLAUDE.md; схема стабильна + миграции ручные уже.
- **Прод без деплоя в момент перехода** → новый пайплайн поднимается и проверяется ДО депрекейта старого (фаза-overlap).
- **Потеря истории** (если снапшот) → монорепо архивируется, история не теряется (доступна в архиве).
- **Деньги-путь** → код money-path (agent-worker settleRun, gateway D-0) едет целиком в свой репо без изменений; общий Postgres/gateway-контракт не трогаем.

## Почему НЕ исполнено сразу
Это необратимая структурная операция (новые репо, фильтр истории, ×2 deploy-инфра) на ЖИВОМ money-path-продукте, сразу после починки деплоя. Правильно — исполнять отдельной сфокусированной операцией по этому плану (фаза за фазой, с проверкой прод-деплоя на каждой), а не в конце огромной сессии. Дизайн и порядок зафиксированы здесь.
