## Цель и границы

Исследования должны выбрать полезные сценарии и снять неопределённость перед реализацией. Число фич, моделей или интеграций само по себе не является успехом. Рабочая гипотеза общего продукта: **создать версию решения → проверить качество → опубликовать → выполнить задачу → получить результат и корректный расчёт → использовать обратную связь для следующей версии**. Каждый сервис при этом даёт самостоятельную ценность: API-покупатель не обязан участвовать в конкурсе, пользователь агента — становиться автором, участник Arena — продавать решение.

Основание: [функциональный срез](../ecosystem/2026-09-07-functional-checkpoint.md), [чекпойнт](../consolidation/2026-09-07-pause-checkpoint.md), [предыдущее проверенное исследование](2026-09-07-ai-hub-reviewed-synthesis.md). Баллы не повышаются за документы; исследование не отменяет принятые денежные инварианты, отдельные БД/репозитории и результат независимого review.

Статусы ниже означают именно состояние исследования: **очередь** — ещё не выполнено; **частично** — есть перечисленная опора, но выход не принят; **срез готов** — закончена ограниченная проверка с явными исключениями. P0 снимает неопределённость перед ближайшими продуктовыми изменениями; P1 нужен до соответствующей функциональной волны/выпуска; P2 — гипотезы следующего горизонта. Это не общий запрет исправлять известные ошибки до завершения всей программы.

## Порядок и ограничение объёма

**Волна A — продуктовые решения:** R01/R02/R03/R16; R04 и R05/R06 параллельно с ограниченной выборкой. Сначала выбрать по одному ценному сценарию для AG, AM и Arena и общую связь между ними. Для первой desk-итерации достаточно сравнения 3–4 релевантных альтернатив по одинаковым задачам. Интервью и пилот — отдельные evidence; если респондентов пока нет, явно оставить гипотезу и продолжать обратимые работы.

**Волна B — необходимые контракты:** R07/R09/R10/R12/R13, R18 по выбранным зависимостям. R08 следует за сценариями; R11 — за выбором runtime и trust boundaries. Результат волны — конкретные спецификации, а не решение немедленно переписать все три сервиса.

**Волна C — продуктовый выпуск:** R14/R15 и фактические эксперименты R16. Пройти самостоятельные сценарии и межпродуктовый pilot. R17 идёт отдельно и не блокирует рабочий v1; новая технология включается по доказанной потребности.

Известные узкие исправления продолжаются без нового общего research: AM cleanup deadline и terminal settlement CAS; AG уже принятый durable quota design; Arena contest deadlines. Исследование требуется там, где остаётся решение, способное изменить интерфейс, модель данных, финансовый контракт или выбранный runtime. Оно не разрешает пропускать уже обязательные tests/review.

## Как результат попадёт в разработку

Материальные пропуски проверяются явно: коммерческая комиссия не должна влиять на независимый рейтинг Arena (R12); отзыв подключения или истечение найма переоценивается перед новым внешним действием (R10/R11); доступность API/платежей для выбранных пользователей и стоимость поддержки двух клиентов входят в R14. Эти вопросы имеют владельцев, даже если ответ пока неизвестен.

Каждый пакет завершается карточкой: **вопрос → источники/версия/дата → наблюдение → уверенность → альтернативы → принятое решение или bounded experiment → ограничения → IDs задач/проверок**. Для отрицательных результатов тоже записывается решение. «У конкурента есть» не является критерием добавления функции.

Перед implementation исполнитель открывает связанные R-IDs, проверяет свежесть именно влияющих фактов и добавляет в узкий Superpowers plan поля `Research inputs`, `Decision/ADR`, `Acceptance`, `Deferred`. Изменение вывода отражается одновременно в плане, API/state contract и приёмке. Если вывод не влияет ни на решение, ни на тест, дополнительный обзор останавливается. Завершение исследования требует reviewed вывода; feature readiness требует отдельного работающего кода и evidence.

Серьёзные продуктовые/архитектурные исследования — Astra high; извлечение источников/инвентаризация — более лёгкая модель через model-router. Независимые источники можно исследовать параллельно; один владелец на документ, один тяжёлый run на хост. Общий интегратор принимает выводы и устраняет противоречия.

## Гипотезы сильных функций для проверки

Это кандидаты R01/R02/R16, не обещанный scope: (1) выбор агента по примеру нужного результата с проверенными стоимостью/правами; (2) результат и квитанция одного run с понятным восстановлением; (3) паспорт качества точной версии из Arena; (4) рабочий набор подключений и знаний с переносом между своими агентами без утечки секретов; (5) выпуск новой версии только после измеримого улучшения и возможности отката. Для каждого нужны наблюдаемая потребность, эффект и стоимость поддержки. Личная память пользователя или тестовые данные не передаются на обучение/публичную Arena без отдельного основания.

## Хранение и возобновление

Репозитории хранят планы, решения и evidence. Этот реестр содержит общую навигацию; Brain и Memory Graph ссылаются на владельцев, Serena/Graphify индексируют код. LightRAG получает устойчивые принятые выводы с provenance/readback; очередь исследований и сырые журналы туда не дублируются. Статус последней семантической синхронизации см. в [MEMORY-STATUS](../consolidation/MEMORY-STATUS.md); наличие новых файлов не означает обновления внешней памяти.

После паузы: сверить код/HEAD → прочитать этот реестр и нужный продуктовый entrypoint → выбрать первый незакрытый вопрос перед задачей → завершить его bounded output → обновить план → реализация и проверка через Superpowers. Перечитывание всей программы на каждой маленькой правке не требуется.
