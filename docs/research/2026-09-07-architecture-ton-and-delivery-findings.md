# AI Hub: архитектура, общий вход TON и влияние на выпуск

Дата проверки: 07.09.2026. Исследовательский вывод для R09/R10/R11/R13/R14/R15/R17/R18. Это desk/source analysis и предложения к планам; новый код, платежи, кошельки и production-конфигурация не изменялись. Пользователь во время исследования уточнил: **вход через TON-кошелёк нужен в AI Aggregator, Agents Market и AI Arena**. Wallet-only, удаление RUB или автоматическое объединение существующих аккаунтов не запрашивались.

## Резюме решения

Выбранные три репозитория и отдельные доменные БД подходят текущему масштабу. Основной недостаток — незавершённые контракты исполнения, денег, идентичности и версий. Дополнительный orchestration framework не закрывает эти разрывы автоматически. Рекомендуется сохранить существующие приложения и workers, добавить версионированные HTTP-контракты, серверные state machines и локальные outbox/inbox там, где действительно есть межсервисный эффект. Это архитектурный вывод по [текущему функциональному срезу](../ecosystem/2026-09-07-functional-checkpoint.md), а не утверждение, что нынешняя реализация оптимальна при любой нагрузке.

TON даёт общий способ входа и платёжный транспорт. В первом выпуске один пользовательский кошелёк может использоваться во всех трёх продуктах, но каждый продукт выдаёт собственную сессию и ведёт собственные обязательства. Автоматический SSO и взаимозачёт трёх балансов — отдельные функции. Пользователю нужен понятный переход и сохранение владения, а backend — однозначный ответ, кто авторизовал действие, кто принял платёж и кто отвечает за возврат.

В AM текущий управляющий backend и денежный ledger сохраняются. Hermes можно подключать как изолированный исполнитель через его реальный протокол длительных запусков после contract tests. Сначала завершаются полезный run, подтверждение результата, расходы и восстановление; установка произвольных сторонних расширений откладывается до доказанной изоляции.

## 1. Общий TON sign-in: доступная функция и граница доверия

[TON proof documentation](https://docs.ton.org/applications/ton-connect/how-to/ton-proof) описывает backend verification подписи и выдачу сессии. Нужны одноразовый challenge, ожидаемые domain/address, срок, подтверждённый public key и атомарное потребление nonce. Важная деталь: сама подпись `ton_proof` **не связывает сеть**; выбранная сеть проверяется отдельно. SDK и wire spec также различаются представлением timestamp. Поэтому скопированный сниппет из Context7 не является законченной реализацией верификатора. [Спецификация TON Connect](https://github.com/ton-blockchain/ton-connect/blob/main/spec/connect.md) — отдельный источник совместимости; её ревизия фиксируется перед implementation.

Предлагаемый UX: выбрать вход кошельком → подписать понятный запрос входа → получить серверную сессию → продолжить выбранную задачу. Подключение адреса без доказательства не создаёт сессию. Вход не требует перевода средств. Подпись входа не выдаёт право автоматического расходования и не меняет адрес выплаты автора. Отдельно отображаются отказ пользователя, неподдержанный proof, неподходящая сеть, истёкший запрос и недоступная проверка.

**ADR-W1, рекомендовано для v1:** общий versioned proof-verification contract и набор conformance fixtures, но отдельные challenge/session/account owners в трёх backend. Поля домена/сети/purpose выбираются сервером по опубликованной поверхности; nonce связан с конкретным login/link attempt. Testnet и mainnet credentials/fixtures не смешиваются. Пакет общего кода, если появится, распространяется закреплённой версией; импорт соседнего checkout запрещён.

Альтернативы: один новый общий identity service сразу добавит единую точку отказа и миграцию всех auth flows; три независимых копии криптографического алгоритма создадут drift. Для v1 выбирается общий контракт и тестовый набор, затем решение о центральном issuer на основе потребности в настоящем SSO. Это не обещание однократной подписи на все домены: proof одного dApp не переносится как login token другого.

**Account linking:** если человек уже вошёл через Web/TG, добавить wallet можно только при свежем доказательстве обеих сторон — действующей сессии нужного аккаунта и контроля кошелька. Одинаковый display address, имя или Telegram username не объединяют аккаунты. Уже привязанный wallet вызывает явный conflict flow; перенос активов/данных не производится автоматически. Внутренний user ID остаётся стабильным при добавлении или смене кошелька. Для потерянного кошелька нужен заранее подключённый способ восстановления; поддержка не восстанавливает криптографический контроль по одному заявлению.

При реализации проверяются: чужой/повторный/истёкший nonce, неверный domain, future timestamp, address/public-key mismatch, подпись для другого purpose, network substitution, две конкурентные привязки, session fixation, конфликт двух существующих аккаунтов, disconnect и отзыв сессии. Изменение payout wallet — отдельная step-up операция. Эти тесты пока не выполнялись; существующий AM wallet binding требуется проверить на переиспользование, а не автоматически признать полноценным login.

### Что уже есть в коде и что предстоит изменить

Проверка текущих canonical checkout обнаружила в AM **привязку кошелька к существующему Telegram аккаунту**, а не самостоятельный wallet login. [Выдача proof payload](/home/bob/Projects/agents-market/apps/tma/app/api/tma/wallet/proof-payload/route.ts) и [link route](/home/bob/Projects/agents-market/apps/tma/app/api/tma/wallet/link/route.ts) требуют уже выданную сессию; ответ link не выдаёт новую сессию. Этот flow нельзя считать готовой авторизацией Web.

В [текущем verifier](/home/bob/Projects/agents-market/apps/tma/src/lib/ton-proof.ts) challenge построен из timestamp/HMAC, без случайного server nonce, привязки к аккаунту/purpose и атомарного consume; проверка ожидаемой сети отсутствует. Извлечение public key из stateInit требует отдельной проверки поддерживаемого wallet code/layout. Следующий auth brief включает ограниченную входную schema, server-bound одноразовый challenge, canonical network/address, доказательство ключа и негативные replay/link tests. Это вывод чтения исходников; live эксплуатация или полноценный security audit не выполнялись.

В [AM identity schema](/home/bob/Projects/agents-market/packages/database/migrations/0001_identity.sql) есть UUID accounts, но [wallet bindings](/home/bob/Projects/agents-market/packages/database/migrations/0006_wallet_and_ledger.sql) ещё принадлежат Telegram ID, а уникальность проверяет исходную строку адреса. Нужен аккуратный переход на account ownership с проверкой адресных aliases и сохранением старых прав/балансов; адрес кошелька не подставляется вместо Telegram ID в существующий JWT. В проверенных [AG auth providers](/home/bob/Projects/ai-aggregator/apps/web/src/auth.ts) и [Arena auth providers](/home/bob/Projects/aiarena/aiarena-app/src/auth.ts) TON-вход пока не зарегистрирован. Это ограниченный срез текущего кода, не утверждение обо всех ветках или deployed releases.

## 2. Shared infrastructure: что сохраняем и что добавляем

**ADR-A1, сохраняем принятый принцип:** каждый продукт владеет профилем/ролями, своей БД и ledger; общая идентичность связывается явными claims/consent. Межсервисный credential не равен пользовательской browser-сессии. Вызов чужого API проверяет audience, scope и конечного владельца ресурса. Публичный artifact manifest не содержит личной памяти или credentials. Основание и существующие [API/data ownership contracts](../ecosystem/integration.md) уже определены.

Вместо новой большой общей платформы нужны четыре практических контракта: catalog/capability/price revision; run/attempt/usage receipt; immutable artifact/version/rights; evaluation evidence/method/dataset. Доменное изменение и outbox пишутся одной локальной транзакцией, доставка допускает повтор, принимающая сторона хранит inbox identity и идемпотентно применяет событие. Отключение Arena не должно останавливать ранее купленный агент; недоступность AG не должна запускать неразрешённый платный fallback. Это наши проектные требования, а не гарантия выбранного брокера.

[OpenRouter routing](https://openrouter.ai/docs/guides/routing/provider-selection) предоставляет явные provider/data/parameter/price policies; для AG переносим контракт выбора и объяснимый отказ при несовместимости. Публичный каталог должен отличать модель, deployment, capabilities и тарифную ревизию. Fallback расходует общий разрешённый бюджет попыток. [Replicate prediction lifecycle](https://replicate.com/docs/topics/predictions/lifecycle/) подтверждает полезность самостоятельной сущности исполнения со статусом; наша отмена и refund policy определяются собственным финансовым контрактом.

## 3. Runtime и расширения: очередь не является денежной гарантией

[BullMQ stalled jobs](https://docs.bullmq.io/guide/workers/stalled-jobs) описывает потерю worker lock и последующую обработку stalled job. [Idempotent jobs](https://docs.bullmq.io/patterns/idempotent-jobs) требует проектировать задания с учётом повторов. Следовательно, повтор очереди не разрешает автоматически ещё раз вызвать платную модель, отправить письмо или перевести средства. Нужны сохранённая identity попытки, authoritative outcome и reconciliation неопределённого результата.

**ADR-A2, рекомендовано:** AM Postgres/control plane + текущая очередь остаются владельцами run и денег. Изолированный Hermes adapter — сменный executor с закреплённой версией, собственным lifecycle и ограниченными capabilities. Он не получает merchant treasury keys и чужие connections. Фактические возможности/ограничения Hermes сведены в [полную матрицу семейства функций](/home/bob/Projects/agents-market/docs/research/2026-09-07-hermes-capability-matrix.md). Готовность hosted isolation и recovery проверяется отдельно от наличия API.

Новый workflow engine или Kubernetes рассматриваются только при измеренном дефиците нынешнего решения: невозможности воспроизводимо восстанавливать требуемые многошаговые сценарии, неприемлемых queue lag/capacity либо невозможности изоляции в выбранном hosting. Замена очереди без этих данных добавит миграцию и не решит side-effect idempotency. Возможные новые backend-функции BullMQ из последней документации не считаются поддержанными установленной версией до R18.

**ADR-A3, рекомендовано:** connection/binding/invocation отделены от skill/plugin package. Для v1 — curated встроенные tools и remote MCP, затем versioned skills, позже изолированное исполнение third-party code. [MCP authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) и [безопасность](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices) задают собственные resource/auth границы. Shell sandbox не заменяет разрешение внешнего аккаунта. Revocation, новый scope и истечение найма проверяются перед следующим действием во всех клиентах. Полный вывод — [extensions research](/home/bob/Projects/agents-market/docs/research/2026-09-07-providers-and-extensions.md).

## 4. Общий TON-контур и раздельные обязательства

**ADR-M1, рекомендовано:** общие asset/invoice/verification contracts и UX, но product-owned invoices/ledger/refund/payout. Вход кошельком не перемещает деньги между продуктами. Общий экран может показывать суммы по владельцам, не обещая, что баланс одного сервиса оплачивает любой другой. Исторические RUB и AM единицы сохраняются до отдельной миграции. Базовые состояния и ограничения уже заданы в [payment/evidence design](../ecosystem/payment-and-evidence-design.md).

Для v1 предпочтительны раздельные merchant receiving addresses или иной доказанный способ разделения получателей по продукту. Если будет выбран один общий receiving address, до запуска потребуется **один авторитетный owner входящих chain events и глобальная защита от повторного зачёта**: три независимых сканера не должны зачислять один перевод трижды. Общий signer/custody backend также требует собственного доменного владельца и политики; он не возникает из общего TON SDK.

Server quote закрепляет asset, сумму в atomic units, курс/срок/комиссию и recipient. Сначала подтверждается входящий chain effect, затем выдаётся доступ/кредит. Исходящая выплата — отдельное обязательство с durable intent и проверкой неизвестного исхода перед повтором. Это сохраняет текущие инварианты и не требует собственного escrow smart contract для первой версии. Право на возврат, налогообложение, допустимость способов выплат и условия providers остаются отдельной проверкой перед коммерческим выпуском; исследование инженерной схемы их не устанавливает.

## 5. Экономика: что можно решить сейчас

Достоверных фактических unit-cost/pilot данных сейчас нет, поэтому итоговая наценка, author share и цена запуска не назначаются. Вычислять нужно стоимость **принятого полезного результата**, включая неудачные попытки, tools, compute, storage, платёжные комиссии, возвраты и поддержку. Это собственная модель расчёта, а не оценка рынка:

`Маржинальный вклад продукта = признанная выручка − затраты поставщика/инструментов − инфраструктура задачи − комиссии − авторское вознаграждение − фактические возвраты/поддержка`.

В консолидированной экономике хаба внутренний счёт AG→AM исключается как внутригрупповой оборот; внешний inference cost учитывается один раз. Если определение признанной выручки уже содержит возвраты, повторно вычитать их нельзя. Для цены нужны измеренные сценарии base/high-cost/provider failure и чувствительность к курсу/длительности/повторным попыткам. Access fee и usage показываются раздельно до запуска, BYOK объясняет, кто выставляет внешний счёт. Существующие обязательства не пересчитываются по новой формуле автоматически.

R14 получает конкретный следующий артефакт: dataset pilot runs с cost components, outcome acceptance и support events, затем versioned pricing policy с break-even диапазоном. До этих данных заявлять прибыльность или брать цифры из старого landing нельзя. Это ограничение измерений, а не основание остановить реализацию receipt/лимитов.

## 6. Эксплуатация и критерии выпуска

[BullMQ production guidance](https://docs.bullmq.io/guide/going-to-production) отдельно требует настройки Redis persistence/eviction и поведения соединений. Наличие работающего worker не доказывает восстановление очереди. [OpenTelemetry HTTP conventions](https://opentelemetry.io/docs/specs/semconv/http/http-spans/) указывают на риск сбора всех headers; для хаба trace по умолчанию содержит IDs/состояния/метрики, а не prompts, токены и личные документы. [Текущий индекс OpenTelemetry conventions](https://opentelemetry.io/docs/specs/semconv/) сообщает о переносе GenAI conventions в отдельный репозиторий: версия instrumentation фиксируется при внедрении, не копируется произвольный старый атрибут.

Сохраняем AG на восстановленном VPS, AM TMA/API/worker — на существующем размещении; отдельный AM Web Vercel остаётся кандидатом после API/auth compatibility. Arena выпускается независимо. [Live audit](../consolidation/2026-09-07-resume-audit.md) выявил конфликтующие владельцы процессов; это отдельная эксплуатационная задача до обновления боевого релиза. Дополнительный read-only probe в этой исследовательской волне: публичный AG `/health` снова вернул200/ok, но платный inference не выполнялся.

Нужны связанные request/run/attempt/receipt/evidence IDs, возраст pending операций, queue lag, ошибки providers, фактическая стоимость принятого результата и ответственный оператор. До release: backup restore на отдельном стенде, restart/replay/refund/unknown payout сценарии, source/build/schema/deployed parity и rollback. Нагрузочный бюджет и SLO определяются наблюдением выбранного пилота, не выдуманным обещанием uptime.

## 7. Горизонт развития без блокировки v1

| Возможность | Решение сейчас | Условие следующего шага |
|---|---|---|
| TON wallet login | Включить в функциональную спецификацию всех трёх продуктов | Proof/link/recovery conformance + отдельная приёмка клиентов |
| Agentic wallet | Сохранить adapter boundary и отдельный testnet pilot | [Текущие contracts](https://docs.ton.org/onboarding/ai/wallets) помечены developer preview и не прошедшими аудит; перед средствами перепроверить именно release/audit и лимиты, не общий аудит TON |
| A2A | Внешний adapter к собственному Run/Artifact API | Реальный внешний потребитель, pinned [protocol](https://a2a-protocol.org/latest/specification/) и conformance, auth/expiry/budget |
| x402/AP2 | Изолированная последующая ветвь платежей/mandates | Совместимый актив/network/facilitator и доказанная потребность; [предыдущая проверка](2026-09-07-ai-hub-reviewed-synthesis.md) остаётся опорой, live settlement не выполнен |
| Автоматическое улучшение агента | Кандидат версии → Arena regression → staged release → rollback | Разрешённый dataset/trace, измеримое улучшение, неизменность прав и лимитов; не самостоятельная выдача себе новых полномочий |
| Новые compute/identity протоколы | Не добавлять в critical path v1 | Измеримое преимущество по цене/качеству/доступности; не обещать будущий аудит/релиз к дате |

## Ограничения и противоречия

Проверены собственные документы, primary docs/протоколы и источники параллельных исследований. Для конкретных API вендор — один первичный authority; несколько страниц одного вендора не считаются независимой триангуляцией. Архитектурные выводы сопоставляют TON/MCP/BullMQ и собственные failure cases, но не доказывают превосходство на несуществующем нагрузочном тесте. Нет интервью, платных вызовов, оценки маржи или испытания нового wallet login.

Context7 успешно использован для TON Connect. Его криптографический пример сверён с primary documentation; пример не закрывает atomic nonce, network/domain policy и account linking. LightRAG hybrid recall успешно ответил, но фрагмент вновь содержал историческую двухпродуктовую/монорепозиторную модель; она отвергнута в пользу текущих канонических boundaries. Это подтверждение необходимости provenance, а не неработоспособности сервера памяти.

Матрица источников исследовательской волны сохраняется рядом с итоговым synthesis. Изменения планов и take/defer/reject решения — [результат интеграции исследований](2026-09-07-research-impact-and-decisions.md). Данный отчёт не меняет функциональные F-баллы и не закрывает production gates.
