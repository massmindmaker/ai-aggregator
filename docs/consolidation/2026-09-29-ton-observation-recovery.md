# AEG Web: восстановление сверки TON

Дата: 29.09.2026. Только AI Aggregator. База: `fe6b10f`; рабочая ветка `feat/ag-author-version-20260928`.

## Что изменено

Продолжен существующий TON3-план с Task4. Предыдущие чистый verifier, native-only TON Center adapter и PostgreSQL-наблюдения уже были реализованы и приняты; они не переписывались. Авторский цикл также сохранён без изменений.

Добавлен обработчик сверки одного источника, который получает временное право обработки в БД, продолжает с сохранённой позиции, проверяет возвращённые данные и записывает наблюдения. Позиция меняется только после подтверждённых записей всей принятой части страницы. Если связь оборвалась после записи, следующий процесс читает фактическое состояние БД, а не предполагает, что запись не состоялась.

Два процесса не могут одновременно обрабатывать один источник. После истечения или передачи права обработки старый процесс не записывает результат позднего ответа и не освобождает право нового владельца. Во время запроса к поставщику открытая SQL-транзакция не удерживается.

При остановке завершается уже начатая операция в ограниченное время. Незавершённое ожидание не считается ни подтверждением платежа, ни доказательством его отсутствия. Поздний ответ не запускает последующие записи.

## Существенные ограничения

Это **только наблюдение за платежами**, не автоматическое пополнение клиентского баланса. Даже результат verifier `verified` сохраняется как `verified_candidate`. Проверки на настоящей PostgreSQL отдельно подтверждают нулевое изменение покупательского баланса и отсутствие нового TON settlement event.

Поддерживается только native TON в testnet `tvm:-3`. Jetton, mainnet и режим `settle` отвергаются. Факты берутся из ранее выбранной модели доверия серверному индексатору; они не названы самостоятельно проверенным криптографическим доказательством.

Создана функция безопасного запуска `startTonObservationFromEnv`, по умолчанию отключённая. **В общий worker index она не подключена и на работающем сервисе не включена.** Сначала нужны независимое ревью этой волны и следующий пакет с проверенным внутренним путём settlement. Права отдельного worker в БД проверяются ещё одним самостоятельным этапом; одного флага или TypeScript-типа недостаточно.

Новых миграций, изменений исторического SQL, зависимостей, Web-страниц и provider endpoints в этой волне нет. Production, внешние RPC, тестовые переводы, mainnet и реальные выплаты не выполнялись.

## Проверяемые границы

| Область | Реализованный контракт |
|---|---|
| Входные данные | Точный источник, сеть, asset и адрес; идентификатор источника пересчитывается. Позиция из внешнего запроса не принимается. |
| Право обработки | 90 секунд; повторная проверка до получения страницы, после получения и при сохранении новой позиции. |
| Объём | До четырёх целых страниц по восемь кандидатов за один проход. После четвёртой страницы непрочитанная история не сбрасывается. |
| Ожидания | Весь запрос страницы ограничен 60 секундами; каждый вызов БД — 10 секундами; закрытие пула — 5 секундами. Исходные 8 секунд на отдельный provider HTTP-запрос сохранены. |
| Повтор после сбоя | Наблюдения дедуплицируются. Потеря подтверждения записи требует нового чтения/claim, а не повторного изменения курсора вслепую. |
| Остановка | Новая работа не начинается; уже начатая операция получает только оставшийся срок. Закрытие memoized, повторный вызов не создаёт повторных release/pool-close. |
| Суммы и идентичность | Используются существующие immutable invoice, exact reference и verifier policy. Новый обработчик не пересчитывает цену и не вызывает settlement. |

Неизвестная reference записывается отдельно без привязки к случайному счёту. Неполный trace или недостаточная глубина индексирования остаются наблюдением; противоречивые данные передаются на проверку. Ошибка поставщика сохраняет позицию и использует существующую задержку повторной попытки, рассчитанную БД.

## Локальные доказательства

Первый набор новых проверок: 63 PASS. Отдельные шесть сценариев с настоящей PostgreSQL прошли до финального уточнения контроля ошибок. Финальная профильная проверка включает новые тесты вместе с ранее принятыми provider/verifier тестами; точные окончательные числа и commit приведены в завершающем разделе.

Native-сценарии проверяют потерянное подтверждение сохранённого наблюдения, запуск конкурирующего процесса, отсутствие SQL-транзакции во время ожидания поставщика, передачу права обработки, потерянное подтверждение изменения позиции, серверную задержку следующей попытки и остановку после записи. Каждый сценарий отдельно проверяет, что деньги не начислены. Данные провайдера синтетические, а записи, блокировки и транзакции PostgreSQL настоящие.

При самопроверке исправлены три воспроизведённые ошибки: занятый источник больше не выдаётся за отсутствие платежа; неизвестный результат сохранения наблюдения сохраняет неопределённость; некорректное подтверждение освобождения права обработки тоже не называется известным исходом. Линтер не отключался. Ошибка нового теста числа миграций исправлена учётом обоих каталогов: 89 ordered SQL + 1 Drizzle baseline = 90.

Независимого GLM/Codex-одобрения этой волны нет. Новый запуск рецензента не имитировался; сохранён узкий review brief и журнал результатов. Ранее Codex упёрся в квоту, подтверждённого интерфейса автоматического GLM/ZCode-ревью в этой сессии нет. Это остаётся отдельным условием дальнейшего runtime-подключения.

## Как повторить на локальной машине

Из актуального worktree, с установленными Bun 1.4.2 и локальными тестовыми PostgreSQL/Redis:

```bash
bun install --frozen-lockfile
flock /tmp/ai-ecosystem-build.lock bun run --cwd apps/worker type-check
flock /tmp/ai-ecosystem-build.lock node node_modules/typescript/bin/tsc -p apps/worker/tsconfig.ton-recovery-test.json
flock /tmp/ai-ecosystem-build.lock bun run --cwd apps/worker build
scripts/with-native-test-services.sh bash -c 'bun run db:test:bootstrap && RUN_NATIVE_DB_INTEGRATION=1 bun run test:unit --no-file-parallelism --testTimeout=60000 --hookTimeout=60000 apps/worker/src/__tests__/ton-payment-reconciler.native.integration.test.ts'
flock /tmp/ai-ecosystem-build.lock bun run test:unit --no-file-parallelism --testTimeout=30000 --hookTimeout=60000
```

Native helper сам удерживает общий lock — не нужно оборачивать его во второй `flock`. Сценарии используют одноразовые дочерние БД, а не production. Команды не выполняют перевод, RPC-запрос или включение фонового сервиса.

В плане остаются: независимое ревью Task4, Task5 с внутренним settlement-путём и проверкой его повторов в fixtures, Task6 с подключением observe-запуска только после его prerequisite gates, отдельная проверка worker-only полномочий БД. Затем — связка кошелька, checkout и подтверждённый testnet-платёж. Чистые тесты наблюдения не разрешают пропускать эти этапы.
