# Матрица функционала экосистемы: кто чем владеет

Дата: 30.09.2026. Решение владельца, зафиксированное здесь как основание:
**авторские начисления остаются в Aggregator**, конкурсная площадка уезжает в Arena.

## Решение в одну фразу

**Два входа публикации, один каталог, один авторский кошелёк — всё в Aggregator.
Конкурсный контур (заявки, отбор, оценка, лидерборд, призы) — целиком в Arena.**

```
        ┌─ вход 1: с улицы ─────────────────┐
        │  автор сам публикует модель        │
        │  Aggregator /dashboard/models      │
        └────────────────┬───────────────────┘
                         │
                         ▼
              ┌──────────────────────┐
              │  AGGREGATOR          │
              │  • каталог версий    │  ← единственный источник правды о том, что продаётся
              │  • модерация         │
              │  • вызов + биллинг    │
              │  • начисление автору  │  ← единственный авторский кошелёк
              │  • выплата автору     │
              └──────────┬───────────┘
                         ▲
        ┌────────────────┴───────────────────┐
        │  вход 2: из конкурса                │
        │  ARENA → publication-drafts (HTTP)   │
        │  автор нажал «опубликовать» в конкурсе│
        └─────────────────────────────────────┘
```

Ключевое: вход 2 **не создаёт второй кошелёк и второй каталог**. Arena говорит
«этот участник выиграл с этой версией» — Aggregator делает всё остальное.

## Что меняется при выпиливании конкурса из Aggregator

| Было в Aggregator | Становится |
|---|---|
| `api/contests/**`, `api/admin/contests/**` | удаляется, функция переходит в Arena |
| `schema/contests.ts`, `evaluations.ts`, `prize-awards.ts` | удаляются из схемы; **применённые миграции остаются** |
| `queues/contest-eval.ts`, `close-contests-cron.ts`, `eval-runner/**` | удаляются |
| Лидерборд читает `contest_submissions.public_score` | удаляется; лидерборд в Arena |
| `author_earnings`, `earnings.ts`, начисление за модели | **ОСТАЁТСЯ** — это не конкурс, это продажа моделей |
| `contest_submissions.published_model_id` | удаляется; связь «конкурс → каталог» заменяется на HTTP-вызов `POST /v1/publication-drafts` |

## Как лучше сделать — рекомендация

**1. Не удалять код сразу. Сначала ввести HTTP-вход, потом убрать конкурс.**

Порядок, при котором ни один шаг не ломает работающее:
1. Реализовать `POST /v1/publication-drafts` в Aggregator — идемпотентный, по `manifest_digest`,
   с авторским согласием. Это **общий вход** для обоих путей.
2. Переключить `api/admin/contests/[slug]/publish-submission` на вызов этого эндпоинта
   (временная проверка, что он ходит туда же).
3. Добавить в `/v1/catalog` авторские модели — иначе Arena опубликует, а агент не увидит.
4. **И только теперь** удалить конкурсный код из Aggregator и перенести в Arena.

Так конкурсный контур перестаёт быть источником истины, но не ломает себя на полпути.

**2. Разделить `payouts`/`author_earnings` на два смысла, если они общие.**
Авторская выплата за продажу модели и выплата приза за конкурс — разные сущности с разной
семантикой. Если они седят на одной таблице, удаление конкурса не должно уносить выплату
автору. Это проверяется первым шагом.

**3. Данные в конкурсных таблицах, скорее всего, отсутствуют** — миграции создают схему, но
работающего evaluator'а не было ни в одном продукте (заглушка выбрасывает результат). Если
строк нет, удаление кода не требует миграции данных. Это надо проверить до удаления.

**4. Что делать с применёнными миграциями: оставить.** Они историческая запись. Таблицы
останутся в БД мёртвыми, что безопасно и обратимо. Удаление через `DROP TABLE` — отдельное
решение, и его стоит принимать, когда Arena заберёт функциональность.

**5. Судьба `publish-submission` в Arena: вызывать Aggregator, а не дублировать.**
Arena получает `author_consent_id` и версию, Aggregator делает `publication-drafts`. Так
авторский кошелёк и начисления остаются в одном месте, а Arena не получает ещё одну
финансовую книгу.
