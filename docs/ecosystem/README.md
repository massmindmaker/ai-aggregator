## Решение

Три самостоятельных продукта образуют общий цикл: **разработка → доказательство качества → продажа → применение → новая оценка**.

- **AI Aggregator** продаёт доступ к AI-моделям и исполняемым алгоритмам: каталог, API, подключение авторов, тарификация, доход и выплаты.
- **AI Arena** организует конкурсы и независимое сравнение моделей, агентов и RAG-систем. Владеет заданиями, методиками, результатами, голосами, рейтингами и призовыми процессами.
- **Agents Market** продаёт шаблоны и использование агентов, управляет их запуском, наймом, подключением рантаймов и бюджетами. Покупает модели у Aggregator как отдельный клиент. По уточнению основателя имеет **два отдельных приложения: полноценную веб-версию и Telegram Mini App**, с общими API, каталогом и агентным движком.

Допущение: «RAC-системы» означает RAG-системы. «Финальный этап» — промышленный выпуск согласованной версии v1, включая полный цикл автора и интеграцию; дальнейшее развитие продукта не имеет конечной точки. Последующие указания основателя разрешили автономную локальную реализацию всего плана и разделение на три репозитория. Платные операции и внешняя публикация этим локальным этапом не выполнялись.

Проверенные фрагменты кода показывают:

1. В свежем web есть транзакционный settlement платежей. Однако в исследованном `settle.ts` начисляется `users.balance`, а прямого обновления кошелька организации нет. Требуется проследить весь путь до платного вызова gateway; наличие webhook-теста не доказывает доступность купленных кредитов.
2. В `core` TMA всё ещё читает `models/model_upstreams` SQL-запросами. Физическая и контрактная независимость от Aggregator не завершена.

4. В Arena есть auth, challenges, teams, moderation, notifications и audit. В исследованной схеме и дереве API не обнаружены полноценные submissions/evaluations/battles/votes. Это существенная разработка, а не финальная полировка экранов.
5. В web-repo общий worker запускает evaluator, но его production wiring результата содержит log-only sink. Polling внешних задач также подключён через заглушки. Старый конкурсный контур можно использовать как источник отдельных компонентов, но не объявлять готовой Arena.

## Шкала 108: доказательства вместо впечатления

У каждого продукта **12 блоков × 3 требования × 3 подтверждения = 108 баллов**. Три требования каждого блока перечислены в его плане. За каждое требование начисляются по одному баллу за:

1. **I — реализацию:** законченный сценарий, работающий серверный эффект и соответствующий UI/API; записаны commit и путь.
2. **T — проверку:** воспроизводимый тест с положительным и отрицательным случаем, изолированными данными и результатом на указанном commit. Для финансов/ролей/очередей обязательны гонки, повторы и сбои.
3. **O — эксплуатационную приёмку:** проверено на выпущенной версии в нужном окружении; записаны release, дата, сценарий восстановления/поддержки и подтверждение владельца. Для UI — браузерная проверка, для денег — сверка проводок, для договора — утверждённый документ и работоспособность связанного процесса.

O нельзя засчитать без I и T. Частичный интерфейс не даёт балл за весь сценарий. Непроверенное обозначается `UNVERIFIED`, отсутствующее `MISSING`, пройденное `PASS`, проваленное `FAIL`. N/A не повышает оценку: изменение обязательного состава требует новой версии шкалы. CSV изначально UNVERIFIED — это реестр будущей приёмки, а не утверждение, что всё отсутствует.

Сумма экосистемы — 324 продуктовых проверки **плюс** сквозные тесты интеграции. Высокий средний балл не компенсирует неработающий денежный контур или изоляцию пользователей.

| Известная прежняя оценка | Что она означает |

| Web 65.5/108, ревью 03.09, ссылка в плане исправлений | Исторический показатель до/вокруг последующих исправлений. Полный исходный протокол этого ревью здесь не восстановлен |
| Arena 48/108, 31.08, HEAD `4bb4762` | Полнота исходного продукта по прежней шкале экранов и потоков |

Эти числа нельзя сравнивать между собой или выдавать за текущую оценку. Честный новый балл требует прохода по единой матрице на актуальном commit и окружении.

| E5. Эксплуатационная доводка | UX всех ролей, нагрузка, поддержка, восстановление, отчётность, независимые релизы | Все 108 проверок каждого продукта PASS и все интеграционные проверки PASS |

После E0 независимые части Arena (teams/workspace) и Agents Market (UX/runtime) можно вести одновременно с денежными исправлениями Aggregator. Общий API-контракт проектируется с E0, сквозные тесты начинаются с E1, а не после полной готовности трёх приложений. Один тяжёлый build/test одновременно на текущем 6-ГБ хосте.

Ориентир трудоёмкости, **не обещание сроков**: E0 3–5 инженерных дней; Aggregator 30–50; Arena 50–85; Agents Market вместе с отдельными Web и TMA 45–80; общая интеграция и выпуск 20–35. Итого 148–255 инженерных дней до резерва. Диапазоны предполагают reuse имеющегося кода и одного поддержанного рантайма; добавить 25–35% резерва после E0. Внешние подключения платежей, юридические решения, GPU и ожидание пилотных пользователей считаются отдельно. Через E0 оценки пересчитать по фактическим карточкам работ.

3. Дни 6–8: закрывать разрыв settlement→кошелёк gateway; Agents Market — клиент каталога; Arena — схема submissions и жизненный цикл задачи evaluator.
4. Дни 9–10: демонстрация первого вертикального среза, сверка проводок, негативные проверки и корректировка очереди. Не пытаться одновременно завершить все экраны трёх продуктов.

Владелец каждой задачи — соответствующий продукт; изменения API требуют согласованного contract-test у потребителя. Задача закрывается связкой `ID → commit → тест → release/evidence`, а не сообщением «сделано». Блокеры безопасности, денег, прав доступа и потери данных запрещают выпуск независимо от суммы баллов.

## Измеримая финальная приёмка

Предлагаемые внутренние цели для v1, подлежащие фиксации по ресурсам в E0. Это не заявленный клиентам SLA и не фактические результаты тестирования.

| Область | Проверяемый критерий |
|---|---|
| Бизнес-цикл | Каждый основной сценарий проходит от нового аккаунта до сохранённого результата и квитанции; есть отдельные прогоны модели, агента и RAG, Web и TMA |
| Деньги | В race/replay/failure-наборе нет повторных начислений/выплат и необъяснимых проводок; любая pending reconciliation видна оператору и имеет срок разрешения |
| Изоляция | Все негативные проверки tenant/role/secret проходят; нет открытых критических дефектов доступа, SSRF/runner isolation или утечки данных |
| API | На согласованной тестовой нагрузке 20 параллельных клиентов p95 собственной добавленной задержки gateway ≤300 мс; время upstream измеряется отдельно; очередь имеет backpressure |
| Интерфейс | На целевых устройствах p75 LCP ≤2.5 с, INP ≤200 мс, CLS ≤0.1 для ключевых web-поверхностей; до набора полевых данных использовать согласованный лабораторный прогон и честно обозначать его |
| Восстановление | Учебное восстановление на отдельном окружении: предложенные RPO ≤1 час, RTO ≤4 часа; внешние денежные эффекты дополнительно восстанавливаются сверкой провайдера, не только backup |
| Пилот | Не менее 7 дней наблюдения и минимум 10 завершённых сквозных сценариев на продукт; нет неразобранных инцидентов денег/данных; маленькая выборка не выдаётся за доказательство долгосрочного SLA |
| Релиз | Все обязательные I/T/O и INT PASS; фиксированы версии, миграции, feature flags, возврат к предыдущему релизу и ответственный за поддержку |

Нагрузочные данные создавать на отдельной БД и контролируемых adapters; боевые платные upstream проверки выполняются только в согласованном бюджете. Метрики релиза не подменяют продуктовую цель: marketplace обязан довести независимого автора до продажи и дохода, Arena — до достоверной оценки, Agents Market — до полезного результата и понятной стоимости.
